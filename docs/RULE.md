# RULE.md — yok3x 멀티 에이전트 운영·개발 규칙

이 문서는 yok3x 프로그램을 **만들고 쓸 때** 지켜야 할 규칙이다. 코드·리포트·에이전트 작업 모두 여기에 따른다.

---

## 1. 정체성 — 코딩용 멀티 에이전트 도구

- 목적: Claude·Codex·Gemini CLI를 묶어 **구독 한도를 지키며** 코딩 루프(구현→리뷰→수정)를 돌린다.
- YouTube/콘텐츠용이 아니라 **코딩용**이다. 워커·태스크·라우팅은 코딩 워크플로우 기준.
- 의존성 0(파이썬 표준 라이브러리만). 새 의존성 추가 금지.
- Windows 우선 지원(개발자 실사용 환경). 모든 변경은 Windows에서 검증한다.

## 2. 한도는 무조건 지킨다 (요금 가드)

- 실측 한도가 있으면 그것이 기준이다: **codex = app-server 라이브 실측**, claude = transcript 롤링 추정(+`calibrate` 보정), gemini = 원장.
- 매 워커 호출 전 가드 점검. `hard_ratio` 도달 시 루프 자동 정지. 실측 실패 시 `on_probe_failure` 정책(기본 ledger 폴백).
- 정확한 수치를 모르면 **지어내지 말 것**. claude 토큰 상한은 `plan` 프리셋(근사) 또는 `calibrate`(정확)로만 설정.

## 3. yok3x 기법 (프로그램을 만들 때 적용)

코드를 생성/수정하는 워커에는 **계획 → 구현 → 자가검증** 구조를 강제한다(`orchestrator.YOK3X_TECHNIQUE`).
폭주 방지 4중 브레이크를 항상 건다:

1. **단계 분할** — 한 번에 다 하지 않고 스텝 단위로 실행·로그.
2. **사람 승인** — 게이트(y/N/q). `--auto`는 신뢰된 루프에서만.
3. **항상 검증** — 검수 워커(producer-reviewer) + 체크리스트.
4. **예산 제한** — 요금 가드.

## 4. 할루시네이션 방지 (필수)

- 모든 워커 프롬프트에 사실성 규칙 주입(`orchestrator.ANTI_HALLUCINATION`): 추측을 사실로 쓰지 말 것, 모르면 '모름', 존재하지 않는 파일·함수·API·플래그 날조 금지, 근거 제시.
- 검수 워커는 환각/날조를 명시 지적(`REVIEW_GUARD`).
- 체크리스트가 근거 없는 과잉 확신 표현을 자동 표시.
- **에이전트(및 이 프로그램을 만드는 AI)도 동일 규칙을 따른다**: 파일·함수·수치를 주장하기 전에 실제로 확인(Read/실행)하고, 검증 못 한 것은 "미확인"으로 표시한다. 렌더/실행으로 확인 가능한 것은 코드만 보고 단정하지 않는다.

## 5. 검증 우선 (코드만 보고 판단 금지)

- 동작·수치·렌더는 **실제로 실행/확인**하고 보고한다. 실패는 실패대로, 스킵은 스킵대로 정직하게.
- "될 것이다"가 아니라 "실행해서 됐다/안 됐다"로 말한다.

## 5.5 폴백·하드코딩 최소화 (필수)

- **폴백(fallback)과 하드코딩은 꼭 필요한 곳에만** 적용한다. "일단 돌아가게" 식 임시 폴백·매직넘버 금지.
- 허용 기준:
  - 폴백: 외부 자원(CLI·파일·네트워크) 실패 시 **명시적 열화 경로**가 사용자에게 표시되는 경우만 (예: 실측 실패 → `⚠stale`/`원장` 배지). 조용히 값을 지어내는 폴백 금지.
  - 하드코딩: 프로토콜 상수(API 필드명·창 크기 300/10080분 등)·안전 상한(타임아웃)은 허용. **사용자 환경마다 다른 값**(예산·한도·경로·모델명)은 반드시 설정(yok3x.json)으로 뺀다.
- **적용할 때는 별도 리포트를 만들어 제출한다**: 어디에 · 왜 필요한지 · 실패 시 어떻게 표시되는지 · 설정으로 뺄 수 없는 이유. 리포트 없는 폴백/하드코딩 추가 금지.
- 기존 폴백/하드코딩 현황은 최신 `docs/reports/*-fallback-hardcoding-audit-*.md` 레지스트리에서 추적한다.

## 5.6 GUI · UI/UX 변경은 사용자 명령 없이 금지 (필수)

- **사용자의 명시적 지시 없이 GUI·UI/UX(`gui/` 파일, 화면 레이아웃·문구·색·상호작용)를 바꾸지 않는다.**
  기능/백엔드 수정 중 GUI를 건드리고 싶어져도, 명령이 없으면 **손대지 않는다**.
- GUI를 바꿔야 한다고 판단되면 **직접 수정하지 말고 리포트로 제안**한다: `reports/`에 무엇을 · 왜 ·
  어떻게 바꿀지 적어 제출하고, 사용자의 승인을 받은 뒤에만 반영한다.
- 예외: 백엔드가 GUI에 넘기는 **데이터 값**(버전 문자열, 사용량 수치, 모델 목록 등)을 정확하게
  고치는 것은 데이터 정정이며 GUI 레이아웃 변경이 아니다 — 단, 표시 방식(문구·배치)을 바꾸는 것은
  본 규칙의 대상이다.

## 5.7 저장소 루트에 임시/테스트 산출물 만들지 않기 (필수)

- **저장소 루트에 `.tmp`/`.pytest-*`류 임시 디렉터리를 만들지 않는다.** pytest·codex 등 외부
  도구를 실행할 때 `--basetemp`를 저장소 안 경로로 주지 말 것 — 시스템 임시 디렉터리(기본값)나
  세션 스크래치패드를 쓴다. 근거: `pyproject.toml`의 F2-3 결론(2026-07-27, 실측) — yok3x 자체
  pytest 설정은 이 문제를 안 일으키지만, `--basetemp=...`를 **CLI 인자로 직접 넘기는 외부
  호출**은 그 설정을 그대로 이긴다. 특히 codex 등을 샌드박스(`--sandbox`)로 돌릴 때 그 프로세스가
  시스템 임시 디렉터리에 쓰기 권한이 없어 저장소 안으로 `--basetemp`를 돌리는 경우가 실제로
  반복 발생했다(2026-08-11~12, 소유권 회수도 안 되는 권한으로 남아 삭제조차 어려운 잔해가 다수
  쌓임 — 재발 방지가 사후 정리보다 훨씬 싸다).
- **테스트용 샘플·픽스처 데이터**는 반드시 `test_samples/`나 `tests/`(용도에 맞는 기존 폴더) 안에
  만든다 — 저장소 루트나 새 폴더를 임의로 만들지 않는다.
- codex 등 외부 에이전트에게 pytest 실행을 맡길 때는 프롬프트에 저장소 밖 임시 경로(예: 세션
  스크래치패드)를 명시적으로 지정하도록 요청한다.

## 6. 리포트 파일 네이밍 규칙

`reports/` 아래 리포트 파일명은 **[버전]-[짧은 작업명]-[날짜]-[시간]** 형식:

```
v2.3.0-gui-prototype-2026-07-04-1336.md
v2.3.0-coding-fit-review-2026-07-04-1340.md
```

문서 맨 위 헤더에도 동일하게 `버전 · 작업 · 날짜 시간`을 적는다.

## 7. 변경 이력 (HISTORY.md)

- 코드·기능·문서를 바꾸면 **매번 [HISTORY.md](HISTORY.md)에 한 줄 이상 기록**한다: 버전, 날짜/시간, 변경 요약.
- 릴리스(zip)를 만들 때 버전을 올리고 HISTORY에 릴리스 항목을 남긴다.

### 7.1 버그 리포트 (docs/reports/bugs/)

- **버그를 발견·수정할 때마다** `docs/reports/bugs/BUG-NN-<slug>.md`를 만들고 인덱스(`docs/reports/bugs/README.md`)
  표에 추가한다. 형식: 증상 · 근본원인 · 진단 · 수정 · 검증 · 교훈 (+ 시점·심각도·커밋·상태).
- 디버깅 세션의 내역을 이 폴더에 **꾸준히 누적**한다(잊지 말 것). HISTORY는 요약, bugs/는 상세 근본원인.

### 7.2 문서 폴더 구조 (docs/)

문서는 **유형별 폴더**로 나눈다. 매 작업마다 해당 유형 파일을 만들거나 갱신한다.

| 위치 | 무엇 | 시점 |
|------|------|------|
| `docs/plans/` | 계획서·제안서(`vX.Y.Z-plan-*`) | **작업 전**(미래지향) |
| `docs/reports/` | 평가·분석·감사·리뷰·완료보고(`*-assessment-*`·`*-analysis-*`·`*-audit-*` 등) | **작업 후/에 대해**(회고) |
| `docs/reports/bugs/` | 버그 리포트(`BUG-NN-*` + README 인덱스) — §7.1 | 버그 수정 시 |
| `docs/HISTORY.md` | 변경 이력(단일 파일) — §7 | 매 변경 |
| `docs/RULE.md`·`docs/ADOPTIONS.md` | 규칙·채택 원장(루트 유지) | 규칙/채택 변경 시 |

- **README.md는 저장소 루트 유지**(pyproject `readme=` + GitHub 관례). docs/로 옮기지 않는다.
### 7.3 HISTORY 롤링 아카이브 (codex 공동검토 2026-07-18)

활성 이력은 항상 `docs/HISTORY.md`(폴더 안 이동 — 참조 안 깨짐). 파일이 커지면 낡은 항목만 아카이브한다.

- **트리거**: `docs/HISTORY.md`가 **800줄 또는 80KB 초과** 시(둘 중 하나). minor·월 기준은 증가량이 불규칙해 부적합.
- **아카이브**: 오래된 **완전한 엔트리 묶음**을 순번형 `docs/history/HISTORY-vNNN.md`(v001부터)로 이동.
  버전명 파일명은 한 파일에 여러 버전이 걸쳐 부적합 → 순번형. 각 아카이브 상단에 담긴 날짜·버전 범위 기록.
- **활성본 잔존**: 롤링 후 **최신 30개 엔트리**를 남긴다(단, 한 작업/릴리스 묶음이 경계에 걸리면 묶음째 남김).
- **인덱스**: `docs/history/README.md`에 `파일 · 날짜 범위 · 버전 범위 · 엔트리 수` 표를 갱신.
- **수동**(과설계 지양). 2~3회 반복해 번거로우면 그때 `yok3x` 서브커맨드로 스크립트화.
- 항목별로 쪼개지 않는다(통독·grep 편의) — 묶음 단위로만 아카이브.

## 8. 릴리스 · 버전 보존

- 정본 소스: **저장소 루트**(패키지 `yok3x/` + `gui/`·`tests/`·`docs/`·`pyproject.toml`·`yok3x.py`). 배포물: `release/yok3x-vX.Y.Z.zip`.
- zip 만들기 전 `__pycache__`·런타임 산출물(`.yok3x/`·생성된 `yok3x.json` 등) 제거.
- Windows 스모크 테스트(`init/setup/run/gui/limits`) 통과 후 패키징.
- **이전 버전 zip을 삭제하지 않는다.** 새 릴리스를 만들면 이전 릴리스 zip을 `backup/versions/`로 옮기고 `backup/versions/VERSIONS.md`에 항목을 추가한다(내부 `__version__`으로 검증). 리브랜딩 등 대규모 변경 전에는 정본 폴더 전체를 `backup/`에 스냅샷한다.

### 8.1 주기적 백업 (누적 트리거)

업데이트가 일정 이상 쌓이면 **묻지 말고 자동으로** 스냅샷한다. 트리거(**아무거나 하나** 충족 시):

1. **버전**: minor 이상 올릴 때(x.**Y**.0 / **X**.0.0) → 릴리스 zip을 `backup/versions/`에 반드시 보존(§8) + 정본 폴더 스냅샷.
2. **누적 변경**: 마지막 스냅샷 이후 **HISTORY 항목 5개** 또는 **patch 3회**가 쌓이면 → 정본 폴더 전체를 `backup/yok3x-vX.Y.Z-YYYYMMDD-HHMM/`로 스냅샷.
3. **위험 작업 전**: 리네임·대량 삭제·구조 변경 등 되돌리기 어려운 작업 **직전** → 스냅샷.
4. **시간**: 활발히 작업한 날은 그날 마지막 작업 후 1회 → 스냅샷(선택).

스냅샷 방법: 정본 소스 트리(패키지 `yok3x/`·`gui/`·`tests/`·`docs/`·`pyproject.toml`·`yok3x.py`)를 `backup/yok3x-<버전>-<날짜시간>/`로 복사(`__pycache__`·런타임·`backup/`·`release/` 제외). 버전 zip은 `backup/versions/`(추적됨, GitHub 보존), 폴더 스냅샷은 `backup/`(로컬). 스냅샷 시 HISTORY에 한 줄 남긴다.

> 요지: "일정 이상 쌓이면"(HISTORY 5개/patch 3회/minor 버전/위험작업 전) = 백업 시점. 판단이 애매하면 백업하는 쪽으로.

## 9. TeamFlow 이슈 트래킹 (실무 작업 관리, 2026-09-05 도입)

- **TeamFlow(yok3x 프로젝트, key=YOK, projectId=89)를 이 저장소의 실제 작업 등록·관리 공간으로 쓴다.**
  지금까지 한 작업과 앞으로 할 작업은 문서(TODO.md 등)뿐 아니라 TeamFlow 이슈로도 등록해 추적한다.
- 연동은 MCP 워커도구(§3, a1)로 되어 있다: `yok3x.json`의 `mcp_servers.teamflow`(로컬 경로,
  git 미추적) → `jira_for_me/mcp-server`(별도 저장소) → `mcp-server/.env`의 `TEAMFLOW_API_TOKEN`
  (git 미추적, yok3x-bot 계정, YOK 프로젝트 admin 권한).
- 워커가 TeamFlow 도구를 쓰려면 task.json의 `agents.<worker>.mcp_tools`에 `servers`·`allow_tools`를
  **필요한 도구만 최소로** 명시해야 한다(opt-in, 화이트리스트 — §3 폭주 방지와 동일 원칙). MCP 도구
  호출은 `_gate_mcp` 승인 게이트를 항상 거친다(자동화 시에도 우회 안 됨 — 사람이 그 순간 승인).
- `create_issue`의 `projectId`는 **숫자 id**(YOK=89)이며 프로젝트 key("YOK")가 아니다 — 실제 혼동
  사례가 있었다([YOK-2](https://jira-for-me.vercel.app), mcp-server 쪽 스키마 설명 보강 필요로 등록됨).
- 이슈 설명(desc) 필드의 실제 파라미터명은 `description`이 아니라 `desc`.
- 부분 수정은 `update_issue_fields`(배치, 보내지 않은 필드 보존)를 쓴다. `replace_issue`(전체 교체)를
  쓰면 보내지 않은 필드가 기본값으로 초기화되니 일부 필드만 바꿀 때는 쓰지 않는다.
