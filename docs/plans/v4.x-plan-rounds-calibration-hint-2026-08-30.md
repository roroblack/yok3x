# v4.x · 계획 — 실측 라운드 캘리브레이션 힌트(V-8 파일럿) · 2026-08-30

## 배경 (사용자 제안)

사용자 지적: `triage.estimate_execution()`과 `automation.recommend_effort_rounds()`는 둘 다
**작업 텍스트 길이·키워드 같은 정적 특징**으로만 pattern/tier/rounds를 추천한다("추천만,
적용 안 함"). 실제로 쌓인 실행 결과(calibration.jsonl)를 근거로 삼는 "증거 기반" 버전이
있으면 더 낫지 않겠냐는 제안 — "이건 근거있는 증류잖아".

## 조사 결과

1. **원래 제안(에이전트 종류·수 자동 결정)은 지금 데이터로 불가능**: 메인 저장소(2건)+T-2
   전체(22건), 총 24건의 실 calibration 기록을 확인한 결과 **전부 `producer-reviewer`
   패턴**이었다. `solo` 패턴 실행 기록이 단 하나도 없어 "이 유형엔 producer-reviewer가
   solo보다 낫다"를 학습할 대조군 자체가 없다 — V-1이 원래 부딪혔던 것과 같은 종류의
   선행조건 미충족이지만, 여기선 표본 수가 아니라 **변수(pattern) 자체의 다양성이 0**이라는
   점에서 더 근본적이다.
2. **축소판(라운드 수)은 지금 데이터로 가능하고, 필요한 코드도 대부분 이미 있었다**:
   `calibration.py`의 `aggregate_calibration_statistics()`는 이미 `bucket` 필드를 기대하고
   그룹 출력에 포함하도록 짜여 있었다(`bucket_info_missing` 사유 코드까지 존재) — 그런데
   `orchestrator.py`가 calibration.jsonl을 쓸 때 `bucket`을 **한 번도 채운 적이 없었다**.
   즉 "실측 기반 학습" 인프라는 이미 설계돼 있었고, 정작 실행 쪽에서 그 필드를 안 채워서
   죽어 있던 상태였다.

## 구현

- **`bucket` 필드를 항상 채움**(opt-in 아님 — 순수 텍스트 특징 계산, 호출·비용 0):
  `orchestrator.py`의 `run_producer_reviewer`가 매 런마다
  `automation.recommend_effort_rounds({"task": task}, cfg)`로 bucket을 구해 계산 레코드에
  포함시킨다. 이건 그냥 기존에 있어야 했던 필드를 채우는 것이라 안전장치가 필요 없다.
- **`calibration.rounds_by_bucket()`/`rounds_hint_for()`**(신규, 순수 함수): (bucket, pattern)별
  실측 rounds의 중앙값·평균·성공률을 집계한다. 표본이 `min_samples`(기본 5) 미만이면
  `available: False`로 명시(값을 지어내지 않음) — `calibrated_benchmark_scores`와 같은
  fail-closed 관례.
- **로그로만 노출, 실행에는 반영 안 함**(opt-in, `automation.show_rounds_calibration_hint`
  기본 False): 켜면 매 런 시작 시 `[calib-hint] bucket=... pattern=... 과거 N건 — 중앙값
  라운드=X, 성공률=Y%`를 로그로만 남긴다. **`max_rounds`를 자동으로 바꾸지 않는다** —
  V-5§4.1과 같은 원칙: 가치가 검증되기 전에는 관측만 하고 실행에 반영하지 않는다.

## 왜 로그만이고 자동 적용은 안 하는가

지금 24건 표본은 전부 producer-reviewer·비슷한 시기·비슷한 난이도군이라 다양성이 낮다.
`max_rounds`를 실측 힌트로 **자동** 조정하게 만들면, "지금까지 쉬운 작업만 있었으니 라운드를
줄이자"는 식으로 표본 편향을 그대로 강화할 위험이 있다(V-1 계획서가 지적한 위험 2와 같은
종류). 관측만으로 시작해 실제로 유용한 신호인지(T-6처럼 데이터 쌓이면 검토) 확인한 뒤 실행
반영 여부를 별도로 결정한다.

## 원래 제안(에이전트 종류·수 자동 결정)의 재검토 조건

`solo` 패턴(또는 다른 패턴) 실행 기록이 실제로 쌓여야 한다 — 지금은 pattern 선택을 학습할
근거 자체가 없다. 데이터가 쌓이면 이 계획서를 확장해 `rounds_by_bucket`과 같은 방식으로
`pattern`별 success_rate/cost를 비교하는 함수를 추가하는 것이 자연스러운 다음 단계.
