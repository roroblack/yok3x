## 0. 우리는 어떤 프로그램인가 (이 문서의 축)

**yok3x는 프로듀서-리뷰어 멀티에이전트 오케스트레이터다.** 기본 패턴이 그것이고
([orchestrator.py:2537](../../yok3x/orchestrator.py:2537) — `spec.get("pattern", "producer-reviewer")`),
한 에이전트가 만들고 다른 에이전트가 채점(`SCORE: n`)하고 기준 미달이면 다시 돌린다. 거기에
쿼터 가드가 어느 계정·모델로 보낼지 정하고 소진되면 폴오버한다.

이 정체성이 이 문서의 모든 결정을 지배한다. **사용자가 요구한 것들은 서로 다른 기능 3개가
아니라, 같은 루프에서 참가자와 입자 크기만 바꾼 것이다**:

| 사용자가 원한 것 | 실제로는 |
|---|---|
| 채팅 | 작은 task 하나 = 1 run. producer가 답하고 reviewer가 검수한 답을 받는다 |
| 런 중 피드백 | **사람이 reviewer 자리에 앉는 것.** `_gate`는 이미 리뷰 지점이다 |
| 코딩 에이전트 | 같은 루프에 도구 켠 워커 |
| 실행 그래프 UI | 그 루프가 지금 어디까지 왔는지 보여주는 창 |

★**채팅을 "백엔드 하나와의 다중턴 대화"로 만들면 안 된다.** 그건 yok3x를 claude CLI의 얇은
프록시로 만드는 것이고, 그러면 Claude Code보다 나은 점이 하나도 없다(오히려 한 겹 더 씌운
만큼 느리다). **검수를 통과한 답을 준다는 것**이 대체할 유일한 이유다.

## 4. 핵심 설계 — 런 도중 추가 요청을 어떻게 처리하는가

사용자 지적: *"이미 런이 돌고 있으니까 기다려라는 말이 안 되잖아."* 맞다. 그래서
**"기다려" 대신 "선택지와 비용을 보여준다."** 사람은 대기하는 게 아니라 **판단**한다.

요청의 성격마다 처리가 다르고, 그걸 가르는 것이 라우터다:

| 런 도중 사용자가 하는 말 | 처리 | 기반 |
|---|---|---|
| "아니 그거 말고 이렇게" — 현재 작업 수정 | 실행 중 워커를 죽이고 지시를 덧붙여 그 스텝 재실행 | `abort_event` (있음) |
| "그리고 X도 해줘" — 범위 추가 | 안 죽임. 다음 스텝 프롬프트에 주입하거나 **워커를 하나 더 붙임** | S1 피드백 주입 + fanout |
| "이거 왜 이렇게 했어?" — 질문 | 런을 안 건드리고 **다른 워커가 옆에서** 답함 | 멀티런 필요(S11) |
| "아 딴 거 하자" — 무관한 새 작업 | 새 run으로 분기, 계보만 기록 | S5의 `DERIVED_FROM` |

**비용 제시가 필수다.** 지금 죽이면 그 스텝에 이미 쓴 토큰·시간이 날아간다. 예시:

```
지금 중단하고 다시 하면:  약 3분 · $0.4 손실
다음 단계에 반영하면:     약 2분 뒤 반영, 손실 없음
새 작업으로 분리하면:     현재 런 영향 없음
```

WSO 문서의 Conversation Router를 초기에 "과대 범위"로 기각했으나, **여기서 구체적인 할 일이
생긴다** — 이 4갈래 분류가 그 라우터의 실제 직무다.

## 5. 근거를 모아 루프를 닫는다 (NeoHorse-1 적용)

논문([arXiv 2609.08183](https://arxiv.org/abs/2609.08183), 초록만 읽음 — 본문 PDF 미독,
11개 벤치 이름·라우팅 정책 학습 방법·명시된 한계는 확보 못 함)의 구조는 4단계다:

1. 턴마다 `(예측된 능력 수요 · 선택된 서비스 티어 · 이후 상호작용)`을 한 레코드로 기록
2. 그걸 그대로 안 쓰고 **걸러냄** (구조 검증 → 6차원 의미 평가 → subscene 라벨링)
3. 걸러낸 것으로 **다음 배치를 정함** (evaluation → selection → update 루프)
4. 갱신 대상 = **모델 가중치** (3단계 SFT 커리큘럼 + on-policy distillation)

**yok3x는 1~3을 가져오고 4만 바꿔 끼운다 — `가중치` → `라우팅·역할 배치 정책`.**

정직하게: **1과 3의 뼈대는 원래 yok3x 설계였다**(triage 예측 → calibration 기록 → 집계).
논문이 준 것은 새 방법이 아니라 **빠뜨린 두 개를 짚어준 것**이다 — (2) 걸러내기가 없다,
(3) 집계하고 표시만 하지 루프를 닫지 않는다.

**가중치 학습은 안 가져온다.** yok3x는 CLI를 shell-out할 뿐 가중치 접근이 없다.
*안 해본 것*: V-7(로컬 MoE를 offline degrade 백엔드로)이 실현되면 그 로컬 백엔드는 가중치
접근이 되므로, **로컬 백엔드에 한정해서는** 가능하다. "원천 불가"가 아니라 "현 구성 불가,
V-7 조건부 가능"이다.

★**과적합 위험 — 반드시 지킬 것**: 논문은 루프를 모델 학습으로 닫아 느리고 표본이 크다.
우리는 라우팅 정책으로 닫으니 훨씬 빠르고, 그만큼 **표본이 적을 때 잡음에 과적합**한다.
지금 2줄·7건 같은 표본으로 정책을 바꾸면 근거 없이 바꾸는 것과 같다. yok3x에 이미 있는
방어선(`min_samples: 5`, 리뷰 관측 백엔드당 20건)을 **넘기 전에는 계속 표시만 한다.**

## 6. 두 축은 서로 물려 있다 (착수 순서의 근거)

왜 자동화가 꺼져 있었나 — 겁이 나서가 아니라 **근거 없이 자동 적용하면 위험해서** 일부러
관측 단계에서 멈춰둔 것이다. 그러면 켜는 조건은 "근거 축적"이고, 근거의 가장 좋은 원천은
**사람이 실제로 무엇을 고쳤는가** = 런 중 개입이다.

```
런 중 개입(신규) → 사람 판정이 기록으로 쌓임 → 이미 있는 집계가 처음으로
의미 있는 표본을 가짐 → 걸러내기 → automation_mode를 근거 갖고 켬
```

개입 없이 자동화만 켜면 근거 없이 켜는 것이고, 개입만 만들고 자동화를 안 켜면 사람이 매번
같은 말을 반복해야 한다. **둘 다 해야 의미가 있고, 순서는 개입이 먼저다.**

- 분류 결과와 **비용 추정을 함께 제시**하고 사람이 고른다. 자동 실행하지 않는다
- "현재 작업 수정" 갈래는 `abort_event`+`_terminate_active_processes` 재사용

#### S11. 멀티런 스케줄러 · YOK-115 — **신규** (코어)

### D축. 표면 — 상시 쓰는 물건이 된다

#### S7. 채팅 모드 — **1턴 = 1런** · YOK-109 (개정됨)

★이전 판의 "백엔드 하나와 다중턴 대화"는 **폐기**. 0절 참조 — 그건 프록시일 뿐이다.

  미달이면 다시 돌고, 사람은 **통과한 답**을 받는다
- 가벼운 질문까지 2단계를 태우면 느리고 비싸다 → triage(S13)가 "이건 1인 답변으로 충분"을
  판정하게 한다. **이것이 S13 자동화의 첫 실사용처다**
- 세션 연속성: `claude --resume <id>` / `codex exec resume` 활용. **첫 작업은 실측** —
  `--help`에 플래그가 있다는 것만으로 된다고 가정하지 않고 실제 왕복 2턴을 돌려 확인
- 방식 2안(프로세스 유지 vs 매 턴 `--resume`)은 **A·B·A·B 교대로** 자원·지연 측정 후 선택
- 쿼터: 채팅은 호출 빈도가 런보다 훨씬 높다. `usage.py` 가드·페이싱이 채팅 호출도 세는지
  확인하고 안 세면 포함시킨다
- GUI는 S3의 체크포인트 패널을 승격 — 새 화면을 따로 만들지 않는다
