# v4.8.0 · 계획서 — 구조화 Agent 통신 프로토콜: reviewer checklist 스키마화 · 2026-08-13

상태: **S1~S5 구현 완료** (2026-08-19)

**배경**: yok3x의 producer-reviewer 루프는 reviewer에게 산출물을 검수하게 하지만, 리뷰어의 체크리스트/결함 지적은 아직 순수 자유 텍스트다. `yok3x/orchestrator.py`의 `_defect_sig()`가 줄 단위로 SCORE 줄을 제외하고 글머리표·번호를 제거한 뒤 공백/대소문자/구두점을 정규화해 `issues_sig`를 만들며, 이 값이 `_new_evidence()`와 `run_producer_reviewer()`의 재시도·수렴 판정에 들어간다. 이는 의미를 보존하는 통신 스키마가 아니라 휴리스틱 파싱이다.

**목표**: reviewer가 최소한의 파싱 가능한 결함 구조를 반환하도록 프롬프트와 파서를 점진적으로 도입해, 라운드 간 동일 결함 판정의 신뢰도를 높인다. 기존 `SCORE` 파싱, 기존 자유 텍스트 리뷰어, 재개/리플레이 데이터와의 호환은 유지한다. 이 계획서는 구현 전에 작성하는 설계 문서이며, 이번 단계에서는 실제 코드나 테스트 파일을 변경하지 않는다.

## 1. 현재 구조와 문제 진단

### 1.1 현재 신호의 분리

| 경로 | 현재 역할 | 한계 |
|---|---|---|
| `_checklist(self, res)` (약 697행) | 실행 실패, 빈 응답, 20k 초과, 거부성 응답, 근거 없는 확신 표현 등 응답 자체의 메타 품질 기록 | reviewer가 산출물에서 지적한 결함은 수집하지 않음 |
| `_defect_sig(text)` (약 718행) | SCORE로 시작하는 줄을 제외하고 각 줄을 결함으로 간주한 뒤 정규화 | 자유 텍스트의 문장 경계와 의미를 모르는 줄 단위 휴리스틱 |
| `SCORE_RE` 및 `call_worker()` | `re.compile(r"SCORE:\\s*(\\d+(?:\\.\\d+)?)")`로 응답 어디서든 첫 SCORE 값을 추출 | SCORE와 결함 구조가 서로 검증되거나 연결되지 않음 |
| `run_producer_reviewer()` (약 1578행) | reviewer 결과의 score, verify 상태, `issues_sig`를 이용해 게이트·재시도·에스컬레이션을 진행 | 결함 신호 품질이 낮으면 실제 진전/정체 판정도 흔들림 |
| `_new_evidence()` (약 745행) | `artifact_sig`, `verify_ok`, `issues_sig` 중 하나라도 바뀌면 새 증거로 인정 | `issues_sig`가 의미 기반이 아니라 텍스트 모양 기반 |

### 1.2 자유 텍스트가 깨지는 구체적 시나리오

- 리뷰어가 `널 체크 누락`을 `입력값이 None일 때 예외 가능성`처럼 조금 다르게 쓰면 같은 결함이 다른 문자열로 인식되어, 실제로는 진전이 없는데 새 증거로 오판할 수 있다. 반대로 문장을 거의 복사하면 다른 위치의 결함도 같은 결함으로 뭉개질 수 있다.
- `인증 토큰이 로그에 남을 수 있음. 실패 시 재현하려면 debug 로깅을 켜야 함.`처럼 하나의 결함과 재현 조건이 여러 문장에 걸치면 두 줄의 독립 결함으로 쪼개져 중복·우선순위 판정이 왜곡된다.
- `검토 결과`, `다음 라운드에서 확인하자`, 인용문, 마크다운 제목 같은 무관한 줄이 4자 이상이면 결함으로 들어간다. 그러면 단순한 리뷰어 문체 변화만으로 `issues_sig`가 바뀐다.
- 한 줄 안에 여러 결함을 세미콜론으로 나열하면 하나의 결함으로 합쳐지고, 반대로 한 결함을 번호 목록과 보충 문단으로 반복하면 여러 결함으로 중복된다.
- 심각도, 근거 파일, 재현 절차가 텍스트에 섞여 있어도 파서는 이를 구분하지 못한다. 따라서 “치명적이지만 설명이 짧은 결함”과 “장황한 저위험 설명”을 안정적으로 비교할 수 없다.
- `SCORE`가 첫 줄이라는 지침을 따르지 않아도 현재 정규식은 응답 어딘가의 SCORE를 찾지만, JSON/코드 블록 속 SCORE나 인용된 이전 리뷰의 SCORE까지 후보가 될 수 있어 점수와 결함 목록의 소유권이 모호하다.

BUG-03에서 드러난 것처럼 메타 체크리스트만으로는 정상적인 reviewer 응답이 `()`로 축약되어 실제 결함 반복을 놓칠 수 있다. 기존 `_defect_sig()` 개선은 순서·번호 차이를 흡수했지만, 자유 텍스트라는 근본 전제는 남아 있다.

## 2. 제안하는 reviewer 통신 프로토콜

### 2.1 표준 형식

reviewer 프롬프트에 다음 최소 JSON 객체를 요구한다. JSON은 응답 전체 또는 하나의 fenced code block 안에 한 번만 둔다.

```json
{
  "protocol_version": "review-v1",
  "score": 0,
  "defects": [
    {
      "severity": "critical|high|medium|low",
      "description": "산출물의 구체적 결함 한 가지",
      "evidence": "파일·심볼·재현 조건(선택)",
      "fix": "수정 방향(선택)"
    }
  ],
  "summary": "통과 또는 남은 위험의 짧은 요약(선택)"
}
```

- `protocol_version`, `defects`, 각 결함의 `severity`와 비어 있지 않은 `description`만 필수로 한다. `evidence`와 `fix`는 모델별 순응도와 토큰 비용을 고려해 선택 필드로 둔다.
- `score`는 0~10 숫자여야 한다. 기존 호환을 위해 프롬프트에는 여전히 `SCORE: <0-10>` 한 줄을 요구하며, JSON 예시 안의 score와 동일하게 쓰도록 한다.
- 결함 하나는 하나의 의미 단위로 작성하고, 설명은 한 줄이어야 한다. 심각도는 `critical`, `high`, `medium`, `low`의 고정 열거값만 허용한다.
- `defects: []`는 결함이 없다는 유효한 응답이다. `summary`나 설명 문장을 결함으로 추정하지 않는다.
- `ADVERSARIAL_REVIEW`에도 같은 계약을 추가하되, 반례·미검증 가정·보안 결함을 `defects`의 구체적인 항목으로 넣도록 한다.

### 2.2 stdlib 파싱과 안전한 폴백

신규 파서는 `json`만 사용하고 pydantic 등 외부 의존성은 추가하지 않는다.

1. reviewer 원문에서 JSON 객체 후보를 찾는다. 먼저 전체 응답이 객체인지 시도하고, 그 다음 fenced JSON 블록 또는 첫 `{`부터 균형 잡힌 객체 후보를 시도한다. 문자열 안의 중괄호와 이스케이프를 고려해 단순 첫 `{`/마지막 `}` 자르기는 피한다.
2. `json.loads()` 후 객체 타입, `protocol_version`, `defects` 리스트, 결함 객체 타입, 허용 severity, 비어 있지 않은 문자열 description, score 범위/숫자 여부를 검증한다. 알 수 없는 추가 필드는 보존하지 않고 무시한다.
3. 파싱 성공 시 `defects`를 canonical defect record로 만든다. 서명에는 `severity`와 정규화한 `description`을 사용하고, evidence/fix는 반복성의 핵심이 아니므로 기본적으로 서명에서 제외한다. 동일 결함의 경미한 공백·구두점 차이는 기존 정규화 규칙으로 흡수한다.
4. JSON이 없거나, 잘렸거나, 스키마 검증에 실패하거나, 결함 항목이 모호하면 **전체 결과를 실패 처리하고 기존 `_defect_sig()` 자유 텍스트 경로로 폴백**한다. 부분적으로 JSON 결함을 사용해 자유 텍스트와 섞으면 라운드별 서명 규칙이 바뀌어 오히려 스톨 판정이 불안정해지므로 금지한다.
5. 파서 결과에는 내부적으로 `source = "structured" | "legacy_text"`, `defects`, `raw_text`를 구분해 둔다. 기존 `StepLog.checklist`는 메타 체크리스트 의미를 유지하고, 구조화 결함을 그 필드에 몰래 합치지 않는다.

### 2.3 SCORE와 하위호환

- `SCORE_RE`와 현재 `call_worker()`의 추출 경로는 유지한다. 응답에 유효한 레거시 `SCORE:`가 있으면 기존 동작을 그대로 우선한다.
- 레거시 SCORE가 없고 구조화 JSON의 유효한 `score`만 있으면 이를 보조 점수로 사용할지 별도 플래그/로그로 명시한다. 초기 이행에서는 게이트 동작 변경을 최소화하기 위해 “구조화 score만으로 strict 통과시키지 않음”을 기본으로 하고, 캘리브레이션 후 활성화 여부를 결정한다. 즉 형식 미준수 모델이 우연히 JSON score를 넣었다고 기존 게이트 의미가 바뀌지 않게 한다.
- 구조화 응답의 `defects`는 `issues_sig`의 새 입력이 되지만, `_new_evidence()`의 키와 반환 계약은 유지한다. `artifact_sig`와 `verify_ok`가 기존처럼 독립적인 증거 신호로 남아야 한다.
- 구조화 파서 도입 초기에 `issues_sig_source`와 파서 실패 사유를 로그/관측용 메타에 남기되, 기존 status/step JSON을 읽는 재개 로직이 요구하지 않는 새 필드는 선택적으로 읽도록 한다. 과거 step 기록에는 `source`가 없으므로 `legacy_text`로 간주한다.

## 3. 구현 범위와 단계별 계획

### S1. 프로토콜 상수·파서 단위 설계

- `yok3x/orchestrator.py` 내부 또는 의존성 없는 소형 모듈에 protocol version, severity 집합, JSON 추출/검증 함수, canonical defect 정규화 함수를 추가한다.
- 입력은 reviewer 원문 하나이며, 출력은 구조화 성공 여부와 canonical defects를 포함한 내부 dict/tuple로 제한한다. 외부 스키마 라이브러리와 자동 복구형 JSON 패키지는 사용하지 않는다.
- 경계가 불분명한 JSON, 배열/문자열 최상위값, score 범위 오류, 중복/빈 description, 잘린 fenced block을 모두 폴백 대상으로 정의한다.

검증: pytest 단위 테스트로 정상 JSON, `defects: []`, 필드 순서/공백, 잘못된 severity, 누락 필드, 중첩 중괄호가 든 evidence, JSON 앞뒤 설명, malformed/truncated JSON을 검증한다. 성공 경로와 폴백 경로가 각각 결정적으로 같은 입력에 같은 서명을 내는지도 확인한다.

### S2. reviewer 프롬프트를 구조화 계약으로 확장

- 일반 reviewer 지침과 `ADVERSARIAL_REVIEW`에 `review-v1` JSON 계약, 한 결함 한 객체, severity 의미, `defects: []` 규칙, JSON 외 설명은 결함으로 해석하지 않는다는 지침을 추가한다.
- 기존 `SCORE: <0-10>` 요구는 그대로 유지하고, JSON의 score와 일치시킨다. 프롬프트 길이 증가는 실제 backend별 입력 토큰 비용에 포함되므로 예시를 짧게 유지한다.
- producer에게 전달되는 `round_feedback`는 구조화 JSON 전체를 그대로 주입하기보다 사람이 읽을 수 있는 canonical 결함 요약을 우선하고, 호환을 위해 원문도 필요한 범위에서 남긴다. 이 결정은 구현 시 자기오염·토큰 비용 회귀 테스트로 확정한다.

검증: mock `call_worker`로 일반/적대적 reviewer prompt에 protocol version, SCORE 지침, severity/defects 계약이 포함되는지 확인하고, producer revise prompt가 JSON의 summary 잡음이 아니라 실제 defects를 받는지 테스트한다.

### S3. `issues_sig` 연결과 레거시 폴백

- `run_producer_reviewer()`에서 reviewer 원문을 한 번 구조화 파싱한 뒤, 성공하면 canonical defects로 `issues_sig`를 만들고 실패하면 기존 `_defect_sig(rev.text)`를 호출한다.
- `_checklist(res)`는 응답 메타 품질 검사로 유지한다. 구조화 결함을 실행 체크리스트로 합치지 않아 `StepLog.checklist`의 기존 의미와 재개 파일 호환을 보존한다.
- `SCORE_RE` 기반 score, `verify_ok`, `artifact_sig`, `_new_evidence()`의 비교 순서와 `no_new_evidence` stop reason은 변경하지 않는다. 구조화는 issues 신호의 생산 방식만 교체한다.

검증: 기존 자유 텍스트(`SCORE: 6`, 번호/글머리표, 설명 문장) 테스트가 계속 통과하는지 확인하고, 동등한 JSON 결함의 순서 변경은 같은 `issues_sig`, severity/description 변경은 다른 서명을 만드는지 검증한다. `_checklist()`가 여전히 빈 응답·20k·거부성·과신 표현만 메타 이슈로 보고하는 회귀 테스트도 둔다.

### S4. 라운드·스톨·재개 통합 검증

- 동일한 artifact와 verify 상태에서 구조화 결함이 반복되면 `no_new_evidence`로 종료되는지, 결함이 추가/해소되면 `issues_changed`로 재시도되는지 확인한다.
- artifact만 바뀌거나 verify만 바뀌는 경우에도 기존 R-2 규칙대로 재시도되는지 확인한다. 구조화 파서 실패가 이 두 신호를 덮어쓰지 않아야 한다.
- JSON reviewer와 레거시 reviewer가 섞인 라운드, reviewer backend가 claude/codex/gemini로 바뀌는 escalation, 중단 후 resume/replay에서 과거 step에 source 필드가 없는 경우를 검증한다.
- 기존 SCORE만 있는 리뷰 응답은 score gate와 calibration 기록이 이전과 동일해야 한다. 구조화 defects는 calibration의 기존 `issues` 개수/필드 의미를 깨지 않는 범위에서만 추가 관측한다.

검증: pytest mock backend 시나리오로 (1) JSON 동일 결함 반복 조기 종료, (2) JSON 결함 변화 재시도, (3) malformed JSON→레거시 폴백, (4) JSON/레거시 혼합 라운드, (5) resume/replay, (6) SCORE-only 회귀를 실행한다. 전체 pytest도 실행해 기존 producer-reviewer·calibration·resume 테스트를 통과시킨다.

### S5. 관측·점진적 기본값 전환

- 초기에는 구조화 파싱을 관측 모드로 두어 `structured`/`legacy_text` 비율, parse failure 사유, backend별 결함 수/스톨 결과를 기록한다. 원문 전체를 새 로그에 중복 저장하지 않고 기존 보안·토큰 정책을 따른다.
- 최소 표본이 쌓인 뒤 backend별 파싱 성공률과 false stall/false progress 사례를 검토한다. 충분히 안정적인 경우에만 구조화 서명을 기본으로 하고, 여전히 파싱 실패 시 레거시 폴백을 유지한다.
- 구조화 score를 게이트의 독립 입력으로 승격하는 것은 별도 결정으로 남긴다. score를 JSON으로 중복 기록하는 것만으로 기존 strict gate의 의미를 바꾸지 않는다.

검증: fixture/실측 샘플을 backend별로 재생해 성공률, 동일 결함의 안정성, 자유 텍스트 대비 스톨 판정 차이를 표로 비교한다. 표본 부족을 안정성으로 오인하지 않도록 “판정 불가” 상태를 허용한다.

## 4. 하위호환 계약

| 기존 계약 | 이행 후 보존 규칙 |
|---|---|
| `SCORE_RE.search(res.text)`로 응답 어디서든 SCORE 추출 | 정규식과 레거시 SCORE 우선순위 유지; 구조화 score는 보조 경로로만 검토 |
| `StepLog.checklist`는 `_checklist()`의 메타 품질 목록 | 구조화 defects를 checklist에 섞지 않음 |
| `_defect_sig()`의 자유 텍스트 정규화 | JSON 검증 실패 시 동일 함수/동일 의미로 폴백 |
| `_new_evidence(prev, cur)`의 `artifact_sig`·`verify_ok`·`issues_sig` 계약 | 키와 반환값 유지; issues_sig의 생산원만 단계적으로 변경 |
| 기존 step JSON과 resume/replay | 새 메타가 없어도 legacy로 읽고 재생 가능 |
| `calibration.jsonl`의 score/verify 라벨 | 기존 필드와 SCORE 기반 통계 불변; 새 파서 메타는 선택적 부가 정보 |

## 5. 리스크와 트레이드오프

- **모델별 순응도 차이**: claude/codex/gemini 또는 같은 계열의 모델·설정마다 JSON 준수율이 다르다. 강제 전환은 형식 미준수 시 결함 신호를 통째로 잃을 수 있으므로 실패 즉시 기존 휴리스틱으로 폴백한다.
- **프롬프트 비용**: 스키마 설명과 예시가 입력 토큰을 늘리고, 긴 JSON 출력은 비용·지연을 늘린다. 필수 필드를 최소화하고 evidence/fix를 선택 필드로 둔다.
- **거짓된 구조화 신뢰**: JSON 파싱 성공은 결함의 진실성을 보장하지 않는다. 구조화는 의미 비교의 안정화일 뿐이며 verify_cmd와 artifact_sig를 대체하지 않는다.
- **스키마 경직성**: severity 열거를 너무 빨리 늘리면 모델별 변형(`"warning"`, 대문자 등)이 실패율을 높인다. 초기에는 고정 소수 집합과 명확한 폴백을 사용하고, 실제 샘플을 보고 별도 버전업한다.
- **중복 score 불일치**: `SCORE: 7`과 JSON `score: 9`가 동시에 나오면 게이트가 흔들릴 수 있다. 초기에는 레거시 SCORE를 authoritative로 기록하고 불일치를 관측 이벤트로 남기며, 자동 보정하지 않는다.
- **중첩 JSON/마크다운**: reviewer가 설명·코드 예시 속 JSON을 함께 출력할 수 있다. 객체 추출은 균형 문자열과 스키마 검증을 모두 통과해야 하며, 애매하면 안전하게 자유 텍스트 폴백한다.
- **새 서명과 기존 서명의 단절**: 같은 결함이 이행 전후에 다른 `issues_sig`가 될 수 있다. source를 구분해 관측하고, 이행 중에는 JSON/레거시를 같은 canonical 정규화 규칙에 태워 불필요한 라운드 변화가 생기지 않게 한다.
- **민감 정보 보존**: evidence에 경로·토큰·로그 조각이 들어갈 수 있다. 원문을 추가 저장하지 않고 기존 출력/로그 클리핑 및 민감정보 정책을 그대로 적용한다.

## 6. 결정 필요

1. 표준 JSON을 전체 응답으로 강제할지, 설명 허용 + fenced JSON을 기본으로 할지 — 권장안은 후자이며 폴백 판정이 단순하다.
2. 구조화 `score`를 SCORE_RE 대체 입력으로 승격할 시점 — backend별 성공률·불일치율·캘리브레이션 표본을 본 뒤 별도 결정.
3. canonical defect 서명에 `evidence`를 포함할지 — 권장안은 제외하고 description/severity만 포함해 위치·재현 문구 변화로 인한 false progress를 줄이는 것.
4. 관측 메타를 step JSON에 추가할지 calibration에 추가할지 — 기존 소비자와 resume 호환을 우선해 선택적 필드로 결정.
