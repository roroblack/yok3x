# 계획 · 워커 호출 전 verify_cmd 프리플라이트 (YOK-120)

- **작성**: 2026-09-21 · **상태**: 계획 — **기본 결론은 보류, 계측 후 판단** · **이슈**: YOK-120
- **계기**: RSIAgent 논문(arXiv 2609.15364) 논의의 적용 후보 ②. 논문 내용은 초록·요약 본문만 봤다.

## 제안된 아이디어

워커(프로듀서)를 부르기 **전에** `verify_cmd` 를 한 번 돌려 시작 상태를 잰다.

- 이미 통과하는 상태면 작업이 필요 없거나 `verify_cmd` 가 아무것도 검증하지 않는다는 신호.
- 시작부터 실패하면(환경 문제·기존 실패) 워커 호출 비용을 쓰기 전에 알 수 있다.
- 시작 실패 목록을 기록해 두면, 이후 라운드의 실패가 "새로 생긴 것"인지 "원래 있던 것"인지 가를 수 있다.

## 현재 코드 사실

[yok3x/orchestrator.py](../../yok3x/orchestrator.py) 에서 검증 실행 지점은 셋이다: `_run_verify`(594행),
`_run_round_verify`(707행), 라운드 루프 호출부(1845행 근방)와 파이프라인 사후 검증(1698행).
**워커 호출 전에 verify 를 돌리는 곳은 이 파일에서 찾지 못했다**(검색 범위: `orchestrator.py` 만 —
다른 모듈에서 하는 사전 점검은 확인하지 않았다).

`_run_verify` 는 `subprocess.run(shell=True, timeout=verify_timeout)` 이고 결과를 `StepLog` 로 남긴다.
`_verify_cmd_escapes_stage`(F2-11)는 절대경로 인자로 스테이징 밖을 검증하는 라벨 위조를 막는다.

## 근거가 얇은 이유 — 솔직한 평가

이 후보는 세 후보 중 **근거가 가장 약하다.**

1. **필요를 보인 사례가 없다.** "시작 상태를 몰라서 손해를 본 런"을 기록에서 찾지 못했다
   (찾은 범위: 이 세션에서 본 BUG 리포트·T-1 결과 문서. 전 이력을 훑지는 않았다).
2. **비용이 실재한다.** 프리플라이트마다 `verify_cmd` 를 한 번 더 돈다. 이 프로젝트의 `verify_cmd`
   는 전체 시험일 수 있어 느리다. 게다가 스테이징 복사(`_run_round_verify`)까지 하면 더 든다.
3. **이미 있는 방어와 겹친다.** 라운드 1의 verify 실패가 어차피 다음 라운드 프롬프트로 되먹임된다
   (`orchestrator.py:1928` `[직전 검증 실패]`). 프리플라이트가 더하는 것은 "워커 호출 **전에** 안다"뿐이다.
4. **새 실패 모드를 만든다.** 시작 상태가 이미 실패인 저장소는 흔하다(고치라고 시키는 작업). 이걸
   "중단 사유"로 삼으면 정상 작업을 막는다. 그래서 정보로만 써야 하는데 그러면 가치가 더 줄어든다.

## 최소안 (하려면 이것만)

**관측 전용, 기본 off, 동작 변경 없음.**

- `automation.verify_preflight` (기본 False). 켜면 라운드 1 전에 `_run_verify` 를 한 번 돌리고
  결과(통과 여부·종료 코드·소요 시간)를 `StepLog(kind="preflight")` 와 캘리브레이션 기록에만 남긴다.
- **결과로 중단·분기·프롬프트 변경을 하지 않는다.** 이 원칙은 V-5§4.1·V-8 파일럿과 같다
  (가치를 검증하기 전에는 실행에 반영 안 함).
- 스테이징 복사는 하지 않는다 — 시작 상태이므로 원본 workdir 에서 돈다.

## 가치 검증 기준 (이게 안 나오면 접는다)

관측이 N 런 쌓인 뒤 다음을 센다:

| 질문 | 볼 것 |
|---|---|
| 시작부터 통과하는 런이 있는가 | 있으면 `verify_cmd` 가 작업을 변별 못 하는 사례 — 값어치 있음 |
| 시작 실패였는데 최종 통과한 런의 비율 | 분모 = 프리플라이트가 켜진 전체 런 |
| 프리플라이트 소요 시간이 런 전체에서 차지하는 비율 | 크면 비용 대비 가치 없음 |

**N 은 미정.** 어느 작업폴더에서 몇 런이 나올지 모른다. 표본이 작으면 「구분되지 않는다」로 기록한다.

## 시험 (구현 시)

- 기본 off 일 때 기존 동작·호출 횟수가 **정확히 같다**(회귀).
- on 일 때 프리플라이트 1회만 돌고, 실패해도 워커 호출은 그대로 진행된다.
- `verify_cmd` 가 없으면 아무것도 안 한다.

## 이 계획이 확인하지 않은 것

- 논문의 "검증 에이전트"가 시작 상태를 재는지 여부(전문 미열람).
- 다른 모듈의 사전 점검 유무(위 검색 범위 참고).
- 시작 상태 관측이 실제로 결정을 바꿀 사례.
