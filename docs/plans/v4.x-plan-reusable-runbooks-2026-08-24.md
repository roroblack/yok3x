## 2026-09-08 후속 — 참고 논문 3편(구현 아님, 다음 확장 시 참고용)

사용자가 공유한 논문 3편을 조사해 이 계획서와의 접점을 확인했다. **코드·설정 변경은
없음** — 기존 설계 결정을 뒷받침하는 근거와, 다음에 §4의 미결 사항(특히 "축소판 이후
전면판")을 다룰 때 참고할 구체적 메커니즘만 추가한다.

1. **[Repo-To-Skill / DisCo](https://huggingface.co/papers/2609.02749)** — GitHub 저장소를
   "범위결정→근거수집→구성→**검증**"의 4단계로 검증된 스킬(SKILL.md)로 증류하는 기법.
   **접점**: "재사용하려는 지식은 실행으로 검증해야 신뢰할 수 있다"는 원칙이 §2.1의
   기존 제약(verify 통과 + 게이트 통과 라운드만 저장)과 정확히 같은 방향 — 이 계획서가
   이미 옳은 방향을 잡았다는 독립적 확인. 스킬 형식이 Claude Code Agent Skills(SKILL.md)와
   같은 사양이라는 점도 확인했지만, yok3x producer/reviewer 워커는
   `backends.json`에서 `--disallowedTools`로 도구 호출 자체를 차단해두고 있어(텍스트
   생산자=안전 원칙, §2.3 참고) 스킬을 **동적으로 로드해 실행**하는 방식은 적용 안 된다.
   `context_globs`로 SKILL.md **본문을 텍스트로만** 주입하는 우회는 가능하지만, 이건 이
   계획서의 §2.3(짧은 힌트 텍스트 주입)과 본질적으로 같은 메커니즘이라 새로운 구현 여지는
   크지 않다.

2. **[DART-SD](https://arxiv.org/abs/2608.18524)** — "다이아몬드 토폴로지": 순서독립적
   하위목표가 있는 작업엔 원래 유효한 해결 경로가 여러 개(조합론적 격자)인데, 이를 단일
   궤적으로 강제 학습시키면 "토폴로지 붕괴"가 일어난다는 지적. **접점**: 2026-08-30
   후속에서 codex가 지적한 "런북이 producer의 탐색 다양성을 줄이고 같은 편향을
   반복시킬 위험"에 **정식 이름과 이론적 근거**를 붙여준다 — 우리가 겪을 뻔한 문제가
   독립 연구에서도 확인된 실제 현상이라는 뜻. 다만 DART-SD의 해법(self-distillation,
   즉 파인튜닝)은 yok3x가 모델 가중치를 건드리지 않는다는 전제와 정면으로 안 맞아 그대로
   가져올 수 없다 — **얻을 건 "왜 다양성이 중요한지"라는 근거뿐**, "어떻게 고칠지"는
   아니다. §2.1의 "고정 태그 집합"·"참고일 뿐 지시 아님" 설계가 이미 이 위험을 완화하는
   방향이라는 점도 재확인.

3. **[Bilevel Coordinated Reflection / SRMA](https://arxiv.org/abs/2609.02750)** — 텍스트만
   읽는 self-gate로는 reflection의 지속적 개선을 보장할 수 없다는 정보이론적 불가능성
   증명 + 실제 환경/verifier로 평가해 **위험(Risk)이 실제로 줄어들 때만** 기존 기억(M)을
   새 기억(M')으로 갱신하는 SRMA 메커니즘. SWE-bench 500건에서 grounded 검증 없는
   reflection(58.4%)이 reflection 자체를 안 한 baseline(70.8%)보다 **더 나빴다**는 실측이
   핵심 근거. **접점 — 이 계획서에 가장 직접적으로 연결됨**:
   - §3의 위험 1("심판 미검증과 겹치는 문제")이 이 논문의 핵심 주장과 정확히 같다 —
     "심판(텍스트 판단)만으로 재사용 여부를 정하면 위험하다"는 게 형식적으로 증명된 것.
     T-1이 mutation-testing으로 그 심판 신뢰도를 검증한 것 자체가, 이 논문 기준으로는
     "grounded 검증"에 해당한다.
   - **지금 구현(2026-08-30)의 저장 조건은 boolean 게이트다**(`verify_ok` + gate 통과
     라운드만 기록) — SRMA는 이보다 한 단계 더 나아가서 "이 신규 접근(M')을 저장하면
     기존 힌트(M) 대비 실제로 위험이 줄어드는가"를 **비교**한다. §4의 "전면판" 미결
     사항을 다룰 때, 지금의 단순 boolean 저장 대신 **risk-comparison 방식**(신규 태그
     조합을 채택한 이후 라운드의 실측 rounds/score/재작업률이 그 태그 없이 나온 것보다
     실제로 나은지 비교 — §5의 "재사용된 런북이 후속 라운드를 유의미하게 개선하는지
     측정" 항목과 사실상 같은 방향, SRMA는 이걸 저장 시점의 게이트 조건 자체로
     만들라는 제안)을 검토 후보로 추가한다.
   - **re-anchoring**(환경이 바뀌면 기존 기억을 다시 평가) 개념도 참고할 만하다 — 지금
     knot의 시간 가중치(`recency_halflife_days`)는 "그냥 오래되면 약해지는" 수동적
     감쇠인데, re-anchoring은 "yok3x 코드/설정이 바뀌면 그 변경과 관련된 기존 런북 항목을
     능동적으로 재검증"하는 방식이라 다르다. 런북이 전면판으로 갈 경우 이 능동적
     재평가 방식이 §3의 위험 3("단조 증가/정체성 오염")에 대한 더 나은 대응일 수 있다.

**결론**: 세 논문 모두 "지금 이대로 진행해도 되는가"보다는 "이미 신중하게 짜둔 설계가
독립적으로도 타당했는가"에 대한 답이다 — 셋 다 그렇다고 확인해준다. 새로 바꿀 건
없지만, §4의 "전면판" 논의를 다시 열 때 SRMA의 risk-comparison 방식을 boolean 게이트의
대체 후보로 우선 검토할 것을 권고한다. TeamFlow: YOK-100.

## 2. 제안하는 설계(초안 — 확정 아님)

### 2.1 무엇을 저장할 것인가 — 반드시 지켜야 할 제약

이번 세션에서 이미 두 번 확립한 원칙을 그대로 따른다:

- v4.8.0 S5(`review_protocol.log_observation`)는 리뷰 관측을 남기되 **원문 텍스트·결함 설명을 절대
  저장하지 않는다**(source/parse_error 같은 메타데이터만).
- v4.9.0 S3(`calibration.py:read_calibration_jsonl`)의 `FIELDS`는 집계 가능한 필드만 남기고
  "임의/미지 필드는 절대 반환하지 않는다"(작업/프롬프트 텍스트 유출 방지)는 주석이 이미 있다.

런북도 같은 원칙: **원문 프롬프트·산출물 코드·프로젝트 고유 정보는 절대 저장하지 않는다.**
저장 대상은 "무엇을 했는지"의 **구조화된 요약**뿐이어야 한다 — 예를 들면:

```json
{
  "bucket": "medium",
  "pattern": "producer-reviewer",
  "approach_tags": ["tdd-first", "incremental-refactor", "add-defensive-check"],
  "outcome": {"verify_ok": true, "score": 8.5, "rounds": 2},
  "run_id": "...", "ts": "..."
}
```

`approach_tags`는 자유 텍스트 요약이 아니라 **사전에 고정된 유한 태그 집합**에서만 골라야 한다
(자유 텍스트를 허용하면 결국 원문 유출 통로가 될 위험 — CLIP 교훈과 같은 종류의 실수).
태그 집합을 어떻게 뽑을지(producer 응답에서 자동 분류? reviewer가 태깅?)는 미결정 — §4 참고.

### 2.2 어디에 저장할 것인가

`calibration.jsonl`의 스키마를 건드리지 않고(v4.9.0 S3에서 이미 "기존 스키마를 안 건드린다"는
결정을 두 번 반복함 — review_protocol도 같은 이유로 별도 파일을 씀), **별도 append-only 파일**
`.yok3x/runbooks.jsonl` 신설을 제안한다.

### 2.3 어떻게 주입할 것인가

`build_automation_decision_snapshot()`(v4.9.0 S5)이 이미 "off 모드는 계산 자체를 안 한다"는
zero-overhead 원칙을 세워뒀다 — 런북 조회도 같은 원칙: `automation_mode != off`이고 별도
opt-in(`automation.use_runbooks` 같은 새 플래그, 기본 false)일 때만 조회한다. 조회 결과는
producer 프롬프트에 "참고: 비슷한 과거 작업에서 효과가 있었던 접근 — {approach_tags}" 정도의
짧은 힌트로만 주입하고, **지시가 아니라 참고로만 취급**한다(v4.4.0 계획서의 few-shot 예시가
"명령이 아니라 형식 참고"로 취급되는 것과 같은 패턴 — `orchestrator.py`의 examples 처리 참고).

## 3. 위험 — 왜 신중해야 하는가

1. **T-1 미검증과 겹치는 문제**: 지금 "성공한 라운드"의 판정 기준은 `verify_ok` + 심판(codex-critic)
   SCORE 게이트 통과다. 그런데 T-1(`docs/TODO.md`)이 아직 "심판이 SCORE를 신뢰할 만큼 잘 매기는지"를
   검증 못 한 상태다(N0′: 심판이 명백한 결함을 원본보다 낮게 평가, 캘리브레이션 데이터 부족으로
   착수 조건 미충족). **심판이 부정확하면, 실제로는 안 좋은 접근인데 우연히 통과한 라운드의
   태그가 "효과적인 접근"으로 잘못 학습되어 반복 주입될 위험**이 있다 — v5.0.0 계획서가 이미
   지적한 위험 A("심판 미검증")·E("단조 증가 편향")와 정확히 같은 종류.
2. **표본 편향/과적합**: bucket별 표본이 적은 초기에는 우연히 한두 번 통과한 접근이 과대표현될 수
   있다. v4.9.0 automation.py의 S3 통계도 같은 이유로 최소 표본 임계값(`_MIN_CALIBRATION_SAMPLE`)을
   쓴다 — 런북도 최소 표본 미만이면 "insufficient_data"로 주입을 보류해야 한다(이미 있는 패턴 재사용).
3. **단조 증가/정체성 오염**: v5.0.0 계획서의 위험 E(나이틀리는 구조적으로 "추가만" 함)와 유사 —
   런북이 계속 쌓이기만 하면 오래된/저품질 태그가 안 걸러지고 누적될 수 있다. TTL이나 재평가
   주기가 필요할 수 있음(미결정).
4. **선행조건**: 이 기능이 실제로 유의미하려면 **실 producer-reviewer 런이 다수 쌓여야** 한다 —
   지금 `calibration.jsonl`은 6줄뿐이고 `review_protocol_observations.jsonl`은 아예 없다(T-2가
   여전히 실 쿼터 승인 대기 중). **런북은 T-2/T-1보다 먼저 만들 이유가 없다** — 데이터가 없으면
   "재사용할 성공 사례" 자체가 없다.

## 4. 결정이 필요한 것(구현 착수 전 사용자가 정해야 함)

- `approach_tags`를 누가/어떻게 매기는가 — producer 자기보고(신뢰도 낮음, self-report bias)?
  reviewer가 채점 겸 태깅(리뷰어 부담 증가)? 별도 분류 단계(비용 증가)?
- 태그 집합을 사전에 몇 개나, 어떤 기준으로 고정할 것인가.
- 최소 표본 임계값·TTL을 T-1의 "충분한 데이터" 기준표와 같은 형식으로 사전 고정할 것인가.
- 이 기능 전체를 T-1 완료 이후로 미룰 것인가, 아니면 "심판 신뢰 여부와 무관하게 verify_ok만
  기준으로 쓰는" 축소판(예: score 무시, verify_ok=true인 라운드만 태그 후보로 인정)으로 먼저
  시작할 것인가 — 이러면 위험 1을 상당 부분 피할 수 있다(verify_ok는 심판이 아니라 실제 테스트
  결과이므로 신뢰도가 다름). **이 축소판이 현실적인 타협안일 수 있음.**

## 5. 권고

**지금 구현 착수는 권하지 않는다.** 선행조건(§3.4) 미충족 — 재사용할 실 데이터가 없다. 대신:

1. T-2(실 캘리브레이션 수집)를 사용자 승인 시 재개해 `calibration.jsonl`/
   `review_protocol_observations.jsonl`에 데이터가 쌓이게 한다.
2. 데이터가 쌓이면 §4의 "verify_ok만 기준으로 쓰는 축소판"부터 작은 스코프로 시작해서, 실제로
   재사용된 런북이 후속 라운드의 rounds/score를 유의미하게 개선하는지(A/B 유사 비교) 측정한 뒤
   범위를 넓힐지 결정한다 — v4.8.0 S5의 T-6("파싱 성공률 검토 — 데이터 대기 중")과 같은 패턴.

링크해 둔다.
