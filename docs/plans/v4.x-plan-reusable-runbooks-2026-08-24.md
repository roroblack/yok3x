## 2026-08-30 후속 — 착수 조건 재검토 및 제한적 구현

**T-1 재검토**: 원래 §3.1의 위험("심판 미검증 상태에서 재사용하면 나쁜 패턴이 강화될 위험")은
T-1의 mutation-testing 파일럿(대상 2개·mutant 4개, 4/4 정확 탐지)으로 완화됐다. 단, codex와의
직접 토론에서 통계적으로 정확한 반박을 받았다 — **4/4 성공만으로는 실제 탐지율의 95% 신뢰
하한이 약 50%에 불과**(4연속 성공은 rule-of-three류 추정으로 강한 신뢰를 못 준다). 따라서
"T-1이 완전히 해결됐다"가 아니라 "**제한적 전진을 정당화할 만큼은 됐다**"는 절충 결론을 채택.

**codex가 추가로 지적한, 원래 계획서에 없던 위험**: 런북이 producer의 탐색 다양성을 줄이고
같은 편향을 반복시킬 수 있으며, 그 결과가 다시 런북에 들어가면 피드백 루프가 생길 수 있다.
이를 막기 위해 아래 구현은 (a) 실패·반려된 라운드는 애초에 기록하지 않고 (b) 힌트는 "참고,
지시 아님"으로만 제시하며 (c) 재사용 횟수가 늘어도 힌트 문구의 확신도를 자동으로 올리지 않는다.

**구현 범위(의도적으로 축소)**: §2.1의 "approach_tags는 사전 고정 유한 집합만" 원칙을 그대로
따르되, 태그 부여 방식은 §4의 미결 사항 중 "producer 자기보고"(신뢰도 가장 낮지만 비용 0)를
채택 — codex도 "지금은 이 정도로 시작하고 운영 중 검증하라"고 동의. 리뷰어에게 힌트 존재를
숨기는 조건은 기존 아키텍처가 이미 만족한다(critic 프롬프트는 산출물+rubric만 받고 producer
프롬프트를 보지 않음 — 별도 조치 불필요, 이번에 코드로 재확인).

**전면 활성화 기준(codex 권고, 사전 고정)**: 주요 작업 유형 4개 이상·총 15~20개 작업,

다양성도 함께 관찰. 이 기준 미충족 상태에서는 opt-in 제한적 파일럿으로만 존재한다(기본 off).

## 1. StateM 논문 요지와 우리 프로젝트의 대응 관계

StateM의 5개 구성요소와 yok3x 현황:

| StateM 구성요소 | yok3x 현재 | 격차 |
|---|---|---|
| 지속 상태(persistent state) | `.yok3x/runs/<run_id>/status.json`, step 파일 | 런 하나 안에서만 — 있음 |
| 절차 제어(procedural control) | `yok3x_technique`의 `require_plan`/`require_selfcheck`(프롬프트 수준 지시) | 있음, 하지만 매 런 처음부터 다시 지시할 뿐 과거 성공 사례를 참고 안 함 |
| 단계별 컨텍스트 | producer→reviewer round_feedback, pipeline stage 간 컨텍스트 전달 | 런 내부만 — 있음 |
| 검증된 전환(verified transition) | `_new_evidence`/score·verify gate | 부분 구현 — 있음(단, T-1 미검증 이슈 아래 참고) |
| **재사용 가능한 "런북"** | **없음** | **이 계획서의 대상** |

**핵심 격차**: `call_key` 기반 resume/replay(`orchestrator.py:_load_replay_steps`, `_resume_supported`)는
**같은 run_id 안에서만** 이전 스텝을 재생한다(`worker\|task_kind\|backend\|model\|prompt\|read_only`
해시가 일치해야 캐시 히트). 즉 "이전에 비슷한 작업을 어떻게 접근했는지"가 **다른 작업, 다른 런에는
전혀 전달되지 않는다** — 매번 처음부터 시작한다.

## 2. 제안하는 설계(초안 — 확정 아님)

### 2.1 무엇을 저장할 것인가 — 반드시 지켜야 할 제약

이번 세션에서 이미 두 번 확립한 원칙을 그대로 따른다:

- v4.8.0 S5(`review_protocol.log_observation`)는 리뷰 관측을 남기되 **원문 텍스트·결함 설명을 절대
  저장하지 않는다**(source/parse_error 같은 메타데이터만).
- v4.9.0 S3(`calibration.py:read_calibration_jsonl`)의 `FIELDS`는 집계 가능한 필드만 남기고
  "임의/미지 필드는 절대 반환하지 않는다"(작업/프롬프트 텍스트 유출 방지)는 주석이 이미 있다.

런북도 같은 원칙: **원문 프롬프트·산출물 코드·프로젝트 고유 정보는 절대 저장하지 않는다.**
저장 대상은 "무엇을 했는지"의 **구조화된 요약**뿐이어야 한다 — 예를 들면:

```json
{
  "bucket": "medium",
  "pattern": "producer-reviewer",
  "approach_tags": ["tdd-first", "incremental-refactor", "add-defensive-check"],
  "outcome": {"verify_ok": true, "score": 8.5, "rounds": 2},
  "run_id": "...", "ts": "..."
}
```

`approach_tags`는 자유 텍스트 요약이 아니라 **사전에 고정된 유한 태그 집합**에서만 골라야 한다
(자유 텍스트를 허용하면 결국 원문 유출 통로가 될 위험 — CLIP 교훈과 같은 종류의 실수).
태그 집합을 어떻게 뽑을지(producer 응답에서 자동 분류? reviewer가 태깅?)는 미결정 — §4 참고.

### 2.2 어디에 저장할 것인가

`calibration.jsonl`의 스키마를 건드리지 않고(v4.9.0 S3에서 이미 "기존 스키마를 안 건드린다"는
결정을 두 번 반복함 — review_protocol도 같은 이유로 별도 파일을 씀), **별도 append-only 파일**
`.yok3x/runbooks.jsonl` 신설을 제안한다.

### 2.3 어떻게 주입할 것인가

`build_automation_decision_snapshot()`(v4.9.0 S5)이 이미 "off 모드는 계산 자체를 안 한다"는
zero-overhead 원칙을 세워뒀다 — 런북 조회도 같은 원칙: `automation_mode != off`이고 별도
opt-in(`automation.use_runbooks` 같은 새 플래그, 기본 false)일 때만 조회한다. 조회 결과는
producer 프롬프트에 "참고: 비슷한 과거 작업에서 효과가 있었던 접근 — {approach_tags}" 정도의
짧은 힌트로만 주입하고, **지시가 아니라 참고로만 취급**한다(v4.4.0 계획서의 few-shot 예시가
"명령이 아니라 형식 참고"로 취급되는 것과 같은 패턴 — `orchestrator.py`의 examples 처리 참고).

## 3. 위험 — 왜 신중해야 하는가

1. **T-1 미검증과 겹치는 문제**: 지금 "성공한 라운드"의 판정 기준은 `verify_ok` + 심판(codex-critic)
   SCORE 게이트 통과다. 그런데 T-1(`docs/TODO.md`)이 아직 "심판이 SCORE를 신뢰할 만큼 잘 매기는지"를
   검증 못 한 상태다(N0′: 심판이 명백한 결함을 원본보다 낮게 평가, 캘리브레이션 데이터 부족으로
   착수 조건 미충족). **심판이 부정확하면, 실제로는 안 좋은 접근인데 우연히 통과한 라운드의
   태그가 "효과적인 접근"으로 잘못 학습되어 반복 주입될 위험**이 있다 — v5.0.0 계획서가 이미
   지적한 위험 A("심판 미검증")·E("단조 증가 편향")와 정확히 같은 종류.
2. **표본 편향/과적합**: bucket별 표본이 적은 초기에는 우연히 한두 번 통과한 접근이 과대표현될 수
   있다. v4.9.0 automation.py의 S3 통계도 같은 이유로 최소 표본 임계값(`_MIN_CALIBRATION_SAMPLE`)을
   쓴다 — 런북도 최소 표본 미만이면 "insufficient_data"로 주입을 보류해야 한다(이미 있는 패턴 재사용).
3. **단조 증가/정체성 오염**: v5.0.0 계획서의 위험 E(나이틀리는 구조적으로 "추가만" 함)와 유사 —
   런북이 계속 쌓이기만 하면 오래된/저품질 태그가 안 걸러지고 누적될 수 있다. TTL이나 재평가
   주기가 필요할 수 있음(미결정).
4. **선행조건**: 이 기능이 실제로 유의미하려면 **실 producer-reviewer 런이 다수 쌓여야** 한다 —
   지금 `calibration.jsonl`은 6줄뿐이고 `review_protocol_observations.jsonl`은 아예 없다(T-2가
   여전히 실 쿼터 승인 대기 중). **런북은 T-2/T-1보다 먼저 만들 이유가 없다** — 데이터가 없으면
   "재사용할 성공 사례" 자체가 없다.

## 4. 결정이 필요한 것(구현 착수 전 사용자가 정해야 함)

- `approach_tags`를 누가/어떻게 매기는가 — producer 자기보고(신뢰도 낮음, self-report bias)?
  reviewer가 채점 겸 태깅(리뷰어 부담 증가)? 별도 분류 단계(비용 증가)?
- 태그 집합을 사전에 몇 개나, 어떤 기준으로 고정할 것인가.
- 최소 표본 임계값·TTL을 T-1의 "충분한 데이터" 기준표와 같은 형식으로 사전 고정할 것인가.
- 이 기능 전체를 T-1 완료 이후로 미룰 것인가, 아니면 "심판 신뢰 여부와 무관하게 verify_ok만
  기준으로 쓰는" 축소판(예: score 무시, verify_ok=true인 라운드만 태그 후보로 인정)으로 먼저
  시작할 것인가 — 이러면 위험 1을 상당 부분 피할 수 있다(verify_ok는 심판이 아니라 실제 테스트
  결과이므로 신뢰도가 다름). **이 축소판이 현실적인 타협안일 수 있음.**

## 5. 권고
