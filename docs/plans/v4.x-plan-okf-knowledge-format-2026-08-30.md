# v4.x · 계획서 — knot(지식그물)에 OKF(Open Knowledge Format) `type` 필드 도입 · 2026-08-30

**구현 완료(2026-08-30)**: `knot.save()`에 `type` 매개변수(기본 `"Note"`) 추가, `cli.py`
`knot save --type` 옵션, orchestrator 자동 노트 2곳에 `Run Stall`/`Run Summary` 부여,
`lint()`에 curated 노트 `type` 누락 검사 추가. 신규 테스트 3개 통과, 전체 스위트
691 passed·1 skipped(기존과 동일, 회귀 없음). 기존 23개 노트·링크 문법·기존 호출부 전부
불변.

## 배경

사용자 질문("오픈위키나 OKF 같은 거 도입 안해도 됨?")에 웹 리서치(2026-08-30 기준)로 확인:
"오픈위키"는 Andrej Karpathy가 제안한 **LLM Wiki** 개념(원문서를 매번 검색하는 대신, 에이전트가
계속 읽고 갱신하는 큐레이션된 지식 베이스), **OKF(Open Knowledge Format)**는 그 개념을
구체화한 결과물 — Google Cloud가 2026-06-12 공개한 오픈 표준(현재 v0.2, 2026-08-12 기준,
[스펙](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)).
벡터DB·임베딩 없이 **마크다운 + YAML frontmatter + 명시적 링크**만으로 지식을 구조화하며,
git으로 버전관리한다.

## 우리와의 접점 — 이미 80% 하고 있었음(코드로 확인)

`yok3x/knot.py`의 docstring이 정확히 "평문 마크다운으로 에이전트끼리 기억을 공유한다"다.
현재 frontmatter(`id/title/tags/source/created`)와 OKF 스키마를 대조:

| OKF 필드 | 상태 |
|---|---|
| `type`(유일한 **필수** 필드) | **없음** |
| `title` | 있음(그대로 대응) |
| `tags` | 있음(그대로 대응) |
| `generated: {by, at}`(권장) | `source`+`created`로 거의 대응(구조만 다름) |
| `verified`/`status`/`stale_after`(전부 선택) | 없음(선택 필드라 없어도 준수 가능) |

**실측 확인**: 현재 `knowledge/*.md` 23개 중 `[[위키링크]]` 문법을 실제로 쓴 곳 **0건** —
OKF의 경로 기반 링크(`[text](/path.md)`)로 나중에 바꿔도 깨질 게 없다(지금은 문법 자체를
안 바꾼다 — 아래 범위 참고).

## 범위 — 이번엔 Phase 1만(공식 마이그레이션 가이드 기준 가장 낮은 노력)

OKF 공식 가이드: "1단계(`type` 추가)만 해도 v0.2 준수"(선택 필드 부재는 허용). 이 계획서는
**Phase 1만** 한다 — `generated:` 구조 변경·`verified`/`status`·링크 문법 전환은 전부 범위 밖
(위험·노력 대비 지금 당장의 이득이 불분명, 필요해지면 별도 계획).

### 변경 사항

1. **`knot.save()`에 `type` 매개변수 추가**(기본값 `"Note"` — 안 넣어도 기존 호출부 안 깨짐).
   frontmatter에 `type: <값>` 한 줄 추가.
2. **호출부 3곳에 의미 있는 type 부여**:
   - `cli.py`의 `knot save` 명령: `--type` 옵션 추가(기본 `"Note"`).
   - `orchestrator.py:1942`(stall 노트): `type="Run Stall"`.
   - `orchestrator.py:2340`(run 요약 노트): `type="Run Summary"`.
3. **`lint()`에 `type` 필드 누락 검사 추가** — 기존 `id/title/created` 검사와 같은 자리,
   같은 대상(curated 노트만, `source=orchestrator` 자동 이력 노트는 제외 — 기존 원칙 유지).
   **관측만, 강제 안 함**(이 프로젝트의 다른 opt-in 기능들과 같은 원칙) — lint는 원래도
   경고만 내고 아무것도 막지 않는다.
4. **기존 23개 노트는 그대로 둔다**(OKF가 점진적 채택을 명시적으로 허용) — `lint`가 `type`
   누락을 알려주면, 원할 때 사용자가 직접 채우거나 나중에 별도 일괄 스크립트로 보완 가능
   (이 계획서 범위 밖).

### 왜 링크 문법(`[[위키링크]]` → `[text](/path.md)`)은 안 바꾸는가

실사용이 0건이라 지금 바꿔도 깨질 건 없지만, `knot.py`의 링크 파싱(`LINK_RE`)·lint의 깨진
링크 검사·`query()`의 관련 노트 탐색 로직이 전부 title 기반이라, 경로 기반으로 바꾸려면
이 세 곳을 다시 설계해야 한다 — `type` 필드 추가보다 훨씬 큰 변경이고, 지금 당장 얻는
이득(다른 OKF 도구와의 링크 상호운용성)이 그 비용을 정당화할 만큼 크지 않다. 나중에 실제로
다른 OKF 인식 도구와 knot 폴더를 공유할 일이 생기면 그때 다시 본다.

## 테스트 계획

- `type` 미지정 시 기본값 `"Note"`로 저장되는지(기존 호출부 회귀 없음).
- `type` 지정 시 frontmatter에 정확히 반영되는지.
- `lint()`가 curated 노트의 `type` 누락을 잡아내고, orchestrator 노트는 여전히 제외하는지
  (기존 `id/title/created` 검사와 같은 패턴 재사용).
- orchestrator의 두 자동 저장 호출이 각각 `Run Stall`/`Run Summary` type으로 저장되는지.

## 결정 필요 — 없음

Phase 1은 opt-in도 아니고(항상 `type` 필드를 붙이되 값이 없으면 안전한 기본값), 기존 동작을
전혀 안 바꾼다(기존 23개 노트 그대로, 링크 문법 그대로, `lint`는 원래도 비강제). 구현
승인만 필요.
