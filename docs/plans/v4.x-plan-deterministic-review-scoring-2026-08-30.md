# v4.x · 계획서 — 구조화 결함 목록 기반 결정론적 SCORE 계산 · 2026-08-30

**옵션 A 구현 완료(2026-08-30)**: `review_protocol.compute_deterministic_score()`,
`config.py`의 `review_protocol` 블록(기본 off), `orchestrator.py` 라운드 루프 배선.
단위 테스트 9개(`tests/test_review_protocol.py`) + 통합 테스트 3개(`tests/test_yok3x.py` —
기본 off 회귀 불변·on일 때 override·legacy_text 폴백) 전부 통과. 전체 스위트 660개 중
2개 실패는 `test_parallel.py`의 기존 타이밍 민감 테스트(단독 실행 시 통과 — 이번 변경과
무관, 회귀 아님). 옵션 B(조건부 블라인드 재리뷰)는 아래 "보류 항목" 그대로 미착수.

## 배경

[`docs/reports/v4.x-result-t1-pilot-spec-test-separation-2026-08-30.md`](../reports/v4.x-result-t1-pilot-spec-test-separation-2026-08-30.md)에서
발견: 완전히 동일한 코드를 codex-critic에 4회 독립 재심사시켰더니 SCORE가 5.0~9.0까지
나왔다(stdev 1.6). 원인 진단(웹 리서치 + codex와의 설계 토론 + 기존 데이터 재검증, 위 보고서
참고)의 결론:

1. 지금 프롬프트는 SCORE를 리뷰어(LLM)가 **직접, 자유형으로** 정하게 한다(`SCORE_RE`가
   `res.text`의 첫 줄 "SCORE: X"를 그대로 파싱 — [`orchestrator.py:1254-1259`](../../yok3x/orchestrator.py)).
2. `review_protocol.py`가 이미 구조화 JSON(`{"score":..., "defects":[{"severity":...}]}`)을
   파싱하지만(T-6), **관측·재시도 판정용으로만 쓰이고 실제 게이트 SCORE 계산에는 전혀
   반영되지 않는다** — `parsed_review["score"]`는 지금 코드 어디서도 읽히지 않는다.
3. 실측 검증: 결함 목록에 `critical -5/high -2/medium -0.5/low -0.1` + severity cap 공식을
   적용해 "결정론적 재계산 점수"를 냈더니, **결함 탐지 자체가 안정적인 사례(#9)는 분산이
   확실히 줄었지만(stdev 0.22→0.04), 결함 탐지 자체가 불안정한 사례(#12 round-1, #8)는
   개선되지 않았다**(입력인 결함 목록 자체가 매번 다르므로 계산 방식을 고쳐도 소용없음).

## 이 계획서의 범위

두 가지 대응책 중 **결정론적 SCORE 계산(A)만 지금 구현**한다. **조건부 블라인드 재리뷰(B)**는
round-loop 재시도 로직·비용 추정에 직접 손대는 더 큰 변경이라 별도 계획서로 미룬다(아래
"보류 항목" 참고) — V-5가 §4.1(관측)과 §4.2(실제 전환)를 분리했던 것과 같은 이유다.

## 설계 (A) — 결정론적 SCORE 계산

### 동작

- `review_protocol.py`에 `compute_deterministic_score(defects, *, weights=None, caps=None) -> float`
  추가: severity별 고정 감점 합산 → 0 이상으로 클램프 → 최고 severity에 따른 상한(cap) 적용 →
  0.5 단위로 반올림. 순수 함수, 외부 상태 없음(기존 `canonical_defect_signature`와 같은 스타일).
- 기본 가중치·cap은 이번 실측에서 쓴 값을 그대로 기본값으로 둔다(`critical -5/high -2/
  medium -0.5/low -0.1`, cap `critical→4/high→7/medium→9`) — 이 숫자 자체는 임의이므로
  `cfg.yok3x["review_protocol"]`에서 재정의 가능하게 한다.
- `orchestrator.py`의 라운드 루프에서 `parsed_review = review_protocol.parse_review_response(rev.text)`
  직후, **opt-in 설정이 켜져 있고 `parsed_review["source"] == "structured"`일 때만**
  `score`를 `SCORE_RE` 결과 대신 `compute_deterministic_score(parsed_review["defects"])`로
  덮어쓴다. 구조화 파싱이 실패하면(`legacy_text`) 기존 `SCORE_RE` 값을 그대로 쓴다
  (fail-closed가 아니라 **fail-safe-to-existing-behavior** — 이 기능이 꺼져 있던 것처럼
  동작). `score` 결과는 로그(`[review] round N score=...`)에도 그대로 흐르므로 어느 쪽
  계산인지는 `.yok3x/runs/*/status.json`의 기존 필드로 재구성 가능.
- **기본값은 off**(`review_protocol.deterministic_scoring: False`). 켜는 순간부터 게이트
  통과/반려가 실제로 달라질 수 있는 변경이라, a1(MCP)·degrade·daily_pace와 같은 급의
  안전 취급(opt-in, 명시 설정 필요)을 한다.

### 왜 프롬프트(리뷰어에게 SCORE를 아예 요구하지 않기)는 안 바꾸는가

codex와의 토론에서 "점수를 먼저 쓰게 하는 순서 자체가 원인일 수 있다"는 가설이 나왔지만,
직접 검증된 근거([Chen et al.](https://aair-lab.github.io/aia2024/papers/chen_aia24.pdf))는
"순서가 평균 점수엔 영향을 준다"였지 "분산을 항상 줄인다"가 아니었다(모델마다 다름).
검증 안 된 프롬프트 변경을 안전장치 코드와 같이 밀어넣지 않는다 — 지금은 리뷰어가 여전히
SCORE를 자유형으로 내게 두고(하위호환), **그 값을 게이트에 쓸지 말지만** 설정으로 분리한다.
나중에 순서 변경을 검증하고 싶으면 이 기능과 독립적으로 A/B할 수 있다.

## 보류 항목 (B) — 조건부 블라인드 재리뷰 (설계만, 구현 안 함)

결함 탐지 자체가 불안정한 고위험 사례(critical/high 결함 존재, 게이트 임계값 근처)에서는
(A)만으로 부족함을 실측으로 확인했다(위 배경 참고). codex가 제안한 조건부 재리뷰(트리거
시에만 2·3차, 점수 평균이 아니라 결함 단위 블라인드 재현 확인)는 round-loop의 재시도
판정(`_new_evidence`, R-2)·비용 추정과 얽혀 있어 별도 계획서·검증이 필요하다. 이 계획서는
그 필요성만 기록하고 착수하지 않는다.

## 테스트 계획

- `tests/test_review_protocol.py`: `compute_deterministic_score` 단위 테스트 — severity별
  감점·cap·빈 결함 목록(=10.0)·0.5 단위 반올림·커스텀 weights/caps override.
- `tests/test_yok3x.py`(또는 orchestrator 전용 스위트): `deterministic_scoring=True`일 때
  구조화 응답의 SCORE가 free-text SCORE를 무시하고 결정론적 값으로 게이트에 쓰이는지,
  `deterministic_scoring=False`(기본)일 때 기존 동작이 **완전히 불변**인지(회귀 방지 —
  가장 중요), `legacy_text` 폴백 시 옵션이 켜져 있어도 기존 `SCORE_RE` 값을 그대로 쓰는지.

## 결정 필요 — 없음(옵션 A는 기본 off, 사용자가 켜기 전까진 기존 동작 100% 불변)

구현 승인만 필요. 실제로 사용하려면(효과를 보려면) `yok3x.json`에서 명시적으로
`review_protocol.deterministic_scoring: true`를 켜야 한다.
