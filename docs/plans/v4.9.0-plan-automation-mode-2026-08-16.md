# v4.9.0 계획 — 옵션 자동화 모드(Opt-in Task Automation) — 2026-08-16

상태: S1~S9 구현 완료 (2026-08-19)

**배경**: yok3x는 flavor·profile·routing·workers·daily_pace·guard 비율과 task spec의 producer/reviewer/max_rounds/pass_score/effort/backend/model을 조합해 실행한다. 현재 이 조합의 상당 부분을 사용자가 GUI 설정 탭이나 `yok3x.json`/task JSON에서 반복 입력해야 한다. 사용자가 원하는 것은 작업의 성격·남은 쿼터·과거 성과를 근거로 실행 강도와 작업량을 자동 조정하는 **옵션 자동화 모드**다. 본 계획은 구현 전 설계 문서이며, 이 단계에서는 실제 `.py`/GUI 코드를 변경하지 않는다.

**목표**: 기본 동작을 보존하면서 `off | assist | full` 단계형 opt-in을 추가하고, 사람이 명시한 값은 항상 자동 추론보다 우선하도록 한다. 자동 선택은 설명 가능하고 되돌릴 수 있어야 하며, 근거가 부족하면 조용히 강행하지 않고 추천/경고 또는 안전한 기본값으로 남긴다.

## 1. 현재 상태와 문제 진단

### 1.1 이미 자동화되어 있는 것

| 영역 | 현재 동작 | 자동화 모드가 새로 해야 하는 일과의 경계 |
|---|---|---|
| 상황별 모델 라우팅 | `orchestrator.py:resolve_model()`이 `active_profile`의 상황별 모델을 고르고, `available(backend)`가 설치 여부와 한도 여유를 필터링한다. 후보가 불가하면 해당 상황의 benchmark 점수 내림차순으로 폴백한다. | “어떤 backend/model이 가능한가”는 이미 처리한다. 작업별 effort·라운드·작업량 예산을 정하는 기능은 아니다. |
| 리뷰 에스컬레이션 | `Orchestrator.escalate`와 `run_producer_reviewer()`가 `after_round`, `if_score_below` 조건을 만족하면 producer/reviewer를 한 번 교체하고, adversarial이면 교차 패밀리를 보장한다. | 실행 중 낮은 점수에 대한 조건부 교체다. 시작 전에 작업 크기·초기 effort를 정하거나 quota에 맞춰 전체 작업량을 축소하지 않는다. |
| backend failover/degrade | guard가 한도 초과 때 다른 backend 또는 lite 모델로 전환할 수 있다(각 기능은 별도 opt-in, 역할 제외와 런당 상한 존재). | 호출 시점의 생존성/비용 보호다. 품질 목표와 예상 작업량을 사전 배분하는 정책은 아니다. |
| daily pace | `daily_pace_status()`와 `_daily_cap_v2()`가 underuse/overuse policy로 오늘의 cap·soft·stop·forward_daily를 계산한다. `pause`는 sticky stop이며 CLI `pace approve`로 당일 해제할 수 있다. | 현재는 쓸지/멈출지를 결정한다. max_rounds 축소, effort 하향, backend별 작업 예산 배분은 새 기능이다. |
| triage | task spec을 보고 pattern/tier/max_rounds/skip_review를 계산해 `[triage] 추천`으로 로그에 남긴다. 현재 실행에 자동 적용하지 않는다. | assist는 이 추천을 사용자에게 보여주고, full은 명시적 override가 없을 때 제한적으로 적용하는 후보 기반이 된다. |

### 1.2 사용자가 반복해서 수동 개입하는 지점

1. 전역 설정: `flavor`, `active_profile`, worker별 `backend`/`model`/`effort`, routing과 profiles/benchmarks를 `yok3x.json` 또는 GUI에서 맞춘다. GUI 설정 탭에는 flavor, 기본 worker 배치, workspace, 모델 profile, failover/offline 토글, guard soft/hard 비율, Claude token refresh, daily pace on/off·cap·mode·underuse/overuse policy가 노출된다.
2. 작업 폼: GUI가 producer, reviewer, `max_rounds`(초기값 3), `pass_score`(8.0), `score_gate_mode`, 반복 횟수, workdir, `verify_cmd`, examples, materialize/overwrite를 매번 채운다. 특히 max_rounds와 effort는 작업 난이도에 따른 자동 산정이 없다.
3. task JSON: producer/reviewer, pattern별 stages/workers/join_worker, `max_rounds`, `pass_score`, `escalate`, worker의 `backend`/`model`/`effort`, `verify_cmd`, workdir, context/rubric/examples, acquire와 QA 수를 사람이 결정한다.
4. 모델 조합 실험: profile을 `best|balanced|cost|speed`로 바꾸거나 routing·benchmarks를 손으로 조정하고, 어떤 조합이 이 작업 유형에서 좋은지 별도 비교해야 한다.
5. quota 대응: daily pace가 경고/정지를 표시해도 사용자가 라운드·effort·backend를 다시 낮추거나 Codex/local로 재배치해야 한다. quota 부족 시 작업 자체를 작게 만드는 정책은 없다.

### 1.3 기본값/추론으로 이미 줄어든 입력

- `Config.load()`는 `DEFAULT_YOK3X`와 파일을 deep merge한다. `default_effort`는 빈 값, `verify_cmd`는 빈 값이며 task 값이 전역값보다 우선한다.
- pattern 기본값은 `producer-reviewer`, producer는 `claude-main`, reviewer는 `codex-critic`, `max_rounds`는 실행 경로에서 2, `pass_score`는 8.0이다. GUI 폼의 rounds 3은 GUI 표시 기본값이므로 CLI/파일 기본값과 다르다. 이 불일치를 자동화 모드에서 숨기지 말고 명시적으로 정리해야 한다.
- `resolve_model()`은 `task_kind → situations`와 profiles/benchmarks를 이용해 모델을 추론한다. worker에 지정한 값과 profile 라우팅의 우선순위도 실행 경로에서 보존해야 한다.
- `run_task_file()`은 `verify_cmd`, workdir, score gate, `escalate`를 읽고 `triage.estimate_execution()`을 호출하지만 triage 결과는 추천 로그일 뿐이다. 자동화 모드는 이 기존 추론을 대체하지 않고 별도 decision layer로 연결한다.

## 2. 제안하는 자동화 모드

### 2.1 설정과 우선순위

기본값은 off로 둔다. sync_layer의 `off/light/standard/deep`, daily_pace의 policy 단계형 opt-in 관례를 따라 이름은 `off/assist/full`을 권장한다.

```json
{
  "automation_mode": "off",
  "automation": {
    "mode": "off",
    "max_rounds_cap": 4,
    "min_rounds": 1,
    "allow_backend_reallocation": false,
    "allow_effort_adjustment": false,
    "calibration_window": 20,
    "low_confidence_action": "assist"
  }
}
```

실제 스키마는 한 곳만 authoritative하게 정한다. `automation_mode` 단일 문자열을 권장하되, 중첩 옵션은 `automation` 아래에 둔다. task spec에도 `automation_mode` per-task override를 허용한다.

우선순위는 다음과 같다.

1. task spec에 명시된 `producer`, `reviewer`, `backend`, `model`, `effort`, `max_rounds`, `pass_score` 등은 수동 override로서 항상 우선한다.
2. 그 다음 per-task automation mode, 전역 automation mode, 기존 profile/routing/default 순으로 적용한다.
3. `off`에서는 기존 실행과 byte-for-byte에 가까운 결정 경로를 유지한다. `assist`에서는 추천과 예상값만 로그/status/GUI에 보여주며 실행값은 기존값이다. `full`에서만 비어 있는 필드를 자동 적용한다.
4. 자동화가 설정 오류·쿼터 불명·calibration 부족을 만나면 조용한 폴백을 하지 않는다. `automation decision=skipped`와 원인을 기록하고 기존 명시값/기본값으로 계속하거나, hard safety 조건이면 중지한다.

### 2.2 작업 성격 추정과 effort/max_rounds 산정

외부 ML 라이브러리 없이 다음의 결정론적 feature와 규칙으로 시작한다.

| 신호 | 계산 예 | 영향 |
|---|---|---|
| 입력 규모 | task/brief/rubric/examples 글자 수, context_globs 파일 수·추정 글자 수 | 긴 문맥은 effort와 예상 호출량을 올림 |
| 구조 복잡도 | pattern, stages/workers 수, acquire QA 수, verify_cmd·materialize 존재 | pipeline/fanout/검증 포함 작업은 base 복잡도 가산 |
| 변경 위험 | refactor/review/security/역직렬화·동시성·마이그레이션 등 명시 tag/키워드 | reviewer 필요성·pass_score·최소 effort를 올림 |
| 과거 결과 | calibration.jsonl의 task_kind/pattern/feature bucket별 score·verify_ok·round·effort·backend | 최근 성공 라운드와 실패/재작업률의 단순 이동평균으로 보정 |

초기 규칙은 작고 고정된 bucket(`tiny`, `small`, `medium`, `large`, `risk`)으로 시작한다. 예를 들어 tiny/small은 effort low/medium과 1~2 rounds, medium은 medium과 2~3 rounds, large/risk는 medium/high와 3~4 rounds를 후보로 만들고 `max_rounds_cap`으로 제한한다. `verify_cmd` 실패·최근 gate 불통과가 반복되면 round 후보를 올리되, `pass_score` 자체를 자동으로 낮추지 않는다. score gate와 verify gate의 의미를 훼손하지 않기 위해 pass_score는 명시값이 없을 때에도 mode 정책으로만 제안하고, full 적용 여부는 별도 결정 필드로 기록한다.

calibration 표본이 충분하지 않으면 benchmark/profile 값을 “성과 학습”으로 과장하지 않는다. 최소 표본 수와 confidence를 계산하고, confidence가 낮으면 assist로 내린다. 이동평균은 최근 N건을 사용하되 task 내용·민감한 prompt·토큰을 저장하지 않고 bucket과 식별 가능한 통계만 저장한다.

### 2.3 쿼터 잔량에 따른 작업량 조절

daily pace 상태를 backend별로 읽어 `remaining = max(0, cap - used)`와 level(`ok|warn|stop`), 실제 limit의 신뢰도, reset/forward_daily를 decision input으로 삼는다. `daily_pace`가 꺼져 있거나 측정값이 없으면 quota-aware 조절을 하지 않고 이유를 표시한다.

권장 정책은 다음과 같다.

- `ok`: 작업 성격 기반 후보를 그대로 사용한다.
- `warn` 또는 예상 런 비용이 remaining을 넘을 때: full은 먼저 예상 호출 수를 줄인다(`max_rounds`를 후보 하한까지 clamp), 다음으로 effort를 한 단계 낮춘다. reviewer 품질 게이트와 명시적 high effort는 자동으로 끄지 않고 “예산 초과 예상”을 표시한다.
- backend가 `stop`이거나 remaining이 부족하면 `resolve_model(..., available=usage.backend_available)`의 기존 가용성 폴백을 재사용한다. 후보 중 Codex가 가용하고 정책상 허용되면 Codex 우선 배정하고, cloud가 모두 unavailable이면 기존 failover/degrade/local 정책을 따른다.
- `stop`인 backend를 무시하고 호출하지 않는다. 남은 quota가 0인데 full이 임의로 local로 바꾸는 것은 `allow_backend_reallocation`이 명시적으로 켜진 경우만 허용한다.
- 한 번의 자동 조절로 결정한 호출 상한은 런 동안 sticky하게 유지한다. 라운드 중 quota 변동은 기존 guard가 처리하고, 자동화가 매 라운드 조용히 계획을 바꾸지 않도록 한다. guard hard stop은 항상 우선이다.

이 정책은 “덜 쓰고 성공률이 유지되는가”를 검증해야 한다. 작업을 줄인다는 이유로 verify 또는 최종 reviewer를 생략하지 않으며, `skip_review`는 assist 추천에만 남긴다.

### 2.4 backend/model 조합 실험과 학습

전면적인 온라인 학습이나 매 실행 다중 모델 비교는 비용과 재현성을 해치므로 MVP에서는 하지 않는다. 대신 기존 인프라를 재사용한다.

- `resolve_model()`의 상황별 benchmark 후보와 `available()` 필터를 조합해 후보 순서를 만든다.
- 기존 `_calib_rounds`/`.yok3x/calibration.jsonl` 기록에 자동화 mode, feature bucket, predicted effort/rounds, selected backend/model, quota level, actual calls/tokens, verify_ok, score, gate_pass, stop_reason을 추가한다.
- 같은 bucket에서 최근 N건의 `success_rate`, 평균/중앙 round, 평균 score, 예상 토큰을 backend/model별로 계산한다. 표본이 충분할 때만 benchmark 점수에 작은 보정값을 더하고, 보정값과 원래 benchmark를 모두 기록한다.
- 새 조합을 무작위 탐색하지 않는다. 후보 간 점수 차이가 작고 quota가 허용될 때 assist에서 “다음 실험 후보”만 제시하며, 사용자가 선택했거나 명시적 experiment budget이 있을 때만 실행한다.
- calibration 파일이 손상·부분 기록·서로 다른 schema이면 해당 표본을 제외하고 `calibration_unusable`을 로그에 남긴다. 기존 고정 benchmark와 profile은 유지한다.

### 2.5 관찰 가능성·되돌리기

모든 자동 결정은 run status와 로그에 다음을 남긴다: mode, source(`explicit|default|triage|calibration|quota`), candidate list, selected value, confidence, quota snapshot, predicted calls/tokens, reason, override 여부. `manifest.json`에도 자동화 결정의 hash와 최종 effective spec을 기록해 resume/replay가 같은 계획을 검증하게 한다.

GUI에는 자동화 mode selector, 이번 작업의 “추천값/적용값/사용자 override” 표, quota 영향, confidence와 “자동화를 끄고 원래 값으로 재실행” 동작을 제공한다. assist는 추천만 표시하고, full 적용 전에는 예상 max_rounds·effort·backend를 확인할 수 있어야 한다. CLI에는 `--automation off|assist|full` 또는 동등한 명시 override와 decision 출력 옵션을 둔다.

수동 override는 자동화보다 항상 우선한다. 자동 적용 값은 원본 task spec을 덮어쓰지 않고 effective spec/manifest에만 기록하며, run replay 시 원본 spec과 decision snapshot을 함께 사용한다. 선택 실패, 측정 실패, calibration 부족, schema 오류는 경고/중지 사유로 표시한다(“조용한 실패/조용한 폴백 금지”).

## 3. 데이터·비용·의존성 원칙

- 구현은 stdlib(`json`, `statistics`, `math`, `dataclasses`, `pathlib`, `logging`)만 사용한다. numpy/pandas/scikit-learn 등 외부 ML 의존성은 추가하지 않는다.
- 이동평균/중앙값·고정 bucket·규칙 기반 점수만 MVP 범위다. feature 계산은 bounded input과 finite number 검사를 거친다.
- 자동화 자체는 새 LLM 호출을 만들지 않는다. task 분석은 문자열/구조/기존 triage와 calibration을 이용한 기계적 계산이며, 예상 비용은 기존 `preflight_budget()` 추정과 일관되게 표시한다.
- 민감한 task 원문·prompt를 calibration에 복사하지 않는다. schema/version과 누락 필드를 명시해 미래 버전이 과거 표본을 잘못 학습하지 않게 한다.

## 4. 단계별 구현 계획과 pytest 검증

### S1. 계약·우선순위·effective decision 모델

- `automation_mode`와 `automation`의 기본값/유효값/범위를 정의하고 task override를 검증한다.
- explicit task field > task mode > global mode > 기존 default/profile 순서의 pure decision 함수를 만든다.
- off가 기존 task 실행을 바꾸지 않으며 잘못된 mode는 config error로 명시되는지 고정한다.

검증: 정상/누락/잘못된 mode, 각 explicit field 우선순위, off의 기존 default(`producer`, `reviewer`, `max_rounds`, `pass_score`) 보존을 pytest로 검증한다.

### S2. 작업 feature와 규칙 기반 effort/rounds 추천

- task 문자열·pattern·stages/workers·verify/acquire/risk tag에서 bounded feature와 bucket을 계산한다.
- triage 추천과 충돌할 때 이유를 합성하되, assist에서는 적용하지 않는다.
- effort 단계와 rounds clamp, confidence, recommendation reason을 결정론적으로 반환한다.

검증: tiny/medium/large/risk fixture, 빈 입력·긴 입력·알 수 없는 pattern, verify/acquire 포함 케이스에서 동일 입력의 동일 결과와 cap/min 경계를 검증한다.

### S3. calibration.jsonl 통계 재사용

- 기존 round calibration writer와 호환되는 versioned record를 정의한다.
- 최근 N건 필터, bucket/backend/model별 이동평균·중앙값·성공률·confidence를 stdlib로 계산한다.
- malformed line, schema mismatch, missing score/verify, 파일 없음은 표본 제외와 명시적 reason으로 처리한다.

검증: 표본 부족/충분, 최근 window, 이상치·malformed line, backend별 분리, 동일 결과 재현과 원문 미저장을 pytest로 검증한다.

### S4. quota-aware 작업량 계획

- `daily_pace_status()` snapshot과 `usage.backend_available()`를 읽는 adapter를 추가한다. daily pace off/unknown도 구분한다.
- warn/remaining 부족 시 rounds→effort 순서로 clamp하고, backend stop 시 기존 resolve_model 후보 폴백을 연결한다.
- predicted calls/tokens와 hard guard/reservation의 차이를 명확히 기록한다. guard stop을 우회하지 않는다.

검증: ok/warn/stop, underuse/overuse policy, reset/forward_daily, 측정 실패, quota 부족으로 max_rounds/effort가 줄어드는 케이스, Codex 우선/대안 없음 케이스를 mock으로 검증한다.

### S5. assist 모드와 설명 가능한 출력

- 추천만 계산하고 기존 effective spec은 변경하지 않는 assist 경로를 연결한다.
- run log/status/CLI sink에 decision snapshot을 표시하고 GUI가 읽을 수 있는 안정된 schema를 정의한다.

검증: assist에서 실제 worker 호출 인자와 manifest가 기존값인지, recommendation만 추가되는지, 모든 skip reason이 보이는지 pytest/API fixture로 검증한다.

### S6. full 모드의 안전한 적용·수동 override

- 값이 비어 있는 필드에만 S2~S4 결과를 적용하고 명시 필드는 보존한다.
- effective spec과 원본 spec을 분리하고 resume/replay manifest 비교에 결정 hash를 포함한다.
- 한 런의 계획을 sticky하게 유지하고, auto backend reallocation/effort adjustment는 별도 opt-in으로 제한한다.

검증: explicit override 보호, full 적용, confidence 낮을 때 assist 하향, resume mismatch 거부, replay 동일 결정, 중간 quota 변동의 sticky 계획을 pytest로 검증한다.

### S7. calibration 기반 보정과 제한된 실험 기록

- 충분한 표본에서만 benchmark 순서를 보정하고, 원 benchmark·보정값·선택 근거를 함께 저장한다.
- 자동 탐색은 하지 않고 사용자가 승인한 experiment budget에서만 후보 비교를 기록한다.

검증: 표본 충분/부족, 후보 가용성, benchmark 동률, 선택적 실험, 보정값이 없을 때 기존 resolve_model 결과 보존을 pytest로 검증한다.

### S8. GUI·CLI 표시와 회귀 검증

- 설정 탭에 `off/assist/full`, quota reallocation/effort adjustment opt-in, calibration window를 추가한다.
- 작업 콘솔에 추천/적용/override를 표시하고 원본 task JSON을 자동 overwrite하지 않는다.
- 문서와 CLI help를 갱신한다.

검증: GUI API round-trip, off 기본 표시, assist/full 설정 저장, override 표시, malformed decision payload의 명시적 오류를 관련 pytest와 가능한 정적 JS fixture로 검증한다.

### S9. 통합·운영 안전성 확인

- producer-reviewer/pipeline/fanout 각각에 대해 off/assist/full을 돌리고 기존 guard, failover, escalation, score gate와 상호작용을 점검한다.
- 전체 pytest와 비용 없는 mock backend 테스트를 실행하고, 실제 backend 실험은 별도 승인된 소수 fixture로만 수행한다.

검증: 기존 전체 테스트 통과, 자동화 off 회귀 없음, quota stop 우회 없음, quiet fallback 없음, status/manifest/calibration 간 effective 값 일치 여부를 확인한다.

## 5. 안전장치와 실패 정책 요약

1. 명시적 사용자 값은 항상 우선하며, 자동화가 원본 task/config를 덮어쓰지 않는다.
2. 자동화 mode 기본값은 off다. assist는 실행을 바꾸지 않는다.
3. quota 측정이 없거나 calibration 신뢰도가 낮으면 자동 결정을 강행하지 않고 이유를 표시한다.
4. guard의 hard stop, score/verify gate, escalation 조건은 자동화가 완화하지 않는다.
5. 모든 폴백·축소·backend 교체는 로그, status, GUI에 이유와 이전/이후 값을 남긴다.
6. 자동화된 full run은 decision snapshot과 함께 재현·중단·재실행할 수 있어야 한다.

## 6. 범위 밖

- 실제 강화학습, 온라인 러닝, bandit/무작위 탐색, 외부 ML 라이브러리 도입.
- task 내용의 의미를 별도 LLM 호출로 분류하는 새 planner/agent.
- 사용자의 명시적 `pass_score`, verify gate, reviewer를 자동으로 삭제하거나 낮추는 정책.
- quota를 우회하는 credential 변경, 무제한 자동 failover, 사용자가 승인하지 않은 backend 설치.
- 이번 단계에서의 실제 코드/GUI 변경, 데이터 마이그레이션, 기존 calibration 전체 재작성.

## 7. 결정이 필요한 사항

1. 전역 키를 `automation_mode` 단일 키로 둘지, `automation.mode`를 authoritative로 둘지 구현 S1에서 확정한다(권장: 단일 mode + 중첩 정책).
2. full의 기본 허용 범위는 effort/max_rounds만으로 시작하고 backend 재배정은 별도 opt-in으로 둘지 확정한다(권장: 별도 opt-in).
3. `max_rounds` 자동 축소의 최소값과 reviewer 보존 규칙을 S2/S4 fixture로 확정한다(권장: producer-reviewer에서는 최소 1 producer+1 reviewer).
4. calibration 표본 최소 수와 이동 window를 확정한다(권장: bucket/backend/model별 5건 미만은 assist).

## 8. 완료 기준

- 기본 off에서 기존 실행·라우팅·에스컬레이션·daily pace 동작이 변하지 않는다.
- assist는 추천과 근거를 보여주고 실행값을 바꾸지 않는다.
- full은 explicit override를 보존하면서 effort/max_rounds와 quota-aware 작업량을 결정하고, 필요한 경우에만 명시적으로 허용된 backend 재배정을 한다.
- 자동 결정은 status/log/manifest/calibration에 남고 resume/replay에서 검증된다.
- 외부 의존성 0, 전체 pytest 통과, quiet fallback 및 quota guard 우회가 없다.
