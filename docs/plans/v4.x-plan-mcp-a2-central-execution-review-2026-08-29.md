## 조사 결과 — a1의 실사용 이력 확인

`yok3x/mcp_policy.py`(124줄)가 하는 일: `resolve_mcp_grant()`(opt-in·화이트리스트·fail-closed 판정),
`write_mcp_config_file()`(임시 MCP 설정 파일 생성), `record_grant()`(`.yok3x/mcp_audit.jsonl` 감사 로그).
`orchestrator.py:1199` 부근에 배선돼 있고, 워커가 `mcp_tools`를 설정했을 때만 동작한다.

실사용 여부를 직접 확인한 4가지 근거:

1. **감사 로그 부재**: `record_grant()`가 매 판정마다 남기는 `.yok3x/mcp_audit.jsonl` 파일이 저장소
   어디에도 없다(`find . -iname "mcp_audit.jsonl"` — 0건). a1은 배포 이후 **단 한 번도 실제로 판정을
   수행한 적이 없다**(테스트 목적의 합성 호출 제외).
2. **전역 화이트리스트가 비어 있음**: 저장소 자체 `yok3x.json`의 `mcp_servers`가 `{}`다. `resolve_mcp_grant()`의
   fail-closed 규칙상 화이트리스트가 비어 있으면 어떤 워커가 opt-in을 시도해도 무조건 빈 grant로
   거부된다 — 즉 지금 이 저장소 설정으로는 **opt-in 자체가 구조적으로 불가능**하다.
3. **워커 설정에 opt-in 없음**: `grep -rn "mcp_tools" yok3x/ tests/`로 실제 호출 지점을 확인한 결과,
   운영 코드·설정 어디에도 워커의 `mcp_tools` 필드가 설정된 곳이 없다. 유일한 등장은
   `tests/test_yok3x.py`·`tests/test_misc_modules_hardening.py`의 단위 테스트(합성 데이터)뿐이다.
4. **버그 리포트에 MCP 관련 기록 없음**: `reports/bugs/`에 "mcp" 언급이 전혀 없다 — 실사용 중 발견된
   결함이 없다는 뜻이 아니라, **애초에 실사용 자체가 없었다**는 뜻이다(안정성 신호가 존재하지 않음,
   "안정적이었다"는 신호가 아니라 "관측 표본이 0"이라는 뜻).

커밋 이력(`git log -- yok3x/mcp_policy.py`)도 이를 뒷받침한다 — a1 도입 커밋(`4c28b8f`, 2026-08-08) 이후
이 파일을 건드린 유일한 커밋은 `8759fce`(BUG-50, 여러 모듈에 걸친 일반 입력 하드닝 패스)뿐이며,
MCP 관련 버그를 고친 커밋이 아니다.

## 결론 — **구현 보류 권고 (T-4 착수 조건 미충족)**

T-4의 착수 조건은 "a1이 **실사용으로** 충분히 안정화된 뒤"다. 위 4가지 근거는 a1이 안정화됐는지
여부를 판단할 수 있는 단계 이전, 즉 **a1이 배포 이후 단 한 번도 실제로 사용된 적이 없다**는 것을
보여준다. "실사용 이력이 없다"는 "불안정하다"와도 다르지만 "안정화됐다"의 근거는 더더욱 될 수
없다 — 판단할 표본 자체가 없다.

a2(호출 단위 실시간 검증·감사·중앙 실행기)는 a1보다 구조적으로 훨씬 큰 위험 표면을 갖는다
(yok3x가 MCP 서버와 직접 JSON-RPC로 통신하며 서버 수명주기까지 관리해야 함 — "텍스트 생산자=안전"
설계를 a1보다 한 단계 더 완화하는 변경). 이런 변경을 실사용 데이터 없이 설계하면, a1 도입 당시
codex 리뷰가 지적했던 위험(인자·경로·호스트 검증 부재, 반복호출·프롬프트 인젝션 대응)을 **실제
사용 패턴에 대한 근거 없이 추측만으로 설계**하게 된다 — 이는 V-1이 T-1(판정 보정) 데이터 없이
런북 재사용 설계를 보류한 것과 같은 종류의 위험이다.

## 재검토 조건

다음이 갖춰지면 그때 다시 검토한다:

1. 저장소(또는 실사용 환경)의 `yok3x.json`에 실제 `mcp_servers` 화이트리스트가 하나 이상 등록되고,
2. 최소 하나의 워커가 `mcp_tools`로 실제 opt-in해 **여러 차례 실제 작업에서 사용**되며,
3. `.yok3x/mcp_audit.jsonl`에 그 실사용 이력이 쌓이고 — 특히 화이트리스트 통과 후에도 워커가 도구를
   오용하거나(예산 초과 호출, 예상 밖 경로 접근 시도) 감사 로그만으로는 잡히지 않는 사각지대가
   실제로 관측되는지 확인한다.

이 조건들이 a1의 "실사용 안정화"를 실질적으로 의미하며, 그 시점에 비로소 a2가 실제로 막아야 할
구체적 실패 사례(a1의 감사-only 한계가 실제로 문제가 됐던 사례)를 근거로 설계할 수 있다.
