여러 파일/도구를 건드리다 중간에 실패하면 "부분 실행 후 죽음"이 오염된 상태를 남긴다는 문제의식,

**한 줄 요약**: `_materialize_outputs()`의 개별 파일 쓰기는 이미 원자적이지만(BUG-53),
**여러 파일 전체를 하나의 단위로 묶어 "전부 성공 아니면 원본 root에 아무것도 안 남기는"** 배치
원자성은 아직 없다 — 이번 계획서가 그 잔여 위험을 메운다.

## 1. 우리 프로젝트에서 이미 확인된 접점

- **사용자가 직접 지적**: jira-for-me 프로젝트의 휴지통 purge 소유권 토큰·업로드 롤백 이슈와
  문제의식이 정확히 겹침(교차 프로젝트 패턴).
- **`_materialize_outputs()`의 잔여 위험(BUG-53에서 이미 발견·기록됨)**: `orchestrator.py`의
  `for fb in plan.accepted:` 루프가 파일을 하나씩 `root`에 직접 쓴다. 파일 하나하나는 이제
  원자적(고정 tmp 이름 제거 + hard-link 기반 create-if-absent, symlink root 차단)이지만, **루프
  중간에 실패(디스크 가득 참, 5번째 파일에서 `OSError`, 프로세스 강제종료)하면 앞서 쓴 1~4번
  파일은 `root`에 그대로 남고 5~N번은 없는 반쪽짜리 상태가 된다.** BUG-53 보고서가 이미 이걸
  "잔여 위험 — 큰 staging/rollback 설계가 필요"로 명시적으로 남겨뒀다.
- **T-4(MCP 워커도구 a2, 미착수)**: yok3x가 직접 여러 MCP 도구를 순차 호출하게 되면 같은
  종류의 부분 실패 문제가 생긴다 — a2 설계 시 이 계획서의 패턴을 재사용할 수 있다(단, a2 자체는
  범위 밖).

## 2. 현재 방어선과 정확한 격차

| 위협 | 현재 방어 | 격차 |
|---|---|---|
| 파일 하나의 쓰기 중 크래시(반쪽 파일) | `_atomic_write_bytes`가 임시파일 완성 후 `os.replace`/hard-link로 교체 — **있음(BUG-53)** | 없음 |
| 동시 런끼리 같은 파일 경쟁(TOCTOU 덮어쓰기) | `overwrite=false`는 hard-link create-if-absent로 방지 — **있음(BUG-53)** | 없음 |
| symlink/junction root로 게시 | `_path_has_symlink` 사전 차단 — **있음(BUG-53)** | 없음 |
| **여러 파일 배치 중 일부만 성공** | **없음** | **이 계획서의 대상** |
| 배치 실패 후 재시도 시 이미 쓰인 파일 인지 | 없음(다음 시도가 `existing` 스냅샷으로 다시 계획을 짜지만, 이전 실패의 "이건 반쪽짜리 게시였다"는 표식은 안 남음) | 이 계획서의 대상 |

## 3. 제안하는 설계(초안)

### 3.1 2단계 게시(stage-then-publish)

현재: 생성 검증 → `root`에 바로 하나씩 쓰기(실패 지점부터 앞은 반영, 뒤는 미반영).

제안:
1. **스테이징**: `root`와 같은 파일시스템의 임시 디렉터리(`root.parent / f".materialize-staging-{run_id}"`,
   `tempfile.mkdtemp(dir=root.parent, ...)` 같은 패턴)에 accepted 파일 **전부**를 쓴다. 이 단계에서
   나는 실패는 `root`를 전혀 건드리지 않으므로 안전하다 — 지금 코드의 "성공한 만큼만 반영"이
   "실패하면 root는 원래 그대로"로 바뀐다.
2. **커밋**: 스테이징이 전부 성공하면, 스테이징의 각 파일을 `root`의 목적지로 **하나씩 원자적으로
   이동**한다(같은 파일시스템이면 `os.replace`/hard-link+unlink는 rename 수준이라 매우 빠르고,
   개별 파일 단위로는 여전히 원자적). 이 마지막 이동 단계 자체가 크래시에 100% 안전하진 않지만
   (이동 도중 강제종료되면 일부만 옮겨질 수 있음), **실패 확률이 훨씬 낮은 구간으로 위험을
   압축**한다(콘텐츠 생성·인코딩·디스크 공간 문제는 전부 1단계에서 걸러짐).
3. **매니페스트(선택, 2단계 견고화)**: 커밋 시작 전 `root/.materialize-manifest-<run_id>.json`에
   "이번에 옮길 파일 목록+해시"를 먼저 쓰고, 전부 이동 완료 후 그 매니페스트를 지운다. 다음 실행이
   시작할 때 고아 매니페스트(이전 실행이 중간에 죽어 못 지운 것)를 발견하면 "이전 게시가 반쪽짜리로
   중단됐을 수 있음"을 로그·GUI에 경고로 남긴다(자동 롤백은 하지 않음 — 사용자가 이미 review
   모드에서 수동 수락하는 흐름과 일관되게, 자동 삭제는 위험할 수 있어 **관측만** 하는 쪽을 권한다).

### 3.2 review 모드는 이미 상대적으로 안전함

`materialize`+`changes.mode=review`(현재 기본 경로)는 이미 `changes.json`/`changes.diff` 번들로
격리 스테이징하고 사람이 수락하기 전엔 원본을 안 건드린다 — **review 모드 자체는 이 계획서의
급한 대상이 아니다.** 직접 materialize(review 없이 `materialize.enabled=true`만 켠 경로)가
실제 위험 구간이다.

### 3.3 롤백은 하지 않는다(스코프 결정)

"부분 실패한 배치를 자동으로 되돌린다"(진짜 롤백)까지는 이번 스코프에 안 넣는다 — 이미 사람이
쓰고 있을 수 있는 프로젝트 파일을 yok3x가 자동으로 지우는 건 그 자체로 위험(다른 파일을 실수로
지우는 사고 가능성)이 crash-partial-write보다 클 수 있다. 대신 **"실패하면 아무것도 안 남긴다"
(all-or-nothing) 수준까지만** 목표로 하고, 매니페스트로 "이전 게시가 의심스럽다"는 신호만 남긴다.

## 4. 위험/트레이드오프

- **디스크 사용량 일시 증가**: 스테이징 단계에서 콘텐츠가 임시로 두 배(스테이징+최종) 존재하는
  구간이 생긴다 — `max_files`(기본 20개) 제한이 있어 실사용 규모에서는 무시할 만한 수준으로 예상.
- **스테이징 디렉터리 청소 — 구현 완료(2026-08-29)**: 크래시로 스테이징 디렉터리가 안 지워지고 남을 수 있다 — 기존
  `.pytest-tmp*` 잔류 문제와 같은 종류. `serve()`/CLI 시작 시 오래된(예: 24시간 이상) 고아
  스테이징 디렉터리를 정리한다. CLI 설정 로드 직후 저장소·기본 출력 부모·기존 run별 기본 출력
  부모만 제한적으로 확인하며, 최근 디렉터리와 심볼릭 링크는 건드리지 않는다.
- **복잡도 증가**: 함수 하나가 2단계로 늘어난다 — BUG-53 감사 때 세운 "orchestrator는 특히
  보수적으로"라는 원칙을 그대로 적용해, 기존 테스트(BUG-53의 회귀 테스트 포함) 전부 통과 확인을
  전제로 진행해야 한다.

## 5. 권고

**V-1과 달리 이건 지금 착수해도 되는 스코프다** — 실 producer-reviewer 데이터나 사용자 쿼터 승인이
필요 없고(순수 파일시스템 로직), BUG-53이 이미 "잔여 위험"으로 명시적으로 남겨둔 구멍을 정확히
메운다. 심판 미검증(T-1) 문제와도 무관하다(materialize는 게이트 통과 이후의 순수 쓰기 단계).

**제안하는 다음 단계(승인하시면 바로 진행 가능)**:
1. `_materialize_outputs()`를 §3.1의 stage-then-publish로 변경(매니페스트는 1단계로 넣을지
   선택 — 최소는 stage+commit만으로도 "반쪽 상태" 문제의 대부분을 해결함).
2. 회귀 테스트: 스테이징 중 실패(디스크 가득 참 모사) → `root` 무변화 확인, 커밋 도중 실패 주입
   → 매니페스트로 감지 가능한지(넣는다면) 확인.
3. 기존 BUG-53 회귀 테스트(`tests/test_orchestrator_hardening.py`) 전부 통과 유지.

진행 여부(그리고 매니페스트/고아 스테이징 청소까지 포함할지, 최소 stage+commit만 할지)는
사용자 결정이 필요합니다.
