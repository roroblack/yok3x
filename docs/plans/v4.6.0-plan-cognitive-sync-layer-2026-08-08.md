## 1. 원안과 yok3x 하드 제약의 충돌 (사전 검토, 채택 전 판단)

| 원안 | yok3x 제약 | 충돌 |
|---|---|---|
| LangGraph 기반 분기·순환 구조 | 의존성0(stdlib만) | **직접 충돌** — LangGraph는 pip 패키지 |
| Evidence Collector·Forensic Explainer·Claim Verifier·Quiz Agent·Quiz Evaluator·Integrator 등 변경마다 도는 신규 상시 에이전트 | 페이싱 규율 최우선(R-3 preflight·R-5 세션귀속·daily_pace 등 쿼터 절약 인프라가 이미 두터움) | **직접 충돌** — 변경 1건당 LLM 호출 5~8회 추가 |
| Planner+병렬 다수 Coding Agent+Integrator+Reviewer의 팀/엔터프라이즈급 파이프라인 전제 | 1인 사용자용, producer-reviewer/소수 fanout(3~5 워커) | **전제 불일치** |

**결론**: 원안 전체를 그대로 흡수하지 않는다. 다만 문제의식(사용자가 변경을 이해 못 하면 도구가 실패한다)과
핵심 설계 원칙 셋(주장 단위 근거 연결·구현자와 설명자 분리·위험도 기반 강도 조절)은 유효하며, **v4.4.0
"리서치 흡수" 방식과 같은 필터**(원안 검증 → yok3x 제약에 맞게 재설계 → 선택적 채택)를 그대로 적용한다.

정확히 몇 회의 추가 LLM 호출을 쓰는지 사용자가 미리 알 수 있어야 한다(불투명한 자동판단 금지).

## 3. codex 공동설계 (2026-08-08 실제 상담 결과)

전체 프롬프트·응답은 세션 로그에 보존. 핵심 결론만 정리:

### 3.1 가설 검증 — "무료 데이터 재활용" 전제는 타당하나 조건부

- StepLog·run.log·calibration.jsonl·ACQUIRE·changes.diff 재활용은 **가능**하나, "거의 무료"는
  **설명을 의미적으로 새로 생성하지 않고 기존 기록을 조립·검증하는 경우에만** 성립.
- 과소평가하기 쉬운 함정(codex 지적):
  1. StepLog만으로는 변경 파일·심볼·테스트와 각 결정의 연결이 부족 — **소규모 스키마 확장 필요**.
  2. `INFERENCE` 판정은 단순 문자열 조립으로 완전히 해결 안 됨.
  3. 진짜 어려운 문제는 "무엇을 모르는가"(근거 없는 주장)를 정확히 표시하는 것.
  4. Replay UI는 데이터 생성보다 **구현·상태 모델링 비용**이 큼(1단계 범위 밖으로 확정).
  5. Drift 검출은 해시 메커니즘보다 **"어떤 범위의 설명이 어떤 코드 범위에 종속되는가"**가 핵심.

### 3.2 MVP 범위 (codex 권고, 그대로 채택)

**만든다(1단계)**:
- `changes.diff` + 기존 StepLog/run.log/ACQUIRE/calibration을 조립한 **Evidence-grounded Explain Diff**.
- 문장 유형 `FACT`/`RECORDED_DECISION`/`INFERENCE`/`OPEN_QUESTION` 표시, 각 문장에 파일·심볼·diff
  hunk·테스트·로그 ID 연결. **근거 없는 문장은 자동으로 `OPEN_QUESTION`**(억지로 채우지 않음).
- base/proposed 해시 + **심볼별 해시**(파일 전체 아님)로 만드는 **Explanation Drift Detector**.
- 기존 **T1(triage) 위험도**에 따른 **정적** comprehension checklist(LLM 아님 — 템플릿 선택).
- 결과를 review bundle(F1-d, `yok3x-out/<run_id>/`)에 JSON/Markdown으로 추가.

**명확히 자른다(1단계 범위 밖)**:
- LangGraph·상시 신규 에이전트(Evidence Collector 등 전용 역할) — 기존 producer-reviewer 호출을 재사용.
- Replay 스크러빙 GUI(§9에서 후속 후보로만 등록).
- 자동 통과/자동 반영 결정 — 사람 게이트는 기존 F1 체계 그대로.
- 자연어 설명의 완전성·정확성을 LLM으로 "판정"하는 기능(과신 위험, §3.4).
- 인증·결제 등 고위험 영역의 정교한 퀴즈 자동 생성(deep 모드에서도 최소한으로).

### 3.3 opt-in 선택 옵션 (codex 설계, 이름·상한 그대로 채택)

기본값 **`off`**.

| 옵션 | 추가 LLM 호출 | 내용 |
|---|---|---|
| `off` | **0회** | 구조화된 Explain Diff·근거 링크·drift 검출·정적 checklist만(전부 기계적). 기존 승인 게이트 불변. |
| `light` | **최대 1회** | 신규 호출 대신 **기존 reviewer 호출**에 "근거 연결 설명"을 함께 요청(프롬프트에 추가 지시만 얹음). 퀴즈 없음. 근거 없는 주장은 여전히 `OPEN_QUESTION`. |
| `standard` | **최대 1회** | 위험도 T2 이상일 때만 핵심 3~5문항 comprehension check 생성. 평가는 **규칙 기반 우선**(키워드·필수개념·불변조건 존재 확인), 애매한 답변만 기존 reviewer로 1회 판정. |
| `deep` | **명시적 예산 설정 시에만, 상한 2회** | forensic 재설명·반사실·불변조건 질문 허용. T3(고위험) 변경에만 권장. 상한 초과 시 자동 중단. |

옵션 이름(`off/light/standard/deep`)은 설정 키·CLI·로그·(후속) GUI select에서 동일하게 유지한다.

### 3.4 비용 최소화 기법 (codex 권고, 구현 원칙으로 채택)

- **캐시 키**: `base_sha + proposed_sha + diff_sha + ACQUIRE답변해시 + mode + prompt_version`. 동일
  diff는 설명·claim·퀴즈를 재생성하지 않는다.
- **신규 호출 만들지 않기**: `light`/`standard`는 기존 reviewer 호출의 응답을 재사용하거나, 그 호출의
  프롬프트에 지시를 추가하는 방식만 쓴다(별도 에이전트 역할 신설 금지).
- **전송량 최소화**: 전체 저장소가 아니라 변경 hunk·관련 심볼·ACQUIRE evidence·관련 테스트만 프롬프트에 넣는다.
- **결정론 우선**: `FACT`(diff·파일시스템에서 기계 생성) · `RECORDED_DECISION`(run.log/StepLog/ACQUIRE에서
  직접 추출) · `OPEN_QUESTION`(근거부재·unknowns·테스트 미실행·drift 규칙) 은 **전부 LLM 없이** 생성.
  `INFERENCE`만 "근거에서 도출된 추정" 템플릿으로 제한.
- **claim 검증은 기계 검사부터**: 경로 존재·심볼 존재(ACQUIRE의 `verify_evidence`와 같은 메커니즘 재사용)·
  diff 포함 여부·테스트 통과·해시 일치 — LLM은 이 기계 검사로 판정 안 되는 잔여에만.
- **퀴즈 평가도 규칙 우선**: 키워드·필수개념·불변조건 존재 여부를 먼저 검사하고, 애매한 것만 LLM.
- **효과 없으면 자동 비활성화**: `calibration.jsonl`로 comprehension 기능이 실제 결함 탐지에 기여하는지
  계측(기존 F0 심판 캘리브레이션 인프라 재사용) — 상관이 없으면 자동 호출을 끈다(과신 방지).
- **예산은 기존 R-3에 등록**: 토큰/호출 상한을 `guard.reservation`에 등록해 기존 preflight 예산검사·
  pacing 체계 안에서 그대로 차단되게 한다(신규 예산 메커니즘 만들지 않음).

### 3.5 실패하기 쉬운 지점 (codex 지적, 완화책 포함)

1. **"근거 있는 환각"**: 근거 링크가 붙어 있어도 설명의 인과관계 자체는 틀릴 수 있다 — 근거 링크 존재를
   "정확성 보장"으로 오인하면 안 된다. **완화**: 불확실성은 적극적으로 `INFERENCE`/`OPEN_QUESTION`으로
   남기고, UI/출력에서 "근거 있음 ≠ 확실함"을 항상 병기한다.
2. **Drift 검출 범위**: 너무 넓으면(파일 전체 단위) 매번 무효화돼 소음이 되고, 너무 좁으면 낡은 설명이
   살아남는다. **완화**: 1단계는 diff hunk·심볼·관련 테스트 단위로 **보수적으로** 무효화한다(파일 전체
   해시가 아니라 심볼별 해시).

## 4. 데이터 스키마 (codex "소규모 확장 필요" 반영)

기존 `StepLog`/`step_NN.json`에 **파일·심볼·테스트 식별자** 필드를 추가한다(신규 LLM 호출 없이 diff
파싱 + 기존 verify 결과에서 기계적으로 채움):

```python
# StepLog 확장(orchestrator.py) — 전부 기계 추출, LLM 호출 0
changed_files: list[str] = field(default_factory=list)      # diff에서 파싱
changed_symbols: list[str] = field(default_factory=list)    # diff hunk의 def/class 시그니처에서 파싱
related_tests: list[str] = field(default_factory=list)      # verify_cmd 결과·pytest 출력에서 파싱(가능한 만큼)
```

`Claim`(주장 단위 — 문서 §13.2 원안의 `evidence_refs` 아이디어 채택, 축소):

```python
{
  "claim_id": "...",            # 결정적 SHA-1(ACQUIRE의 core_claim()과 같은 패턴 재사용)
  "type": "FACT|RECORDED_DECISION|INFERENCE|OPEN_QUESTION",
  "text": "...",
  "evidence_refs": [{"file": "...", "symbol_or_hunk": "...", "source": "diff|run_log|acquire|test"}],
  "symbol_hash": "...",         # drift 검출용 — 이 claim이 종속된 코드 범위의 해시
}
```

`.yok3x/runs/<run_id>/understanding_bundle.json`에 저장(knot에는 저장 안 함 — ACQUIRE와 같은 이유,
BUG-13 자기오염 재발 방지). review bundle(F1-d)에 Markdown 렌더로 함께 게시.

## 5. 설정 (opt-in, 기본 off)

```python
# DEFAULT_YOK3X에 추가
"sync_layer": {
    "mode": "off",              # off | light | standard | deep
    "deep_call_budget": 2,       # deep 모드 상한(초과 시 자동 중단)
    "auto_disable_if_uncorrelated": True,  # calibration으로 효과 없음 확인되면 자동 off
},
```
task spec에서 per-task override 가능(기존 `agents_override` 패턴과 동일하게).

## 9. 후속 후보 (지금 범위 밖, 효과 확인 후 재검토)

- Multi-Agent Execution Replay(스크러빙 GUI) — codex: "구현·상태 모델링 비용이 큼". step_NN.json이
  이미 필요한 원시 데이터를 갖고 있으므로, **순수 GUI 렌더 기능**으로 후속 검토 가능(§5.6 승인 필요).
- Cross-Agent Conflict Map(병렬 워커 간 심볼/설계개념 충돌 탐지) — C(진짜 병렬)가 이미 있으므로 병렬
  fanout 결과에 대해서만 값이 있음. 병렬 사용 빈도가 낮으면 우선순위 낮음.
- 인지 부채 수치화(D = Σ w·n·(1-u)) — F0의 교훈과 동일하게 **데이터 없이 먼저 점수 공식을 만들지
  않는다**. calibration 데이터가 쌓인 뒤 재검토.
