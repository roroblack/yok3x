# 계획 · knot 노트 검증 상태 (YOK-119)

- **작성**: 2026-09-21 · **상태**: 계획 (구현 전) · **이슈**: YOK-119
- **계기**: RSIAgent 논문(arXiv 2609.15364) 논의에서 나온 적용 후보 ①. 논문 자신이 "부분 검증된
  결정이 해로운 재사용 규칙이 될 수 있다"고 인정한다. 우리 knot 은 이미 같은 위험 구조를 갖고 있다.
- **선행 결정**: V-10 계획서([v4.x-plan-okf-knowledge-format-2026-08-30.md](v4.x-plan-okf-knowledge-format-2026-08-30.md))가
  `verified`·`status`·`stale_after` 를 Phase 1 범위 밖으로 미뤘다. 이 문서는 그 Phase 2 이다.

> 논문 근거의 한계: 위 논문 내용은 **초록과 요약된 본문**만 봤고 전문을 읽지 않았다. 아래 설계는
> 논문이 아니라 **우리 코드에서 확인한 사실**에 근거한다. 논문은 문제 인식의 계기일 뿐이다.

## 문제 (코드에서 확인한 것)

[yok3x/knot.py](../../yok3x/knot.py) 의 `context_for_prompt` 는 질의와 맞는 노트 최대 3개를 골라
각 600자를 워커 프롬프트에 넣는다. 이때 거르는 기준은 **`source != "orchestrator"` 하나뿐**이다.

- 사람이 쓴 노트가 **틀렸거나 낡아도** 걸러낼 수단이 없다. 노트가 옳은지 아는 필드가 없다.
  (`status`·`verified`·`stale_after` 를 `knot.py` 전체에서 검색했고 0건 — 이 검색이 놓칠 수 있는 것:
  다른 이름의 같은 개념. `_recency_weight` 가 `created` 기준 감쇠를 하지만 그것은 "옛날 것"이지
  "틀린 것"이 아니고, `recency_halflife_days` 기본값이 0(꺼짐)이다.)
- `source` 필드가 자기 신고 문자열이라 `orchestrator` 가 아니면 통과한다. BUG-13
  ([BUG-13](../reports/bugs/BUG-13-self-poisoning-brief-knot-loop.md))이 실제로 **자기오염 루프**를 냈고,
  거기서 막은 것은 "자동 저장 노트" 한 종류뿐이다. "사람이 저장했지만 검증 안 된 노트"는 여전히 통과한다.
- 주입된 노트가 **어느 것이었는지 기록이 없다.** `orchestrator.py:1096` 은 `context_for_prompt` 의
  반환 문자열을 프롬프트에 붙일 뿐이고, 런 상태에는 노트 id 가 남지 않는다(`knot.`·`injected`·`knot_ids`
  를 `orchestrator.py` 에서 검색, 저장 필드로 쓰이는 곳 없음 — 이 검색은 다른 모듈의 기록을 못 본다).
  그래서 "이 노트가 성공/실패와 관련 있었나"를 **나중에 물어볼 수 없다.**

## 하지 말아야 할 것 (경계)

- **주입량을 늘리는 방향으로 가지 않는다.** 이 계획은 걸러내기(정밀도)에 관한 것이고 회수율이 아니다.
- **자동으로 `verified` 를 붙이지 않는다.** 검증 통과 런에 쓰였다고 노트가 "검증됐다"고 하면 논문이 경고한
  부분검증→재사용 규칙 문제를 그대로 만든다(그 런의 통과는 이 노트 덕이 아닐 수 있다).
  `verified` 는 **사람이 명시적으로** 붙인다.
- **기존 노트를 일괄 변환하지 않는다.** 필드가 없으면 지금과 똑같이 동작해야 한다(하위호환).

## Phase 0 — 계측부터 (구현 전 필수, 작음)

가치를 재기 전에는 걸러내기 규칙을 넣지 않는다(V-5§4.1·V-8과 같은 원칙).

1. `context_for_prompt` 가 주입한 노트의 **id·제목·점수를 반환**하게 하고(문자열은 그대로),
   오케스트레이터가 런 상태에 `knot_injected: [{id, score}]` 로 남긴다. 노트 본문은 저장하지 않는다.
2. 여러 런이 쌓이면 **노트별로 주입 횟수 × 그 런의 게이트 통과/실패**를 세는 읽기 전용 집계를 낸다.
   표본이 작으면 **「구분되지 않는다」**로 표시한다(전역 규칙 §8).

Phase 0 의 목적은 두 가지다: ① 실제로 주입되는 노트가 있는지(있는데 안 쓰이면 Phase 1 은 헛수고),
② 나중에 걸러내기의 효과를 잴 기준선.

**Phase 0 결과가 "실사용에서 주입이 거의 안 된다"면 Phase 1·2 는 접는다.** 이 저장소에는
`.yok3x/knowledge/` 폴더 자체가 없다(2026-09-21 `ls` 로 확인). `test_workspace` 의 다른 작업폴더
몇 곳(`t2_round2_runs/*`, `Modulyth/*`)에는 `knowledge` 폴더가 있으나 **그 안의 노트 수·내용은
세지 않았다.** 즉 지금 가진 데이터로는 효과를 논할 수 없다는 것이 출발점이다.

## Phase 1 — 필드 도입 (Phase 0 가 필요를 보인 뒤)

`save()` 가 쓰는 frontmatter 에 선택 필드 추가. **OKF v0.2 와 이름을 맞춘다.**

| 필드 | 값 | 기본 | 의미 |
|---|---|---|---|
| `status` | `draft` \| `stable` \| `deprecated` | (없음 = 현재와 동일) | `deprecated` 는 주입 제외 |
| `verified_by` / `verified_at` | 문자열 / ISO 날짜 | 없음 | 사람이 확인한 표시 |
| `stale_after` | ISO 날짜 | 없음 | 이 날짜 이후는 주입 제외(또는 강등) |

### 파서 제약 — 결정이 필요한 지점

`_load_notes` 의 frontmatter 파서는 줄 단위 `key: value` 분할이다. OKF 는 `verified` 를
`[{by, at}]`(YAML 목록-맵)로 정의하는데 **이 파서는 그걸 못 읽는다**(한 줄 flow 스타일 값도
불투명 문자열로 취급).

| 안 | 내용 | 장단 |
|---|---|---|
| A (권장) | 평평한 키 `verified_by`·`verified_at` | 파서 무변경, 단순. 다만 OKF 원형과 모양이 다르다(내보낼 때 변환 필요) |
| B | OKF 형태 `verified: [{by: x, at: y}]` 를 한 줄로 쓰고 소형 파서 추가 | 원형과 일치. 파서 확장 = 새 위험·새 시험 |
| C | 전체 YAML 파서 도입 | **stdlib-only 원칙 위배** — 배제 |

권장은 A. 외부 OKF 도구와의 교환이 실제로 생길 때 B 로 옮겨도 늦지 않다(필드 이름은 이미 맞춰 둠).

### 주입 필터

`context_for_prompt` 의 기존 조건에 추가:

- `status == "deprecated"` → 제외
- `stale_after` 가 지났으면 → 제외
- **그 외(필드 없음 포함)는 현재와 동일** → 기존 노트·기존 시험이 깨지지 않는다.

### lint

`lint()` 에 검사 추가: `stale_after` 지난 `stable` 노트, `verified_at` 없이 `status: stable`,
알 수 없는 `status` 값. 자동 저장 노트(`orchestrator`)는 기존대로 lint 제외.

## Phase 2 — CLI (선택)

`yok3x knot verify <id> --by <이름>` / `knot deprecate <id>` — 파일을 손으로 고치지 않게.
RULE §5.6(GUI 는 명령 없이 건드리지 않음)에 따라 **CLI 만**, GUI 는 별도 명령이 있을 때만.

## 시험

- 필터: `deprecated` 노트가 주입되지 않는다 / `stale_after` 지난 노트가 주입되지 않는다 /
  필드 없는 기존 노트는 그대로 주입된다(하위호환 회귀).
- 파서: 새 필드가 있는 노트·없는 노트, 값에 `:` 가 들어간 경우(`line.split(":", 1)` 이므로 첫 콜론만 분할 —
  ISO 시각 `2026-09-21T10:00:00` 은 통과하는지 확인).
- Phase 0: 주입 결과의 id 목록이 런 상태에 남고 본문은 안 남는다.

## 이 계획이 확인하지 않은 것

- 논문 전문. 논문의 검증 에이전트가 "부분 검증"을 어떻게 다루는지는 모른다.
- 실사용에서 잘못된 노트가 실제로 주입돼 해를 낸 **사례**. BUG-13 은 자동 저장 노트 사례이고,
  "사람이 쓴 낡은 노트" 사례는 확인하지 못했다. Phase 0 이 그 사례가 있는지 먼저 본다.
- T-1 에서 잰 리뷰어 점수 편차(최대 표준편차 1.6)는 이 계획과 직접 관련이 없다 — 노트 품질을 점수로
  판정하려는 것이 아니다.

## 진행 순서 제안

Phase 0 → (결과 보고 사용자 판단) → Phase 1 A안 → Phase 2. 각 단계 뒤에 멈춘다.
