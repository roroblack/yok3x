# v4.7.0 · 계획서 — SSH GPU(4070 Super) 원격 로컬 LLM 백엔드 · 2026-08-10

**배경**: 사용자가 SSH로 접근 가능한 GPU 서버(RTX 4070 Super, VRAM 12GB)를 보유. 여기에 Gemma4나
Qwen 같은 로컬 모델을 구성해 yok3x 작업 백엔드로 쓸 수 있게 계획서를 요청.

**핵심 발견**: yok3x는 이미 v3.5.0(P3 오프라인 폴백)에서 **OpenAI 호환 로컬 서버**를 백엔드로 쓰는
어댑터(`backends.local`, `type: openai_http`, `_run_openai_http` — stdlib `urllib`만, 의존성0)를
갖고 있다. 이건 서버 위치를 가리지 않는다 — **로컬호스트든 SSH 터널 너머 원격 GPU 서버든 똑같이
`base_url`만 바꾸면 된다.** 즉 **yok3x 코드는 거의 그대로**, 필요한 건 (1) 원격 서버에 추론 서버
설치, (2) 안전한 연결 경로(SSH 터널), (3) 약간의 설정/편의 코드다.

## 1. 원칙 확인 (착수 전)

- **의존성0 유지**: SSH는 `subprocess`로 시스템 `ssh` 바이너리를 호출(worktree.py가 `git` CLI를
  쓰는 것과 같은 패턴) — 신규 pip 패키지 없음.
- **자격증명 처리 금지**: yok3x는 SSH 키·비밀번호를 다루지 않는다. 사용자가 이미 구성한 SSH
  설정(`~/.ssh/config`, 키 기반 인증)을 그대로 재사용 — yok3x는 `ssh <host>` 명령만 실행한다.
- **보안(필수)**: 원격 추론 서버는 **`127.0.0.1`에만 바인드**(네트워크에 직접 노출 금지). 접근은
  **오직 SSH 터널을 통해서만** — 포트를 공인 IP나 `0.0.0.0`에 열면 인증 없는 코드실행형 서버가
  인터넷에 노출되는 셈이라 절대 금지. 이 문서의 모든 설계가 이 전제를 따른다.

## 2. 원격 서버 설정 (yok3x 밖 — 사용자 몫)

### 2.1 추론 서버 선택
`_run_openai_http`가 요구하는 건 `/v1/chat/completions`(OpenAI 호환)뿐이므로 아무거나 가능:

| 서버 | 장점 | 비고 |
|---|---|---|
| **llama.cpp server** | 가장 가볍고 의존성 적음, GGUF 양자화 모델 바로 지원 | 4070S 12GB에 가장 잘 맞음(권장) |
| Ollama | 설치·모델 관리 쉬움(`ollama pull`) | `/v1` 호환 엔드포인트 있음(최근 버전) |
| vLLM | 처리량 최고, 배치 추론 강함 | VRAM 요구가 커서 12GB엔 타이트 |

**권장**: llama.cpp server(`llama-server`) — 이미 v3.5.0 문서에 "Ollama·llamafile·lm-studio" 등과
함께 언급된 계열, GGUF 양자화로 12GB VRAM에 잘 맞는 모델을 고를 수 있음.

### 2.2 모델 선택 (VRAM 12GB 기준 현실적 후보)

| 모델 | 양자화 | 대략 VRAM | 코딩 적합성 |
|---|---|---|---|
| Qwen2.5-Coder-7B-Instruct | Q8(거의 무손실) | ~8GB | 코딩 특화, 7B치고 강함 — **1순위 후보** |
| Qwen2.5-Coder-14B-Instruct | Q4_K_M | ~9-10GB | 더 강하지만 느림, 컨텍스트 길면 VRAM 빠듯 |
| Gemma-2-9B-it | Q4_K_M | ~6-7GB | 범용, 코딩은 Qwen-Coder 계열보다 약함 |

사용자가 "젬마4나 큐엔"이라 했으므로 **둘 다 구성해두고 `backends.json`의 `model` 필드로 전환**
가능하게 설계(§4). 실제 코딩 워커로는 Qwen2.5-Coder 계열이 더 적합할 가능성이 높다는 점은 참고로
남기되, 최종 선택은 실측(§6 검증) 이후 사용자가 결정.

### 2.3 서버 기동 예시 (사용자가 원격 서버에서 직접 실행)
```bash
# 원격 GPU 서버에서, 127.0.0.1에만 바인드 — 절대 0.0.0.0 아님
llama-server -m qwen2.5-coder-7b-instruct-q8_0.gguf \
  --host 127.0.0.1 --port 8000 --ctx-size 8192
```

## 3. 연결 경로 — SSH 로컬 포트포워딩

```bash
# yok3x가 실행되는 머신에서: 원격 127.0.0.1:8000을 로컬 127.0.0.1:8100으로 터널링
ssh -N -L 8100:127.0.0.1:8000 <user>@<gpu-host>
```
터널이 떠 있는 동안 로컬에서 `http://127.0.0.1:8100/v1`이 곧 원격 GPU 서버다. yok3x 입장에서는
**로컬 서버와 완전히 동일하게 보인다** — `_run_openai_http`는 `base_url`이 로컬인지 터널인지 모른다
(그래서 코드 변경이 거의 필요 없다).

## 4. yok3x 쪽 변경사항

### 4.1 config 추가 (신규 코드 없음 — `backends.json`만)
```jsonc
// backends.json에 신규 항목(기존 "local"과 별개 이름 — 근처 로컬 서버와 원격 GPU를 둘 다 유지)
"local-gpu": {
  "type": "openai_http",
  "base_url": "http://127.0.0.1:8100/v1",   // SSH 터널 로컬 끝
  "model": "qwen2.5-coder-7b-instruct",
  "timeout_sec": 180
}
```
`yok3x.json`의 `workers`에 `"local-gpu-main": {"backend": "local-gpu", "role": "..."}` 추가하면
바로 워커로 쓸 수 있다(P3가 만든 `local-main`과 완전히 같은 패턴).

### 4.2 작은 코드 개선(권장, 선택) — `list_models`가 "local"만 하드코딩
`yok3x/limits.py:235`의 `if backend == "local":`이 백엔드 **이름**을 하드코딩해서, `local-gpu`
같은 새 이름은 모델 목록 조회(`/v1/models`)가 안 된다(GUI 모델 드롭다운이 비어 보임). 이름 대신
**타입**으로 판정하도록 일반화:
```python
if cfg.backends.get(backend, {}).get("type") == "openai_http":
    conf = (cfg.yok3x.get("limits") or {}).get(backend) or {}
    base = str((cfg.backends.get(backend) or {}).get("base_url")
               or conf.get("base_url") or "http://localhost:8000/v1").rstrip("/")
    ...  # 나머지 동일
```
**하위호환**: 기존 `"local"` 백엔드는 `type: openai_http`이므로 그대로 동작(회귀 없음). 신규 테스트로
확인.

### 4.3 SSH 터널 관리 — CLI 편의 명령(선택, 의존성0)
매번 수동으로 `ssh -N -L ...`을 띄우고 관리하는 게 번거로우므로, 얇은 래퍼를 검토할 수 있다:
```
yok3x tunnel up local-gpu     # ssh -f -N -L <local>:<remote_host>:<remote_port> 백그라운드 기동
yok3x tunnel status local-gpu # 로컬 포트 리슨 여부 + /v1/models 호출로 헬스체크
yok3x tunnel down local-gpu   # 관리 중인 ssh 프로세스 종료
```
- 신규 `yok3x/tunnel.py`: `subprocess.Popen(["ssh","-f","-N","-L",...])` + pidfile(`.yok3x/tunnel_<name>.pid`)
  로 수명 관리. `worktree.py`가 `git` CLI를 다루는 것과 같은 패턴(외부 프로세스 호출, 결과 파싱만).
- 설정: `yok3x.json`에 `ssh_tunnels: {local-gpu: {host, user, remote_port, local_port}}`.
- **자격증명 없음**: `user@host` 조합만 저장하고 인증은 SSH 자체(키/agent)에 위임 — yok3x는 절대
  비밀번호·키 파일 내용을 다루지 않는다.
- **이 부분은 순수 편의 기능**이라 §4.1(config)만으로도 이미 완전히 동작한다 — 터널은 사용자가
  수동으로 띄워도 됨. 자동화는 착수 조건이 아니라 "있으면 편한" 후속.

### 4.4 P3 오프라인 폴백과의 통합 (신규 코드 불필요 — 확인됨)
`usage.failover_backend`의 `offline_backend`는 이미 `d.get("offline_backend", "local")`로
**완전히 설정 가능**하다(하드코딩 아님, `yok3x/usage.py:694` 확인). 즉:
```jsonc
"guard": {"degrade": {"offline_backend": "local-gpu"}}
```
로 바꾸기만 하면 클라우드 백엔드 전멸 시 **원격 GPU 서버로 자동 강등** — 코드 변경 0.

## 6. 검증 계획

S4에서 반드시 실측할 것:
1. 지연시간: 로컬 네트워크가 아니라 SSH 터널을 거치므로 왕복 지연이 늘 수 있음 — 실사용 가능한
   수준인지 체감 확인.
2. 코드 품질: 7B/9B급 로컬 모델이 실제 코딩 작업(producer 역할)에서 claude/codex 대비 얼마나
   쓸만한지 — P3 문서도 "로컬을 주 생산자로 쓰는 건 안 만듦(품질 저하)"라고 명시했었다. 이번엔
   실측으로 재평가(4070S급 하드웨어 + 코딩 특화 모델이면 P3 때보다 나을 가능성).
3. 안정성: 터널 끊김 시 yok3x의 기존 에러 처리(`_run_openai_http`가 이미 `URLError`를 명확한
   에러 메시지로 반환 — "로컬 서버가 떠 있는지 확인")가 충분한지, SSH 터널 특유의 실패 모드
   (터널은 살아있는데 원격 서버가 죽음 등)도 같은 경로로 잘 잡히는지 확인.

## 7. 결정 필요 (구현 착수 전)

3. `guard.degrade.offline_backend`를 `local-gpu`로 바꾸는 건 S4 검증 결과를 보고 별도 결정
   (자동 강등은 품질에 직접 영향 — 성급히 켜지 않는다).
