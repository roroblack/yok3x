## 지시와 판단 정정

사용자 지시(2026-09-08): 처음에 나(Claude)는 "yok3x의 워커 실행은 1회성이라 사람이 끼어들
지점이 **구조적으로 없다**"는 이유로 WSO의 세션·개입 모델을 기각했다. 사용자가 반박했다 —
"어차피 너도 나한테 계속 작업중 피드백 받으면서 반영하고 중간 보고도 하고, 한 파트 끝나거나
할 때 내가 추가 지시를 하거나 물어보거나 할 수 있잖아?" 그리고 이어서: **"1회성으로 되어
있으면 그게 잘못된 거야. 내가 이전에 말한 것처럼 동작할 수 있게 개선안 작성해라."**

**내 기각 근거는 코드로 확인해보니 사실과 달랐다.** 상호작용 지점은 이미 존재한다:

| 이미 있는 것 | 위치 |
|---|---|
| 주입 가능한 질의 함수 `self.ask = ask or (lambda msg: input(msg))` | `orchestrator.py:395` |
| 단계 실행 전 승인 게이트(y/N/q) | `orchestrator.py:532-542` (`_gate`) |
| 도구 사용 전용 게이트 — `auto_approve`로도 우회 불가 | `orchestrator.py:544-554` (`_gate_mcp`) |
| CLI 기본값이 "매 단계 사람에게 묻기"(`auto_approve: False`) | `config.py:25` |
| `ask`를 호출자가 갈아끼울 수 있게 뚫린 경로 | `orchestrator.py:3000` (`run_task_file(..., ask=ask)`) |

즉 정확한 진단은 "사람이 개입할 수 없다"가 아니라 —
**개입 방식이 `y`/`N`/`q` 세 글자로 제한돼 있고, GUI에서는 그마저 통째로 꺼져 있다**이다.
사용자가 요구한 "피드백 주면 반영", "중간 보고", "파트 끝날 때 질문"은 이 세 글자로는
표현할 수 없다. 그러니 사용자 판단이 맞다 — 이건 설계상 어쩔 수 없는 게 아니라 **고쳐야 할
결함**이고, 고칠 이음매(`ask`)는 이미 뚫려 있다.

## 진짜 결함 4가지 (코드 근거)

1. **GUI에서 시작한 런은 항상 무인 실행이다.** `guiserver.py:594,597`이 `auto=True`를
   하드코딩한다. 대시보드에서 실행하면 모든 게이트를 건너뛴다. 그리고 GUI API에는 승인·
   피드백·일시정지 엔드포인트가 하나도 없다.
   *확인 범위*: `guiserver.py`에서 `path == "/api/` 정확일치 dispatch 13건을 전부 열거했고,
   접두 dispatch(`path.startswith("/api`)는 0건임을 따로 확인했다 — 두 방식 모두로 봤다.
   이 방법이 놓칠 수 있는 것: 경로명을 런타임에 조립하는 dispatch인데, 이 파일엔 그 패턴이
   없다(위 2건이 전부).
2. **게이트가 이진이다.** 승인·건너뜀·중단만 된다. **피드백 문장을 넣어 다음 단계에
   반영시키는 채널이 없다.** 사용자 요구의 핵심("피드백 받으면서 반영")이 지금 구조로는
   표현 불가.
3. **중간 보고가 없다.** `_gate`는 `description` 한 줄만 보여주고 판단을 요구한다. 직전
   워커가 실제로 뭘 만들었는지는 `step_NN_*.json`에 기록되지만 **게이트 시점에 제시되지
   않는다.** 사람은 내용을 모르는 채 y/n을 눌러야 한다.
4. **질문 채널이 없다.** 런 중간에 "이건 왜 이렇게 했어?"를 묻고 답을 받을 방법이 없다.

## 최종 목표 (North Star) — 사용자 지시 2026-09-08

> "최종적으로 나는 이 멀티 에이전트 툴을 그냥 지금 쓰는 클로드나 코덱스 GUI 대신에 쓰고
> 싶어. 매번 저것들 호출해서 쓰는 거 너무 빡쳐. 겁나 더럽게 무겁고. 그냥 단순히 채팅처럼
> 쓰는 기능도 제공하고 자동완성 코딩툴로서 기능도 제공하고 뭐 이렇게 되어 있으면 좋겠어.
> 그러면서도 지식그물 잘 구축해 놓고 GUI도 내 마음에 들게 설계하고."

**즉 yok3x의 종착점은 "가끔 돌리는 배치 오케스트레이터"가 아니라 Claude Code·Codex GUI를
대체하는 상시 작업 인터페이스다.** 이 문서의 S1~S4는 그 자체가 목적이 아니라 그리로 가는
1단계다 — "런 중에 사람이 보고 끼어든다"가 되면 그게 곧 채팅의 최소 형태이기 때문이다.

**이 목표가 무거움을 이겨야 한다는 제약**: 사용자가 기존 도구에 대해 지적한 불만이
"무겁다"이므로, 대체재가 더 무거우면 의미가 없다. yok3x의 현재 구성(정적 HTML 한 장 +
표준 라이브러리 `http.server`, 빌드 단계 없음, Electron 없음, `knot.py`가 반복해서 지키는
"의존성 0" 원칙)은 그 자체가 경쟁력이다. **프레임워크·번들러·Electron 도입 금지**를 이
로드맵의 설계 제약으로 명시한다.

### 실현 가능성 — CLI 기능을 직접 확인함 (2026-09-08)

"워커가 1회성이라 채팅이 안 된다"는 것도 사실이 아니었다. 실제로 `--help`를 호출해 확인:

| backend | 확인된 기능 | 의미 |
|---|---|---|
| `claude` | `--input-format stream-json`(실시간 스트리밍 입력, `--print`와 함께) · `--output-format stream-json` · `-r/--resume <세션ID>` · `-c/--continue` | **같은 서브프로세스로 양방향 다중턴 세션이 가능**하다 |
| `codex` | `exec resume <id>` · `--last` · `exec fork <id>` · `--json`(JSONL 이벤트) | 세션 재개·분기 가능. 양방향 스트리밍 입력은 미확인 |

*확인 범위*: `claude --help` / `codex exec --help` 출력의 플래그 존재만 확인했다. 이 방법이
놓칠 수 있는 것 — 플래그가 있어도 실제 동작·오류 처리·세션 파일 위치는 다르다. **Phase 2
착수 전에 실제로 왕복 2턴을 돌려 확인해야 한다**(그 확인 자체를 Phase 2의 첫 작업으로 둔다).

현재 yok3x는 이 능력을 하나도 안 쓰고 있다 — `backends.json`의 claude는
`claude -p --output-format json --disallowedTools Bash,Edit,Write,Read,Glob,Grep,TodoWrite,WebFetch`
로 **1회성 + 도구 전면 차단**이다. 다만 `backends.py:181-195`에 `--disallowedTools`를
`--allowedTools` 화이트리스트로 교체하는 경로가 **이미 있다**(조사 프로필·MCP 워커용) —
도구를 켜는 기계장치도 새로 만들 필요가 없다.

다르다. (b)는 LSP 서버나 편집기 확장이 필요해 별도 트랙이다. S8 착수 전에 확인한다.

## Phase 1의 목표 — WSO의 설계 원칙을 런에 적용

WSO 문서의 핵심 원칙 **"자동 실행 · 항상 표시 · 선택적 개입 · 즉시 되돌리기"**를 그대로
가져온다. 기본은 자동으로 흐르되, 사람이 지금 어디인지 보고 있고, 원할 때 끼어들 수 있고,
끼어든 내용이 다음 단계에 반영된다. (원본 WSO의 대화 세션 lifecycle·Topic Detector·자동
세션 분기는 이번 범위가 아니다 — 아래 "범위 밖" 참고.)

## 단계별 작업 — 순서대로 하나씩 끝내고 넘어간다

각 단계는 **그 단계만 끝나도 쓸모가 있는 단위**로 끊었다. 앞 단계 없이 뒤 단계를 못 하는
의존만 남기고 나머지는 독립이다.

### S1. 체크포인트 프로토콜 — 게이트를 이진에서 대화로 (코어, GUI 아님) · YOK-104

- `_gate`의 반환을 `bool` → `GateDecision`(`approve` / `skip` / `abort` / `feedback(text)`)
- 응답 파싱 확장: `y`/`n`/`q`는 지금 그대로, **그 외 문장은 피드백으로 해석**
- 피드백이 오면 다음 워커 프롬프트에 `## 사람 피드백` 블록으로 주입하고, 같은 단계를 다시
  제시한다(사람이 만족할 때까지 반복 가능)
- `step_NN_*.json`과 `status.json`에 피드백 내용·시각을 기록(감사 가능, 조용한 반영 금지)
- **제약 유지**: 워커 스레드에서 `ask`를 부르지 않는다(`orchestrator.py:265` 주석의 기존
  규칙 — 병렬 배치 승인은 제어 스레드에서 한 번만)
- **하위호환**: `auto=True`(무인)면 지금과 동작이 동일해야 한다. `--unattended`(V-12)
  경로도 불변

### S2. 중간 보고 — 판단할 근거를 보여주고 묻는다 (코어, GUI 아님) · YOK-105

- 게이트를 제시하기 직전에 직전 step의 산출물 요약을 사람에게 보여준다
- 요약은 `knot.extract_key_points()` 재사용 — SELF-CHECK·SCORE·결정·결함 같은 결론 신호
  줄만 뽑는 기존 함수라 **새 LLM 호출이 0건**이다(`knot.py:126-135`)
- 함께 표시할 것: 워커·backend·모델, 점수, 발견된 이슈, 이번 단계 비용·소요시간
- CLI는 stdout, GUI는 S3의 체크포인트 패널

### S3. GUI 개입 경로 — 대시보드에서 끼어들 수 있게 (GUI, codex 구현) · YOK-106

- `guiserver.py:594,597`의 `auto=True` 하드코딩 제거 → 실행 시작 시 **무인 / 체크포인트**
  선택
- `ask`를 GUI 큐로 주입: 런이 질문을 걸면 `_RUN_STATE`에 pending question을 올리고 대기,
  사람이 답하면 그 값을 반환
- 신규 엔드포인트 2개:
  - `GET /api/checkpoint` — 대기 중인 질문 + S2의 중간 보고
  - `POST /api/checkpoint/answer` — `{decision: approve|skip|abort|feedback, text}`
- **무응답 정책이 필수다.** 사람이 자리를 비우면 런이 영원히 멈춘다. 기본은 "무기한 대기 +
  대시보드 상단에 눈에 띄게 표시"로 두되, `checkpoint_timeout_sec`(0=무기한)을 설정으로
  노출하고 타임아웃 시 동작(중단/자동승인)을 **명시적으로 고르게** 한다 — 조용한 기본값
  금지

### S4. 실행 그래프 뷰 — 지금 어디인지 보이게 (GUI, codex 구현) · YOK-107

- 좌측: 저장 작업(task) → 실행 이력(run) 네비게이터 (상태 아이콘: running/done/aborted/
  **대기중**)
- 우측: 선택한 run의 pattern별 토폴로지 — pipeline 직선 DAG / fanout-fanin 분기합류 /
  producer-reviewer 반복 루프. worker·backend·상태·점수·비용·시간, step 클릭 시 요약
- **체크포인트 노드를 그래프 위에 강조 표시** — "지금 사람 응답을 기다리는 노드가 어디인가"가
  이 UI의 존재 이유다. 스크린샷에서 사용자가 원한 "실시간으로 내 노드 위치 확인"이 이것
- 실행 중 노드를 그리려면 데이터가 더 필요하다: `StepLog`는 worker 호출이 **끝난 뒤**
  append되므로(`orchestrator.py:1287`) 그것만으로는 현재 위치를 못 그린다 → run별
  append-only `events.jsonl`(`NODE_PLANNED`/`NODE_STARTED`/`NODE_FINISHED`) 추가
- 폴링 주기: 현재 서버 캐시 5초(`guiserver.py:49`) + 브라우저 7초(`index.html:1710`)라
  체크포인트 대기를 알아채는 데 최대 12초가 걸린다. 체크포인트 상태만 별도 경량
  엔드포인트로 1~2초 폴링(전체 `/api/state`는 그대로 둔다)

### S5. 작업 계보 + 후속 작업 제안 (후속, 선택) · YOK-108

- task 간 명시적 관계 기록: `parent_task_id`/`depends_on`/`relation`. 지원 edge는 소수로
  제한 — `RUN_OF`/`RESUMES`/`DEPENDS_ON`/`DERIVED_FROM`/`PRODUCES_KNOWLEDGE`
- 같은 `label`이라는 이유만으로 자동 연결하지 않는다(추측 그래프 방지)
- run 종료 시 `follow_up_tasks` 제안 → **사람이 승인하면** 새 task로 저장/큐잉하고
  `DERIVED_FROM` edge 기록. WSO의 "필요하면 자동으로 새 세션 전환"을 승인 기반으로 축소한
  형태 — 자동 라우팅이 아니라 "검토 가능한 후속 작업 제안"이라 yok3x의 producer-reviewer
  성격에 맞는다

### S6. knot 메모리 계층 경계 정리 (코어, V-14) · YOK-103

WSO의 3계층 메모리(Working/Episodic/Semantic)를 기준으로 보면 현재 구현은 이미 3계층에
가깝지만 경계가 섞여 있다. **코덱스 지적을 Claude가 코드로 재검증해 모두 사실 확인**:

| 계층 | 현재 대응물 | 문제 |
|---|---|---|
| Working | `brief.md`/`context.md`/현재 worker prompt | task/run 귀속이 약함(프로젝트 전역 파일) |
| Episodic | `.yok3x/runs/<run_id>` | 구조적으로 적절 |
| Semantic | `knowledge/*.md` | 자동 run 요약이 같이 들어와 경계가 흐림 |

- `_finish()`가 **모든 성공 run**의 요점을 `knowledge/`에 `source=orchestrator,
  type=Run Summary`로 **저장한다**(`orchestrator.py:2356-2358`). `context_for_prompt`
  (`knot.py:211-216`)는 프롬프트 **주입만** 제외한다 → "knot엔 확정 결론만 있다"는 기존

### S7. 채팅 모드 — 지속 세션으로 다중턴 대화 (Phase 2) · YOK-109

- 세션 지속: 프로세스를 살려두고 stdin으로 다음 턴을 넣는 방식 vs `--resume`으로 매 턴
