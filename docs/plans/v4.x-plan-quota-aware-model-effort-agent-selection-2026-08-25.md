## 1. v4.9.0 계획과 V-5의 관계

v4.9.0 계획서는 처음부터 "작업의 성격·남은 쿼터·과거 성과"로 실행 강도와 작업량을 자동
조정하는 것을 목표로 삼았다. 특히 §2.3과 S4/S6에는 다음 내용이 이미 들어 있었다.

- `daily_pace_status()`의 `remaining`, `level`, reset 정보를 입력으로 사용한다.
- warn/예상 비용 초과 시 rounds를 먼저 줄이고 effort를 한 단계 낮춘다.
- backend stop/잔량 부족 시 `resolve_model()` 후보 폴백과 선택적으로 backend 재배정을 연결한다.
- full 모드에서만 빈 필드에 적용하고, 명시값·reviewer·verify/score gate는 보호한다.
- 한 런의 결정을 sticky하게 유지하고 resume/replay에는 decision hash를 남긴다.

따라서 V-5의 문제의식은 **v4.9.0에서 처음 논의된 범위와 직접 겹친다**. 다만 구현 결과는 아래처럼
계획보다 좁다.

| 항목 | v4.9.0 계획 | 실제 구현 | V-5의 잔여 범위 |
|---|---|---|---|
| 작업 난이도 기반 effort/rounds | S2 규칙 기반 추천 | 구현됨 | 정확도·역할별 적용 검토 |
| quota-aware rounds/effort | S4에서 pace를 읽고 full에 적용 | 순수 함수만 구현, 실행 경로에는 미연결 | 실제 pace adapter와 적용 정책 |
| backend 재배정 | 별도 opt-in으로 후보 전환 | stop에서 `backend_reallocation_required` 신호만 반환, 소비자가 없음 | 후보 재순위·실제 적용 |
| 모델 선택 | benchmark 후보 + quota 고려 | 정적 profile/benchmark와 기존 guard 열화만 사용 | 비용/품질 메타데이터 기반 선택 |
| 낮은 confidence 처리 | full을 assist로 하향 | 옵션은 있으나 실행 적용 없음 | 실제 하향 정책 |
| sticky/resume | 결정 hash로 동일 계획 재생 | 한 번 계산은 하지만 full resume를 아예 거부 | 재현 가능한 결정 스냅샷 |

**판단**: V-5는 "새 기능"과 "기존 계획의 미완 범위"가 섞여 있다. quota로 rounds/effort/backend를
조절하는 골격은 v4.9.0의 재논의이고, **같은 backend 안에서 비용·품질을 비교해 모델을 능동적으로
고르는 정책**과 **producer/reviewer 같은 에이전트 역할 자체를 바꾸는 정책**은 실제로 새로운 범위다.

## 2. 현재 코드가 실제로 하는 일과 하지 않는 일

### 2.1 S2 `recommend_effort_rounds()` — quota와 무관한 작업 분류기

`calculate_task_features()`는 task/brief/rubric/examples 길이, context glob 수, pattern,
stages/workers, acquire QA, verify/materialize 유무와 고정 위험 단어를 bounded feature로 만든다.
`recommend_effort_rounds()`는 이를 `tiny|small|medium|large|risk` bucket으로 나눠 결정론적으로
effort와 rounds를 추천한다.

- tiny: low, 1 round
- small: medium, 2 rounds
- medium: medium, 2 rounds
- large: high, 3 rounds
- risk: high, 4 rounds

`min_rounds`/`max_rounds_cap`으로 clamp하지만, 함수 인자의 `calibration`은 명시적으로 버린다.
즉 S2는 **과거 성과도, 현재 backend도, quota도 보지 않는다**. full 모드에서는 task에
`max_rounds`가 없으면 이 추천을 적용하고, `allow_effort_adjustment=true`이며 top-level `effort`가
없으면 같은 effort를 producer와 reviewer 양쪽 worker override에 넣는다. 이름과 달리 이 opt-in은
"quota 때문에 effort를 조정"하는 스위치가 아니라 현재 실행 경로에서는 **S2의 정적 추천을
적용하는 스위치**다.

### 2.2 S4 `plan_quota_aware_effort_rounds()` — 구현됐지만 실행에는 연결되지 않음

S4 함수 자체에 대한 TODO.md의 설명은 대체로 맞다.

- `ok`: S2 추천을 유지한다.
- `warn`: rounds를 bucket의 후보 하한까지 먼저 내린다.
- rounds가 이미 하한이거나 `used >= cap`이고 `allow_effort_adjustment=true`이면 허용 후보 안에서
  effort를 한 단계 내린다.
- `stop`: 값을 바꾸지 않고 `backend_reallocation_required` 신호만 낸다. 실제 backend를 고르지 않는다.
- 예상 호출 수·토큰 비용은 계산하지 않는다. 함수 주석도 비용 예측을 후속 planner의 일로 남긴다.

하지만 핵심 연결이 없다. `build_automation_decision_snapshot()`은 `pace` 인자를 받은 경우에만 S4를
호출하는데, 실제 `run_task_file()`은 다음처럼 **pace 없이** snapshot을 만든다.

```python
orch.automation_decision = automation.build_automation_decision_snapshot(spec, cfg)
```

저장소 전체에서 production 호출은 이 한 곳뿐이다. GUI의 `build_state()`는 backend별
`daily_pace_status()`를 계산해 화면에 보여주지만 automation decision으로 전달하지 않는다.
결과적으로 현재 full 실행에서 실제 적용되는 것은 S2의 rounds와 선택적 effort뿐이며,
`quota_adjustment`, `backend_reallocation_required`는 런 결정에 도달하지 않는다.

따라서 TODO.md의 "`automation_mode=full` + `allow_effort_adjustment=True`일 때 S4 조정이 실제
적용된다"는 설명은 **현재 코드와 일치하지 않는다**. 정확한 표현은 "S4 결정 함수와 테스트는
있지만 실제 task 실행에는 아직 연결되지 않았다"다.

### 2.3 `resolve_model()`/`backend_available()`과 기존 적응형 열화

`resolve_model()`은 active profile의 상황별 pick을 먼저 놓고, `benchmarks` 점수 내림차순으로
후보를 확장한다. `available` 필터가 false인 backend만 건너뛴다. `backend_available()`의 판정은
CLI 설치 여부와 `check_backend()` 결과가 stop인지뿐이다. warn backend에는 순위 페널티가 없고,
후보 순서는 quota가 아니라 정적 benchmark 점수다. 이 부분은 TODO.md가 말한 **반응형 boolean
필터**라는 진단과 일치한다.

다만 "선제적 전환 로직이 전혀 없다"는 설명은 정확하지 않다. 호출 직전 `execute_call()`에는 이미
v3.2.0의 두 방어선이 있다.

1. `degrade_plan()`: `guard.degrade.enabled=true`이고 사용률이 기본 0.9 이상이면 해당 backend의
   `limits.<backend>.models.lite`로 모델을 낮춘다. `roles_no_downgrade`의 reviewer는 기본 제외한다.
2. `failover_backend()`: stop 또는 기본 0.97 이상에서, opt-in된 cloud failover가 있으면 가용한
   다른 cloud 중 `check_backend().ratio`가 가장 낮은 곳을 골라 런 동안 sticky하게 유지한다.

즉 **호출 직전 임계치 기반 모델 열화/백엔드 전환은 이미 있다**. 없는 것은 reset까지 남은 시간과
지속 가능한 소비 속도를 보고 stop 훨씬 전에 후보 순위를 바꾸는 계획 단계의 proactive 정책이다.
또한 기본 설정에서 Codex의 lite 모델은 빈 값이라 Codex 사용률이 90%를 넘어도 같은-backend 모델
다운그레이드는 일어나지 않는다.

### 2.4 "에이전트 자동 선택"은 아직 없음

현재 자동화는 producer/reviewer 이름을 quota로 바꾸지 않는다. `allow_backend_reallocation`도 S4의
boolean 신호일 뿐, `agents_override`나 `resolve_model()`을 수정하지 않는다. 기존 failover는 같은
worker의 실행 backend를 바꾸는 것이지 producer를 다른 역할/워커로 교체하는 기능은 아니다.
에스컬레이션은 낮은 score를 본 뒤 한 번 역할을 교체하는 별도 반응형 경로다.

따라서 사용자 문장의 세 축을 정확히 나누면:

| 축 | 현재 상태 |
|---|---|
| effort | S2 정적 추천은 full+opt-in에서 적용. quota 기반 S4 조정은 실행 미연결 |
| model | profile/benchmark 정적 선택 + 90% 임계 opt-in lite 열화. 지속 가능 pace 기반 선택은 없음 |
| agent/backend | stop/97% 부근 opt-in failover만 있음. 계획 단계 quota 재배정과 역할 선택은 없음 |

## 3. 사용자 시나리오 — Codex 주간 사용률 70%를 넘었을 때

현재 함수를 직접 호출해 다음 조건을 모사했다: reset까지 약 4일, Codex 7일 rolling 사용률 70%,
daily pace `catch_up + warn`, automation full, effort/backend adjustment opt-in, risk 작업.

관측 결과:

1. S2는 quota와 무관하게 `risk / high / 4 rounds`를 냈다.
2. `daily_pace_status()`는 이 시점의 catch-up cap을 0으로 조여 `warn`을 냈다. Codex는
   `since_reset_known=false`라 첫 관측의 오늘 사용량은 0으로 잡혔다. 즉 "주간 70%" 하나만으로
   오늘 소비량을 정확히 아는 것은 아니지만, 주간 진도 초과는 cap에 반영됐다.
3. `build_automation_decision_snapshot(spec, cfg)`를 실제 런과 같이 pace 없이 호출하면 결과는 여전히
   `high / 4 rounds`이고 `quota_adjustment` 필드조차 없다.
4. 같은 snapshot에 warn pace를 수동으로 넣으면 S4는 `medium / 3 rounds`와
   `rounds_and_effort`를 냈다. **함수는 되지만 배선이 안 된 상태**다.
5. `backend_available()`은 warn을 가용으로 취급하므로 `resolve_model()`의 balanced/build 정적 pick인
   `codex / gpt-5.6-sol`이 그대로 선택된다. Codex를 unavailable로 강제했을 때만 benchmark 차순인
   Claude 후보로 폴백했다.
6. 기존 `degrade_plan()`도 70%에서는 동작하지 않는다. 90%를 넘겨도 기본 Codex lite 모델이 비어
   있어 Codex는 다운그레이드할 모델이 없다.

따라서 "70%를 넘으면 무엇이 바뀌는가"의 현재 답은: **GUI pace 경고/cap은 바뀔 수 있지만,
task의 model·effort·backend는 그 사실 때문에 바뀌지 않는다.** pause 모드로 stop까지 가면
`backend_available()`/guard/failover가 반응하지만, 이는 미리 아끼는 계획이 아니라 정지 직전 또는
정지 후의 생존 경로다.

또한 70%라는 고정 임계치 자체를 정책으로 박는 것도 적절하지 않다. 70%가 안전한지는 reset까지
몇 일이 남았는지, 오늘 이미 얼마나 썼는지, 측정값이 since-reset인지 rolling 추정인지에 따라
달라진다. 정책 입력은 `current >= 70`보다 **남은 기간 대비 지속 가능 pace와 측정 신뢰도**여야 한다.

## 4. 제안하는 설계 — 두 단계로 분리

### 4.1 지금 권고: 관측/assist 배선 완성

첫 단계는 실행값을 바꾸지 않는 범위로 제한한다.

1. initial worker/profile routing 뒤 실제 후보 backend별 pace snapshot을 한 번 만들고, source/real,
   current, reset, daily used/cap/level을 decision input에 넣는다. 측정 실패와 daily pace off를
   `unknown`으로 구분한다.
2. S4를 assist snapshot에 실제 연결해 "현재 값"과 "quota를 고려하면 바뀔 후보"를 status/log/GUI에
   나란히 표시한다. 현재처럼 함수만 있고 production 소비자가 없는 상태를 끝낸다.
3. 전역 effort 하나가 아니라 **역할별 결정**으로 바꾼다. producer와 reviewer의 backend·model·effort를
   각각 표시하고, reviewer에는 `roles_no_downgrade`가 적용됐는지 명시한다.
4. `remaining`과 predicted cost를 구현하지 않은 상태에서는 "예산 안에 든다"고 주장하지 않는다.
   지금 S4처럼 `pace_warn`에 따른 보수적 후보라고만 표시한다.
5. §3의 70% 시나리오를 고정 fixture로 추가하되, reset까지 남은 기간·warn/pause·Codex 측정 신뢰도를
   분리해 검증한다.

이 단계는 새 LLM 호출이 없고 실행 품질을 바꾸지 않으면서, 실제 사용자 데이터로 "추천이 얼마나
자주 무엇을 낮췄을지"를 먼저 볼 수 있다. v4.9.0의 assist 원칙과 가장 잘 맞는다.

### 4.2 나중에만 검토: 제한된 full 자동 적용

자동 적용을 열 때도 세 축을 한꺼번에 켜지 않는다.

- **1순위 — rounds**: 명시값이 없을 때만 후보 하한까지 줄인다. producer-reviewer의 최소
  producer+reviewer 한 쌍과 verify를 보존한다.
- **2순위 — producer effort/model**: 별도 opt-in, `verify_cmd`가 있는 작업부터 제한적으로 시작한다.
  reviewer effort/model은 자동으로 낮추지 않는다. 현재 full이 한 effort를 양쪽 역할에 복사하는
  경로를 quota 조정에 그대로 재사용하면 안 된다.
- **3순위 — backend 재배정**: 또 다른 opt-in으로 분리한다. `resolve_model()`의 전역 의미를 바꾸지
  말고, 정적 quality 후보 목록 위에 quota penalty를 적용하는 별도 planner가 최종 후보와 이유를
  반환하게 한다. adversarial cross-family와 역할 제외 규칙도 보존한다.
- **에이전트 역할 자체 교체**: producer/reviewer 이름을 quota만으로 바꾸는 것은 backend 재배정보다
  영향이 크고 근거도 없다. V-5 MVP 범위에서 제외한다.

같은 backend 안에서 "싼 모델"을 고르려면 먼저 `models_catalog`에 명시적인 `cost_tier`/`quality_floor`
또는 운영자가 정한 downgrade chain이 필요하다. 현재 catalog에는 backend/model ID만 있고
`benchmarks`는 품질 점수일 뿐 비용 정보가 아니다. 모델 이름이나 benchmark가 낮다는 이유로
"쿼터를 덜 쓴다"고 추측해서는 안 된다.

full 결정은 런 시작 시 한 번 고정하고, 원 spec과 quota snapshot/hash를 manifest에 남겨야 한다.
현재처럼 full resume를 통째로 금지하는 보수적 구현은 안전하지만, 향후 resume를 지원하려면 같은
snapshot을 재사용하고 현재 quota로 조용히 재계산하지 않아야 한다.

## 5. 위험 — V-1보다 왜 더 심각한가

1. **T-1 심판 미검증이 품질 저하를 직접 증폭할 수 있음**: V-1은 과거 성공 태그를 다음 prompt에
   참고로 넣는 간접 개입이고, 잘못된 힌트여도 producer가 거부할 여지가 있다. V-5의 자동
   model/effort 다운그레이드는 **producer 호출 자체의 능력과 계산량을 직접 낮춘다**. 산출물이 처음부터
   나빠질 수 있고, 같은 전역 effort가 reviewer에도 적용되면 검수까지 동시에 약해질 수 있다.
   미검증 심판이 이를 통과시키면 "낮은 비용으로 성공했다"는 잘못된 결론까지 남는다. 따라서
   V-1의 §3 위험과 §5 보류 논리가 V-5에는 같거나 더 강하게 적용된다.
2. **verify가 없는 작업은 객관적 안전망이 없음**: 문서·설계·리뷰 작업은 테스트 통과로 품질 하락을
   잡을 수 없다. T-1이 해결돼도 score 하나만으로 자동 다운그레이드의 안전을 보장할 수 없다.
3. **quota 측정 신뢰도**: TODO.md T-2 관측에는 Codex를 실제로 호출해도 대시보드가 0%대로 보였던
   미확인 문제가 남아 있다. 잘못된 잔량을 입력으로 쓰면 필요 없는 강등 또는 늦은 정지가 생긴다.
   `daily_pace_status()`도 Claude since-reset 실측과 Codex rolling 추정을 다르게 취급한다.
4. **비용과 품질의 목표 함수가 없음**: `benchmarks`는 품질 순위이고 models catalog에는 비용·쿼터
   소비율이 없다. "가벼운 모델"이 실제로 해당 플랜의 주간 쿼터를 얼마나 덜 쓰는지 근거가 없다.
5. **정책 중첩과 진동**: automation planner, `resolve_model()`, `degrade_plan()`, failover, escalation이
   모두 같은 호출을 바꿀 수 있다. 우선순위와 sticky 규칙이 없으면 시작 때 Claude로 옮겼다가 호출
   직전 다시 Codex로 폴백하는 식의 모순이 생길 수 있다.
6. **S4의 실제 절감 폭도 제한적**: risk는 4→3 rounds지만 medium은 애초에 후보 하한 2라 rounds가
   줄지 않고, medium effort 후보는 `medium` 하나라 더 낮출 수도 없다. 배선을 연결하기 전에 이
   규칙이 실제 비용을 의미 있게 줄이는지 관측해야 한다.

## 6. 착수 조건과 검증 기준

자동 full 전환 전 최소 조건:

- backend별 quota 측정의 source/real/reset 의미를 신뢰할 수 있어야 한다. 특히 Codex 0% 관측 문제를
  먼저 결론 내린다.
- T-1의 사전 고정 기준(독립 런 ≥10, verify 통과 ≥3, 실패 ≥3)을 충족해 심판과 verify 관계를
  검토한다. 그 전 예외는 `verify_cmd`가 있는 작업의 producer-only 소규모 실험뿐이다.
- 모델별 비용 또는 quota 소비의 운영 메타데이터와 downgrade chain을 사용자가 명시한다.
- baseline과 정책 적용군에서 verify 통과율, gate 통과율, rounds, 실제 tokens/quota 변화, 재작업률을
  함께 본다. "덜 썼다"만으로 성공으로 판정하지 않는다.
- reviewer 불변, 명시 override 우선, pass_score/verify 불변, unknown measurement 시 no-op을 테스트로
  고정한다.

## 7. 권고

**일부만 구현 권고한다.** 지금 권고하는 것은 §4.1의 **실제 pace→S4 연결과 assist 관측**까지다.
현재 문서상 "구현 완료"로 보이는 S4가 production task에는 쓰이지 않는 간극을 먼저 정직하게
메우고, 실행을 바꾸지 않은 채 추천 결과를 축적하는 것은 저위험·고정보가치다.

반면 **남은 쿼터에 따라 model·effort·backend를 자동으로 바꾸는 full 적용은 지금 착수하지 않는다.**
T-1 미완료, Codex quota 측정 신뢰도 미확인, 모델 비용 메타데이터 부재라는 세 선행조건이 동시에
남아 있다. 특히 V-1보다 producer 품질에 직접 개입하므로, "기존 함수가 있으니 배선만 잇자"는
수준으로 처리하면 안 된다.

후속 순서는 다음을 권한다.

1. pace snapshot을 역할/backend별 assist decision에 연결하고 §3 시나리오를 회귀 테스트로 고정한다.
2. 실제 런에서 `would_change` 빈도와 예상 rounds/effort 변화를 관측한다.
3. T-1과 quota 계측 선행조건을 충족한 뒤, verify가 있는 작업의 producer-only rounds 축소부터
   canary로 검증한다.
4. 효과와 품질 보존이 확인된 경우에만 명시적 model downgrade chain, 마지막으로 backend 재배정을
   각각 별도 opt-in으로 연다. quota만으로 producer/reviewer 역할을 교체하는 기능은 제외한다.
