# v4.5.0 · F2-7 병렬 fanout 재개 — **계약 선확정** · 2026-07-27 18:30

계획서(v4.3.0 F2-7)가 요구한 "비결정 순서·부분완료 manifest 계약 선확정". **구현 전에** 무엇을
보장하고 무엇을 보장하지 않는지 못박는다. 코드 대조·실증으로 확인한 사실만 근거로 쓴다.

## 0. 현재 상태 (코드 대조)

- `_resume_supported`는 **pipeline·producer-reviewer + 순차(parallel.enabled=false)** 만 허용하고
  `acquire`/`materialize`/`changes`가 있으면 거부한다.
- 재생은 `_load_replay_prefix`가 `step_NN.json`을 읽어 **번호가 연속(1,2,3…)이고 전부 ok**인
  구간만 캐시에 담는다. 중간에 실패·결번을 만나면 **즉시 중단**.
- 재생 판정은 `CallSpec.call_key` = `sha256(worker|task_kind|backend|model|prompt|read_only)[:16]`.
  **단계 번호는 의도적으로 제외**돼 있다(코드 주석 명시).

## 1. 핵심 발견 — 순서 독립은 **이미** 성립한다

실증(`call_key` 3성질):

| 성질 | 결과 | 의미 |
|---|---|---|
| 같은 호출 → 같은 키 | ✅ | 단계 번호가 달라도 재생된다 = **순서 독립** |
| 상류 산출물이 바뀌면 하류 키가 달라짐 | ✅ | 파이프라인 의존성이 **키에 자동 반영** |
| 워커가 다르면 키가 다름 | ✅ | fanout 워커끼리 섞이지 않음 |

따라서 "비결정 순서"는 **키 설계가 이미 해결**했다. 남은 진짜 걸림돌은 하나뿐:
**`_load_replay_prefix`의 '연속 prefix' 요구**. 병렬에서는 완료가 집합(set)이라 2번이 성공해도
1번이 실패하면 2번의 유효한 결과가 버려진다.

## 2. 계약 (구현이 지켜야 할 것)

### C-1. 재생 단위는 **prefix가 아니라 집합**이다
성공한 `step_NN.json`이면 번호 연속 여부와 무관하게 캐시에 넣는다. 안전성 근거는 **키에 프롬프트
전체가 들어간다**는 점이다 — 상류 결과가 달라지면 하류 키가 달라져 **자동으로 재실행**된다(§1 실증).
즉 잘못된 재생은 구조적으로 불가능하다.

### C-2. 손상 파일은 **그 항목만** 버린다(전체 중단 아님)
JSON 손상·필수 필드 누락·`ok != true`는 **해당 step만 제외**하고 나머지는 살린다. 현재는 하나만
깨져도 이후 전부를 버리는데, 병렬에서는 무관한 워커의 결과까지 날리는 과잉 조치다.
단, **읽을 수 없는 파일을 성공으로 간주하지 않는다**(fail-closed 유지).

### C-3. 부분완료는 manifest가 아니라 **step 파일이 진실**이다
별도 "부분완료 manifest"를 새로 만들지 않는다. `step_NN.json`(원자적 기록)이 이미 완료 사실의
단일 출처이고, 이중 기록은 불일치 위험만 늘린다. manifest는 **재개 가능 여부(strict 일치)** 판정에만 쓴다.

### C-4. `materialize`/`changes`는 **재개를 막지 않는다**(조건부 허용)
근거: 두 부작용의 출력 루트는 `yok3x-out/<run_id>`로 **런마다 격리**된다. 재개는 새 run_id를
쓰므로 이전 산출물을 덮어쓰지 않는다. 단 다음을 지킨다.
- 재개 런의 번들은 **현재 트리 기준으로 다시 계산**한다(이전 base 해시를 재사용하지 않는다).
  이미 수락된 변경이 있으면 그 상태가 새 base가 되는 게 맞다.
- `changes.apply_mode="auto_commit"`이면 재개 시 **새 브랜치**(`yok3x/run_<새 run_id>`)에 커밋한다.
  이전 브랜치는 그대로 둔다(사람이 병합·삭제 판단).

### C-5. `acquire`는 계속 제외한다
사전질의는 **LLM 호출 결과가 다음 프롬프트를 좌우**하는데 preflight 단계라 step 파일 계약 밖이다.
재생 대상이 아니므로 재개 시 다시 돈다 = 쿼터 재소모. 허용하려면 acquire 결과도 step으로
기록하는 별도 작업이 선행돼야 한다. **이번 범위 아님.**

### C-6. 병렬 재개의 비결정성 **정직 표기**
재개해도 **실행 순서·워커 동시성은 재현되지 않는다**(스레드 스케줄링). 재현되는 것은
**호출 결과**뿐이다. 따라서 "완전한 결정적 재현"을 주장하지 않는다 — 로그·문서에 그대로 적는다.

## 3. 수용 기준 (구현 완료 판정)

1. 병렬 fanout 런이 중간 실패해도, **성공한 워커는 재실행되지 않는다**(원장 호출 수로 확인).
2. 파이프라인에서 상류가 바뀌면 **하류는 반드시 재실행**된다(키 불일치 경로).
3. step 파일 하나가 손상돼도 **나머지 재생은 유지**된다(C-2).
4. `materialize`/`changes` 런도 재개되고, **이전 run_id 산출물이 훼손되지 않는다**.
5. 기존 순차 재개 테스트(G-1/G-2) **전부 통과**(회귀 없음).

## 4. 하지 않는 것

- acquire 재개(C-5) · 실행 순서 재현(C-6) · 별도 부분완료 manifest(C-3) ·
  **재생 캐시의 교차런 재사용**(다른 run_id의 step을 끌어오지 않는다 — 오염 위험).
