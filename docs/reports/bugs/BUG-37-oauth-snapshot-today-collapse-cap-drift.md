# BUG-37 · OAuth 스냅샷 모델이 '오늘'을 0으로 붕괴시키고 상한을 실시간 드리프트

- **상태**: 수정 완료 (2026-07-24)
- **심각도**: 높음(오늘 사용이 실제로 있는데 0%로 표시 + 하루 상한이 실시간으로 줄어듦 — 사용자 지적)
- **영역**: `yok3x/usage.py` `_pace_inputs`(claude OAuth 경로)

## 증상

claude가 오늘 분명히 사용했는데 `오늘 0%`로 뜨고, 하루 상한이 `11% → 10.7% → 10.3%`로 **실시간 하락**.
사용자: "실제로 오늘 사용한 양이 잡혀야 하는데 왜 0? 상한이 이 순간에도 줄었다. 이러면 안 되는 거 아냐?"

## 근본 원인

OAuth는 주간 %만 주고 **일간 분해가 없다**. 그래서 '오늘'을 하루 시작 스냅샷으로 쟀다:
`오늘 = 현재주간% − 하루시작주간%(start_pct)`, 상한도 `start_pct` 기반. 그런데 `start_pct`는 프로세스가
하루 경계(오후 6시)에 실행 중일 때만 정확히 잡힌다. **프로세스 재기동·소스 플립·전략 변경으로 하루
레코드가 재초기화되면 `start_pct`가 그 순간의 현재값으로 재캡처**된다(디버깅 중 GUI 재기동 다수):
- `오늘 = 현재 − 현재 = 0` 으로 붕괴.
- `start_pct`가 현재값(계속 상승)으로 올라가 상한 `(100−start_pct)/남은일수`가 실시간으로 하락.

관측: start_pct가 67→68→69로 기어오르며 상한 11→10.7→10.3, 오늘 0. (OAuth가 정수 %만 줘서 1% 미만
소비가 안 잡히는 해상도 한계도 겹침.)

## 수정

claude는 **트랜스크립트(과거 토큰이라 프로세스 재기동에 불변)** 의 오늘/이번주 비율로 OAuth 총량을
'오늘분'으로 **환산**해 쓴다(`_pace_inputs`):
```
today_scaled = transcript_오늘% × (OAuth주간% / transcript_이번주%)
→ (current=OAuth주간%, since_reset_known=True, today_used=today_scaled)
```
그러면 기존 since_reset_known=True 경로가 `u0 = current − today_used`(=오늘이전, 과거값이라 하루 안
고정)로 상한을 안정적으로 낸다. 스케일을 OAuth에 맞추므로 BUG-33의 무보정 혼합(current OAuth −
today transcript, 스케일 불일치로 드리프트)과 달리 **요동 없음**. 재초기화돼도 같은 과거값을
재구성하므로 오늘·상한 불변.

실측 검증: `오늘 0% / 상한 10.3%(드리프트)` → **`오늘 9.9% / 상한 13.3%(안정)`**. 트랜스크립트 없으면
스냅샷으로 폴백.

**codex 한계(별개)**: codex는 세션 `rate_limits`의 % 창만 있고 토큰 단위 일간 데이터가 없어 같은 환산
불가 — 정수 스냅샷 델타 유지(현재 오늘 1%). rate_limit 시계열로 하루 델타를 재구성하는 건 후속 과제.

## 검증

- 신규 테스트 `test_pace_inputs_oauth_rescales_transcript_today_for_stable_daily`: 환산값 정확
  (7.1×69/53.9≈9.1) + 사용이 늘어도 u0(오늘이전=상한 앵커) 불변(하루 안정 불변식). 폴백 테스트도 유지.
- 브라우저 실측: claude `오늘 9.9% / 상한 13.3%`. 312 passed.

## 교훈

라이브 총량 스냅샷으로 '오늘'을 재는 모델은 **스냅샷 시점(프로세스 생존)에 의존**해 재기동에
취약하다(오늘=0 붕괴, 앵커 드리프트). 일간 분해는 과거 이벤트/토큰 같은 **재기동에 불변한 소스**에서
재구성해야 안정적이다. 서로 다른 소스를 섞을 땐 스케일을 맞춰라(BUG-33). 관련: [[BUG-33]], [[BUG-34]], [[BUG-36]].
