# BUG-38 · 트랜스크립트 전량 재스캔으로 build_state가 느려져 GUI 저장이 안 되는 듯 보임

- **상태**: 수정 완료 (2026-07-24)
- **심각도**: 중간(대시보드가 매 새로고침 ~13초 → 폴링 요청 적체 → 설정 저장이 반영 안 되는 것처럼 보임, 사용자 지적)
- **영역**: `yok3x/limits.py` `_rolling_claude_tokens`(트랜스크립트 토큰 집계)

## 증상

사용자가 가드 경고 임계를 84%로 바꿨는데 저장이 안 됐다. 조사 결과 `/api/config` POST 자체는 즉시
성공(0.0초, soft_ratio=0.84 디스크 반영)했으나, `/api/state`(대시보드 데이터)가 **>30초 타임아웃**.
GUI가 저장 후 `load()`로 `/api/state`를 다시 부르는데 그게 멎어, 화면이 갱신 안 되고 '저장 실패'처럼 보였다.

## 근본 원인

`_rolling_claude_tokens`가 호출마다 claude 트랜스크립트 **모든 *.jsonl을 read + 줄마다 json.loads** 한다.
한 번의 `build_state`가 창을 여러 개 질의한다: 5h·7d(probe) + 이번주·오늘(일간 페이싱, BUG-37에서 추가) +
autocalibrate = 트랜스크립트 **4~6회 전량 재스캔**. 트랜스크립트가 크면 각 스캔이 수초 → build_state 13초.
브라우저가 그보다 자주 폴링하면 요청이 적체되고, 그 사이 다른 요청(설정 저장 후 load 등)도 지연/멎는다.
(BUG-37에서 일간 스캔 2건을 더해 임계를 넘김 — 기존 비효율이 드러난 것.)

## 수정

**파싱 결과를 파일당 캐시**(`_TRANSCRIPT_EVENT_CACHE`: path→(mtime, size, [(ts, 토큰)])). 트랜스크립트
JSONL은 append-only라 mtime·size가 그대로면 재파싱 불필요. 창 질의는 메모리의 이벤트를 cutoff로 필터만 한다:
- `_file_usage_events(f)`: mtime·size 불변이면 캐시 재사용, 아니면 파싱 후 저장.
- `_rolling_claude_tokens`: 파일별 이벤트를 받아 cutoff 이상만 합산.

결과: build_state 13초 → **콜드 6초(파일당 1회 파싱)·웜 0.4초**. 서버 기동 첫 요청만 스캔하고 이후 폴링은
즉시 응답 → 적체·저장 지연 해소. 토큰 합산 결과는 동일(회귀 테스트 312 passed).

## 검증

- 직접 계측: `build_state` 콜드 6.1s → 웜 0.4s(3회). 서버 `/api/state` 콜드 11s → 이후 0.5s.
- 저장 확인: `guard.soft=0.84`가 API·GUI 슬라이더/라벨에 반영(84). 312 passed.

## 교훈

파생 지표를 여러 창으로 질의할 땐 **원자료 파싱을 1회로** 모으고(파일 캐시), 질의는 메모리 필터로 처리하라.
append-only 로그는 (mtime, size)로 값싸게 캐시 무효화가 된다. 한 요청 안의 반복 I/O는 사용자 눈엔
'기능이 안 됨'(여기선 저장 실패)으로 보인다. 관련: [[BUG-37]](일간 스캔 추가), [[BUG-32]](원자적 저장).
