# BUG-28 · F-08 statusline 후속 경화 — resets_at 쓰레기값 표시 + tmp 동시쓰기 경합

- **상태**: 수정 완료 (2026-07-22)
- **심각도**: 낮음~중간(①표시 정확도 — 사용자 지적 '95084일 후' · ②저확률 동시쓰기 경합)
- **영역**: `yok3x/limits.py` — statusline 캡처/프로브 (F-08 직후 자체리뷰·실사용에서 발견)

## 증상 ① resets_at 비현실적 값 → "95084일 후"

statusline 캐시의 `resets_at`이 비현실적 값(예: 자리표시자 `9999999999`, 또는 밀리초 오인처럼 초의 1000배)일
때, 리셋 카운트다운이 `resets_at − now`로 계산돼 **"리셋 95084일 10시간 후"** 같은 쓰레기가 표시됐다
(사용자 지적). 5h/7d 창 리셋은 현재로부터 수시간~수일 내여야 정상이다.

## 증상 ② 공유 tmp 동시쓰기 경합

`statusline_capture`가 원자적 저장에 **고정 이름 `<path>.tmp`**를 썼다. Claude Code가 짧은 간격으로 여러 번
호출(동시 렌더)하면 두 프로세스가 같은 tmp를 쓰다 손상/경합 가능.

## 근본 원인

- ①: 캡처 시 `resets_at`을 신뢰성 검사 없이 그대로 저장·표시. 소스가 비정상값을 주거나(밀리초 등) 테스트
  잔여 자리표시자가 섞이면 그대로 노출.
- ②: 원자적 rename의 tmp 파일명이 pid로 구분되지 않아 동시 writer가 충돌 가능.

## 수정

- ①: `_extract_statusline_windows`에 **위생검사** — `reset`이 `now−1일` 이전이거나 `now+9일` 이후면 신뢰
  불가로 판단해 `None`(→ 롤링 라벨 폴백). 정상값(수시간~수일)은 유지.
- ②: tmp 파일명을 `<name>.<pid>.tmp`로 **pid 고유화**해 동시 렌더 경합 차단.

## 검증

- `test_statusline_rejects_implausible_reset`: `9999999999`→None(폴백), 정상 epoch→유지.
- 실제: 정상 데이터 5h(3h후)·7d(4일후) 카운트다운 정확, `9999999999`는 롤링으로 폴백('95084일' 소멸).
- statusline 테스트 5 passed, 전체 스위트 그린.

## 교훈

외부(1st-party 포함) 소스에서 받은 시각값도 **표시 전 범위 위생검사**가 필요하다(단위 오인·자리표시자 방어).
잦게 호출되는 핸들러의 원자적 쓰기는 **호출자 고유(pid) tmp**로 경합을 원천 차단한다. 관련: F-08(statusline),
[[BUG-26]](페이싱 표시), docs/statusline-setup.md.
