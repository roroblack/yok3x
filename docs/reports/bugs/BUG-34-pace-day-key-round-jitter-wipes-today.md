# BUG-34 · reset_at 초 이하 지터가 하루키 round()를 튀게 해 오늘 소비가 0으로 리셋

- **상태**: 수정 완료 (2026-07-24)
- **심각도**: 높음(오늘 소비가 하루 중 0으로 반복 초기화 — 페이싱 신뢰 붕괴, 사용자 지적)
- **영역**: `yok3x/usage.py` `_pacing_day_key` · `daily_pace_status`(win_gen)

## 증상

claude "오늘 소비"가 1.6%→1.8%까지 오르다가 **0%로 돌아감**(반복). 어제 리셋(오후 6시) 이후 실제로
사용했는데도 0으로 잡힘. (claude.ai 주간 66% = OAuth와 일치하므로 정확도 문제 아님 — 순수 리셋 버그.)

## 근본 원인

OAuth usage 엔드포인트의 7d `resets_at`이 **정확히 .5초 경계**(관측: `1785056400.501429`)에 있고, 폴마다
초 이하로 미세 드리프트(.41↔.50)한다. 하루 경계 식별자가 `round(reset_at)`(win_gen)·`round(day_start)`
(하루키)를 쓰는데, .5 경계라 드리프트가 `...400`↔`...401`로 **round 결과를 튀게** 했다. 그러면
`rec.win != win_gen` / `rec.date != today`가 매 폴 참이 되어 **spurious 하루 리셋** 발생 → 스냅샷 모델의
`start_pct`가 현재값으로 재캡처 → `used_today = current − start_pct = 0`으로 초기화. (스냅샷 모델은
BUG-33에서 도입 — OAuth엔 일간 분해가 없어 하루시작 스냅샷으로 오늘을 재기 때문에 이 재캡처에 취약했다.)

증거: 레코드 `win=1785056401` ≠ `reset_at_cache=1785056400.41` — 두 값이 어긋나 있었다.

## 수정

하루 경계 식별자를 **분 단위로 양자화**(초 단위 round 폐기):
- `_pacing_day_key`: `int(round(day_start))` → `int(day_start // 60)`.
- `daily_pace_status.win_gen`: `round(reset_at)` → `int(reset_at // 60)`.

리셋 시각은 분 정밀도면 하루/주간 경계 구분에 충분하고, 초 이하 드리프트에 완전 면역이다. 진짜 리셋(주
단위 이동)은 여전히 감지된다. 오염된 live 레코드는 `start_pct = OAuth현재 − transcript오늘추정`으로 복구.

## 검증

- 신규 테스트 2: reset_at을 .0~.99로 흔들어도 하루키·win_gen 불변; 지터된 reset로 재호출해도 used_today
  누적 유지(0 리셋 안 됨).
- 실측: `yok3x pace` 2회 연속 `claude 오늘소비 3/23%p` 안정(리셋·요동 없음). 306+2 passed.

## 교훈

부동소수 시각을 경계 식별자로 쓸 땐 **초 단위 round()를 쓰지 말 것** — 소스가 .5 경계에 있으면 미세
지터에 결과가 튄다. 필요 정밀도(여기선 분)로 양자화하라. 스냅샷/누적 상태는 경계 식별자 안정성에
민감하므로(재캡처 위험) 더욱 그렇다. 관련: [[BUG-33]](스냅샷 모델 도입), [[BUG-26]](페이싱 하루 경계).
