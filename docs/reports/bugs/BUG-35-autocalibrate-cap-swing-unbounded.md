# BUG-35 · 자동 캘리브레이션 cap이 회당 무제한으로 튀어 3배씩 널뜀

- **상태**: 수정 완료 (2026-07-24)
- **심각도**: 중간(5h/7d 상한이 하루 중 246M→423M→793M로 요동 — 페이싱 헤드룸 신뢰 저하, 사용자 지적)
- **영역**: `yok3x/limits.py` `autocalibrate_claude`

## 증상

claude 5h 상한이 하루 중 `246M → 423M → 793M`(약 3배)로 널뛰었다. 사용자: "왜 계속 줄어/늘어?"
페이싱 표시의 상한 %가 같은 소비량인데도 오르내려 신뢰가 깨졌다.

## 근본 원인

autocalibrate는 `cap = tokens / (live_pct/100)`로 상한을 역산한다. 5h처럼 **창이 작아 %가 빠르게
변하는** 곳은 live_pct가 폴마다 흔들리고, %가 작을수록(예 5%) 분모가 작아 파생 cap이 **노이즈에
크게 증폭**된다(5% → 4%면 cap이 25% 뛴다). 기존 코드는 파생 cap을 `min/max_calib_multiple`
(0.001x~1000x, 사실상 무제한)만 통과하면 **그대로 저장**해서, 노이즈가 그대로 상한 스윙이 됐다.

## 수정 (끄지 않고 고쳐서 정확하게 — 사용자 요청)

**회당 변화량을 ±`calib_max_step`(기본 25%)로 클램프.** 단, **이미 보정된 값(저장 override>0)에만**
적용한다:
- 첫 보정(저장값 0=plan preset뿐): 클램프 없이 현실로 즉시 스냅 → 빠른 초기 수렴.
- 이후 보정: ±25%로 제한 → 단발 노이즈 감쇠, 스윙 소멸. 파생값이 꾸준히 한쪽이면 여러 스텝에
  걸쳐 그쪽으로 수렴하므로 **정확도는 유지**된다(끄기·억제가 아니라 안정화).

"끄자"는 선택지를 사용자가 거부("문제가 있으면 개선하고 고쳐서 정확하게 만들어야지") → 클램프로
정확도를 지키면서 안정화하는 방향으로 재설계.

## 검증

- 신규 테스트 `test_autocalibrate_claude_clamps_swing_and_converges`: 파생 cap이 5배 폭등을 시도해도
  회당 ≤25%만 반영, 6스텝에 걸쳐 단조 수렴(스윙 없음).
- `test_autocalibrate_claude_allows_cache_read_inflation`: 153배 파생도 비현실 거부는 안 되지만
  회당 +25%만(500M→625M) 반영됨을 확인.
- 첫 보정(override 0)은 클램프 없이 스냅(`test_..._saves_cap_from_live_percent` 불변 통과). 310 passed.

## 교훈

측정값을 역산해 파라미터를 자동 갱신할 땐 **회당 변화량을 제한**하라 — 특히 분모가 작아 노이즈가
증폭되는 소스(작은 %/짧은 창)는 단발 값을 그대로 반영하면 발진(oscillation)한다. 초기 수렴 속도와
지속 안정성은 "첫 보정만 자유, 이후 클램프"로 양립시킬 수 있다. 관련: [[BUG-33]], [[BUG-36]].
