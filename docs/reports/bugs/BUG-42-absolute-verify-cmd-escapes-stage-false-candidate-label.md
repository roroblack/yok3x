# BUG-42 · 절대경로 verify_cmd가 스테이징을 우회해 '거짓 candidate 라벨'을 만듦

- **상태**: 완화 완료 (2026-07-27) — 원천 차단은 불가, **거짓 라벨은 차단**
- **심각도**: 높음(T-1 지상진실 오염 — 검증 안 된 후보를 "검증됨"으로 기록)
- **영역**: `yok3x/orchestrator.py` `_run_round_verify` / F2-11 잔여 위험 감사
- **발견**: F2-11 감사 중 **실증 재현**(추정 아님)

## 증상(재현 로그)

스테이징에는 후보(`CANDIDATE`)를 넣었는데, `verify_cmd`가 절대경로로 **원본 트리**를 읽었다:

```
[verify-stage] round 1: 후보 1파일 검증 → ...\yok3x_stage_...\workdir
verify_scope 라벨: candidate
verify가 실제로 읽은 내용: ORIGINAL      ← 후보가 아니라 원본
```

즉 `verify_ok`가 **후보에 대한 사실이 아닌데** `verify_scope="candidate"`로 기록된다.
T-1은 이 라벨만 지상진실로 쓰므로(`calibration.py:34`), 그대로면 **캘리브레이션 결론이 오염**된다.

## 근본 원인

F1-f 스테이징은 `cwd`만 격리 사본으로 바꾼다. 그러나 `verify_cmd`는 `shell=True`로 실행되는
**임의 명령**이라 절대경로를 쓰면 cwd와 무관하게 원본을 읽는다. cwd 격리는 상대경로 명령에만 유효하다.

## 수정 (완화 — 정직한 한계 인정)

stdlib만으로 임의 셸 명령을 샌드박싱할 수는 없다. **막지는 못해도 거짓 라벨은 막는다**:
`verify_cmd`의 **인자**에 절대경로가 있으면 `verify_scope`를 `candidate`가 아니라
**`untrusted_verify_cmd`** 로 기록하고 사유를 로그로 남긴다. 소비자(`calibration`)는
`== "candidate"`만 라벨로 인정하므로 오염 관측이 자동 배제된다.

**정밀도**: 첫 토큰(실행 파일)은 검사에서 제외한다 — venv 인터프리터 절대경로
(`"C:/venv/python.exe" check.py`)는 스테이징의 스크립트를 돌리므로 정상이다. 위험한 건
'무엇을 검증하는가'를 가리키는 인자(`pytest C:/repo/tests`, `--rootdir=C:epo`)다.
이 구분이 없으면 기존 정상 픽스처가 전부 오탐된다(실제로 첫 구현에서 3건 오탐 발생 → 수정).

## 검증

- 재현 테스트: 절대경로 명령 → 라벨이 `untrusted_verify_cmd`, 로그에 사유 출력.
- 탐지 정확도 11케이스(상대경로 5·절대경로 인자 4·인터프리터 절대경로 2) **오탐/미탐 0**.
- 기존 스테이징 테스트 3건이 정상 통과(오탐 없음). 360 passed.

## 남은 한계(정직 표기)

절대경로가 없어도 우회는 가능하다(환경변수, `cd ..`, 심볼릭 링크, 상대 상위경로 `../`).
이 완화는 **가장 흔하고 조용한 실수**를 잡을 뿐 보안 경계가 아니다. 신뢰 경계가 필요하면
컨테이너·별도 사용자 권한 같은 OS 수준 격리가 필요하며, 그건 의존성0 범위를 벗어난다.

## 교훈

**격리는 "무엇을 격리했는지"까지 라벨에 반영해야 한다.** cwd만 바꿔 놓고 "후보를 검증했다"고
기록하면, 검증 대상이 실제로 무엇이었는지에 대한 거짓말이 데이터에 들어간다. 측정 파이프라인에서는
"막지 못하는 위험"이라도 **라벨의 정직성**은 지킬 수 있다. 관련: [[BUG-40]](거짓 verify 실패), [[BUG-25]].
