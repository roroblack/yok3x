# BUG-39 · cp949 콘솔에서 로그의 '—'가 UnicodeEncodeError를 내 작업 단계를 죽임

- **상태**: 수정 완료 (2026-07-26)
- **심각도**: 중간~높음(로그 출력 실패가 **실제 작업 결과를 유실**시킴 — 래칫 체크포인트 1개 소실 실측)
- **영역**: `yok3x/orchestrator.py` `_log`

## 증상

R-7 2단계(auto-commit 래칫)를 실저장소에서 검증하던 중, 라운드 1 체크포인트가 커밋되지 않고 사라졌다:

```
[ratchet] 실패(런은 계속): UnicodeEncodeError: 'cp949' codec can't encode character
          '—' in position 70: illegal multibyte sequence
[ratchet] r2 체크포인트 커밋 7730a336 (1파일)
```

r2는 커밋됐는데 **r1은 통째로 유실**. 원인이 로직이 아니라 **로그 출력**이었다.

## 근본 원인

`_log`가 `print(msg)`를 그대로 호출한다. Windows 한국어 콘솔 기본 인코딩은 **cp949**인데,
로그 문구에 쓰인 **em dash `—`(U+2014)는 cp949에 없다** → `print`가 `UnicodeEncodeError`를 던진다.

한글은 cp949에 있어서 대부분의 로그는 멀쩡했고, `—`가 들어간 줄에서만 터졌다. 그래서
"가끔 특정 단계만 실패"하는 형태로 나타났다. 게다가 예외가 호출부의 `try/except`에 잡히면
**그 단계 전체가 실패로 처리**된다(래칫은 체크포인트 유실, 다른 호출부라면 더 큰 영향 가능).

이 문구 패턴(`— `)은 코드베이스 로그 전반에 흔해 **잠재 범위가 넓은 버그**였다(래칫이 드러냈을 뿐).

## 수정

`_log`를 인코딩 실패에 견디게 한다 — **로그가 런을 죽이지 않는다**:
- `print` 실패 시 콘솔 인코딩으로 `encode(enc, "replace").decode(...)` 해 낮춰 찍는다(조용히 삼키지 않음).
- **파일 로그(`run.log`)는 utf-8이라 원문 그대로 보존**된다 — 정보 손실 없음.
- 부수 발견: `orchestrator.py`에 `sys` import가 없어 폴백 자체가 `NameError`를 낼 뻔했다(같이 수정).

## 검증

- 신규 테스트 `test_log_survives_console_encoding_limits`: stdout을 `cp949(errors="strict")`로 바꿔
  `'체크포인트 — em dash 포함'`을 찍어도 **예외 없음**, 출력은 비어 있지 않고, `run.log`엔 `—` 원문 보존.
- 실저장소 재검증: 수정 후 r1·r2 **둘 다** 커밋됨(유실 없음). 344 passed.

## 교훈

**로그·관측 코드는 절대 본작업을 죽이면 안 된다.** 특히 콘솔 인코딩은 OS·로캘마다 다르므로
(Windows 한국어=cp949) 비-ASCII 장식문자(`—`, `≈`, `·`)를 쓰는 출력은 폴백이 필요하다.
또한 이번처럼 **`except Exception`이 넓게 감싼 부가기능**은 진짜 원인(출력 실패)을 가려
"기능이 가끔 안 된다"로 보이게 한다 — 예외 메시지를 반드시 로그에 남겨야 추적된다.
관련: [[BUG-19]](출력 경로가 기능을 깨뜨린 사례).
