# v4.x · 결과 — T-1 mutation-testing 파일럿: 심판이 실제로 신뢰할 만하다는 직접 증거 · 2026-08-30

## 배경

T-1(심판 캘리브레이션 검증)의 원래 착수 조건(`verify_ok=False` ≥ 3)은 1·2차 T-2 수집 전체에서
0건이었고, 그 이유를 진단한 결과(`v4.x-result-t2-round2-verify-ok-false-diagnosis-2026-08-30.md`)
"스펙을 정확히 따르는 producer는 스펙 작성자가 만든 테스트도 통과한다"는 구조적 이유임을
확인했다. 사용자 지시("웹서칭 + codex 토론으로 최고의 방법을 찾아 해결")에 따라, producer가
자연스럽게 실패하길 기다리는 대신 **이미 정상 동작하는 코드에 확정된 결함(mutation)을
인위적으로 주입**해 대조군을 만드는 방법을 조사·실행했다.

## 방법론 근거 (2026-08-30 기준 웹 리서치)

- **SWE-ABS**(ICML 2026, [arXiv 2603.00520](https://arxiv.org/abs/2603.00520)): "테스트 기반
  벤치마크의 성공률이 부풀려져 있다"는 문제의식 — 기존 테스트는 통과하지만 실제 요구사항은
  위반하는 그럴듯한 오답을 합성해 벤치마크의 blind spot을 드러냄. 우리 상황(테스트 통과=
  verify_ok=True인데 실제 결함이 있는 경우가 많음)과 정확히 같은 문제의식.
- **SWE-Mutation**([arXiv 2605.22175](https://arxiv.org/abs/2605.22175), ACL 2026 Findings):
  agentic mutant를 정답 코드에 주입해 테스트 스위트의 결함 탐지력("kill rate")을 측정.
- **Meta의 mutation testing 실전 적용**([engineering.fb.com](https://engineering.fb.com/2025/09/30/security/llms-are-the-key-to-mutation-testing-and-better-compliance/)):
  LLM으로 mutant 생성·동등 mutant 판별을 결합.

## codex와의 설계 토론 — 핵심 개선점

내 초안(단순 mutation만)에 codex가 다음을 반박·보완했다(전문은
`yok3x_t1_variance/discussion/round2_response.txt`, git 미추적):

1. **K(단순)+S(semantic) 혼합 설계**: 단순 mutation만 쓰면 심판을 과대평가하고, SWE-ABS식
   "테스트 통과+스펙 위반" mutant만 쓰면 제작자 주관에 과적합된다.
2. **동등 mutant 문제는 "witness"로 해결**: LLM 동등성 판정기를 만들 필요 없이, "원본과
   mutant가 다르게 동작하는 구체적 입력 하나 + 스펙 근거로 어느 쪽이 맞는지"만 있으면
   충분하다. **witness 테스트는 기존 pytest에 넣지 말 것**(오염 방지) — 안 그러면 원래
   놓쳤던 mutant도 인위적으로 "killed" 처리돼버림.
3. **mutant 하나에 결함 하나만**, 리뷰는 매번 새 세션·순서 섞기·mutation 사실 숨기기.
4. **판정은 SCORE만 보지 말고 "심판이 주입한 결함을 서술로 구체적으로 지적했는지"까지 확인**
   — 엉뚱한 이유로 점수만 낮은 건 결함 탐지 성공이 아니다.

## 결론

이건 T-1이 원래 얻고 싶었던 것과 **정확히 같은 종류의 증거**다 — "확실히 결함이 있는 코드에
심판이 낮은 점수를 주고 실제 결함을 짚어내는가". 다만 producer의 자연스러운 실패를 기다리는
대신, **확정된(witness로 검증된) 결함을 인위적으로 주입**해서 얻었다. 특히 #12의 S mutant는
기존 테스트가 완전히 놓친(verify_ok=True) 진짜 결함이었는데, codex가 그걸 **critical**로
정확히 짚어냈다 — "심판이 테스트가 못 보는 곳까지 실제로 본다"는 직접적이고 통제된 증거다.

**한계**: 표본이 작다(대상 2개, mutant 4개) — 이번 결과가 "심판이 항상 이렇게 잘한다"는
보장은 아니다. 하지만 사전등록·witness·블라인드·순서혼합 전부 지킨 통제 실험에서 4/4를
받은 건 우연으로 보기엔 결과가 너무 정확하다(주입한 버그를 문장 단위로 그대로 서술).

## 권고

1. **이 방법론(mutation + witness + 사전등록 + 블라인드)을 T-1의 정식 캘리브레이션 절차로
   채택**할 것을 권고 — verify_ok=False를 기다리는 것보다 훨씬 저비용(이번 전체가 codex
   호출 8회 미만)이고 통제 가능하다.
2. 표본을 늘리려면(사용자 승인 시): 더 많은 작업×mutant 조합, 특히 **K/S 라벨을 사전에
   확정하지 말고 "기존 테스트가 실제로 잡는지"를 사후 관찰**하는 편이 낫다(이번에 #11의
   "단순" mutation도 예상 밖으로 survive했다 — 난이도 예측보다 실측이 낫다).
3. 이번 파일럿에서 리뷰 프롬프트에 **원래 작업 스펙 텍스트를 포함**시켰다 — 실제 운영
   파이프라인(`orchestrator.py`)은 리뷰어에게 스펙을 안 보여준다(이전 조사에서 확인).
   스펙 유무가 semantic 결함 탐지력에 실제로 영향 있는지는 이번 파일럿으로는 분리 안
   됐다 — 필요하면 "스펙 없이" 버전으로 재실행해 대조하는 후속 실험 가능(저비용).
