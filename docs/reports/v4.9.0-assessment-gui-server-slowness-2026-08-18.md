# GUI 서버 간헐적 응답 지연 조사 — 2026-08-18

## 결론

이번 증상은 `guiserver.py` 자체의 메모리 누수보다는 시스템 전체 CPU 경합이 주원인으로 보인다. 확인된 `claude`, `Code.exe`, `VirtualBoxVM.exe`의 장시간 CPU 사용은 yok3x 코드가 해결할 수 없는 외부 요인이다. CPU 경합은 새 프로세스 생성, 파일 파싱, Python 스레드 실행 및 네트워크 응답을 모두 늦출 수 있다.

## 호출 경로와 지연 가능성

- `/api/state`는 `build_state()`를 동기 실행한다. `today_totals()`와 백엔드별 `check_backend()` 3회가 먼저 수행된다.
- `check_backend()`의 실제 probe는 백엔드별 캐시와 락을 사용한다. 현재 Codex TTL은 60초이고, 캐시 미스 시 app-server subprocess 생성·응답을 기다리므로 CPU 경합 상황에서는 수 초 이상 걸릴 수 있다. 같은 백엔드의 동시 캐시 미스는 락으로 직렬화되며, 이는 스탬피드를 막는 대신 후속 요청이 첫 probe를 기다리게 한다.
- `coach_messages()`도 백엔드 3개에 대해 `check_backend()`를 호출한다. 정상적인 TTL 적중 시 subprocess를 다시 만들지는 않지만, 캐시가 만료된 시점에는 메인 게이지와 코치 경로가 한 요청 안에서 중복 판정될 수 있다.
- `_routing_preview()`는 세 route kind를 순회하면서 availability callback을 호출한다. 같은 백엔드가 여러 route에서 다시 검사될 수 있었고, 이번 수정으로 한 번의 미리보기 계산 안에서는 백엔드별 결과를 한 번만 조회한다.
- `_profile_routes()`는 상태 probe를 직접 호출하지 않고 설정 기반 라우팅을 계산한다. `limits.list_models()`는 backend별 구현에 따라 외부 CLI/HTTP 조회가 될 수 있으나 각 호출의 timeout이 이미 존재한다.
- `claude_token_status()`, 최근 실행/작업 파일 읽기, JSON 직렬화도 CPU·디스크 경합에 따라 느려질 수 있다. 요청 경로에 무제한 대기 코드는 확인되지 않았지만, 여러 유한 timeout의 합이 `/api/state` 지연 상한을 의미하지는 않는다.

## ThreadingTCPServer 및 GIL 검토

`ThreadingTCPServer`는 연결마다 요청 스레드를 만들므로 폴링 요청이 계산 중 겹치면 대기 스레드가 늘어난다. subprocess/소켓 대기 중에는 GIL이 주된 병목이 아니지만, JSON 파싱·상태 조합 같은 Python CPU 작업은 GIL을 공유한다. 따라서 외부 프로세스가 CPU를 선점하면 스케줄링 지연이 커지고, 여러 요청이 동시에 무거운 probe를 기다리면 응답 없음처럼 보일 수 있다. 이번 증거만으로 bounded worker pool이나 서버 구조 교체를 할 근거는 부족하다.

## 적용한 최소 수정

1. `_routing_preview()`의 가용성 callback을 백엔드별 로컬 메모이즈로 변경했다. 한 state build 안의 중복 `backend_available()` 및 잠재적 `check_backend()` 호출을 줄이며 결과 의미는 바꾸지 않는다.
2. Handler 소켓에 15초 timeout을 설정했다. 부분 요청을 보내고 멈춘 클라이언트가 요청 스레드를 무기한 점유하는 상황을 제한한다. 이는 이미 실행 중인 `build_state()`를 중단시키는 timeout은 아니다.

`limits.py`의 backend lock/TTL, app-server 종료 로직, `ThreadingTCPServer` 구조는 실측 근거 없이 변경하지 않았다. Python 스레드에서 실행 중인 `build_state()`를 강제 종료하는 방식도 적용하지 않았다.

## 운영 판단

현재 관측과 코드 구조를 합치면 우선순위는 yok3x 내부 누수보다 시스템 CPU 경합 완화(장시간 Claude/VS Code/VirtualBox 작업 정리 또는 분산)다. 추가 계측이 필요하면 `/api/state` 전체 시간과 `build_state()` 각 단계, 특히 Codex cache miss 대기 시간을 별도로 기록하는 것이 좋다.
