# GUI 서버 다운/복구 근본 원인 조사 및 수정 — 2026-08-19

## 결론

2026-08-20 실행 관찰에서 `/api/state` 지연의 직접 원인을 확인했다. 요청 스레드가 `build_state()` 안에서 backend probe를 수행했고, Codex probe는 `codex app-server` 왕복/정리까지 15초 이상 걸렸다. Claude OAuth/세션 파일 조회도 약 4~6초 걸렸다. 여러 요청이 동시에 들어오면 같은 backend 캐시 락에서 함께 지연됐다.

지난 2026-08-18 보고서는 시스템 CPU 경합을 주원인으로 추정했지만 요청·probe·락 대기 로그가 없어 코드 경로를 확정하지 못했다. 이번에는 상시 파일 로그와 실제 포트 8760 관찰로 이를 검증했다.

## 실측 증거

로그 파일: `.yok3x/guiserver.log` (append-only)

- 첫 `/api/state`: `request ... duration_ms=25085.6 status=200`
- Claude: `slow backend check backend=claude duration_ms=5860.4 source=claude_oauth`
- Codex: `slow probe backend=codex duration_ms=15154.2 source=codex_sessions`, 이어서 `slow backend check ... duration_ms=15404.2`
- 전체 build: `slow build_state duration_ms=25060.9`
- 동시 3개 요청 관찰에서 각 요청이 약 15~30초 지연됐다. 캐시 만료 시 요청 스레드가 같은 동기 probe를 기다리는 기존 구조와 일치한다.
- 락 계측 보완 후 `probe lock wait backend=codex duration_ms=15172.2 cache_filled=true`가 기록되어, 후속 요청이 첫 probe 완료를 기다린 사실도 확인했다.
- 기존 15초 socket timeout도 `Request timed out` 및 `status=None`으로 기록됐지만, 이미 실행 중인 `build_state()`를 중단하지는 못했다.

## 적용한 수정

1. `guiserver.py`에 모든 요청 경로·처리 시간·상태 코드·예외를 `.yok3x/guiserver.log`에 기록했다.
2. `/api/state`는 마지막 완성 snapshot을 즉시 반환하고, snapshot 생성/갱신은 `gui-state-refresh` daemon thread에서 수행한다. 최초에는 `state_status=warming` 최소 응답을 반환한다.
3. `limits.py`에 GUI 전용 `probe_gui()`/`list_models_gui()`를 추가했다. stale 값은 즉시 반환하고 backend별 refresh는 한 번만 백그라운드에서 예약한다.
4. `usage.py`에 선택적 probe 함수 주입을 추가했다. 기존 `probe()`와 CLI의 동기 최신값 의미론은 유지했다.

GUI 폴링 간격(`gui/index.html`)은 변경하지 않았다.

## 수정 후 검증

새 프로세스에서 3개 동시 GET 결과:

```
status=200 duration_ms=42.1
status=200 duration_ms=42.0
status=200 duration_ms=40.3
```

서버 로그에도 같은 시점에 `request path=/api/state duration_ms=1.4~3.9 status=200`이 남았다. 백그라운드 state build가 수 초 이상 걸려도 HTTP 요청 스레드는 더 이상 그 작업을 기다리지 않는다.

`python -m py_compile yok3x/guiserver.py yok3x/limits.py` 통과. 전체 `pytest -q`는 3회 모두 동일하게 `1 failed, 242 passed, 1 skipped, 353 errors`였고, errors의 공통 원인은 저장소 밖 임시 경로 `C:\Users\playdata2\AppData\Local\Temp\pytest-of-playdata2` 접근 거부(`PermissionError: [WinError 5]`)였다. 코드 assertion 실패가 아니라 fixture setup 단계의 환경 문제다.

## 남은 관찰 사항

백그라운드 refresh 자체의 CPU/파일 스캔 비용은 남아 있지만 HTTP 서버 가용성과 분리됐다. 운영 중에는 `slow build_state`, `slow probe`, `GUI state snapshot refresh failed`를 기준으로 후속 최적화할 수 있다.
