# v4.x · 리뷰 — 멀티에이전트 기술 적정성 (코딩 자동화 코칭 툴 관점) · 2026-07-16

사용자 요청: "멀티에이전트를 이용한 코딩 자동화 프로그램 제작 코칭 툴 관점에서 지금 멀티에이전트
기술이 적당한가?" + 부속 질문(effort ultracode, temp/top_p/top_k/few-shot, 채팅 진행률·토큰·시간 표시).

## 종합 판정
**틈새(투명·안전·의존성0 오케스트레이션)에는 충분히 견고. 단, "멀티에이전트 코딩 자동화 코칭 툴"의
다음 티어로 가려면 5개 격차가 뚜렷.** 대부분 이미 로드맵에 있음(병렬 fanout·MCP·체크포인트).

## 지금 가진 것 (강점)
- **패턴 다양성**: producer-reviewer · pipeline · fanout · 조건부 라우팅(escalate) · ACQUIRE preflight.
- **교차 패밀리 적대적 검수(ARIS)**: 리뷰어를 다른 모델 패밀리로 강제 + 반증 우선(봐주기 방지).
- **역할별 정보계약**: ACQUIRE Questioner/Answerer/Resolver — 읽기전용·독립 조사·정적 선주입.
- **안전 봉투**: 요금/토큰/페이싱 가드 · 승인 게이트 · 자가검증(SELF-CHECK) · fail-safe.
- **의존성 0·투명**: 프레임워크 락인 없음, 전 과정 로깅·감사 가능.
- **2계층 메모리**: knot(장기, consolidation) + 런상태/ACQUIRE QA(단기). 자기오염 방지(BUG-13) 학습됨.
- **백엔드 무관**: claude/codex/gemini 혼용, 폴오버.

## 격차 (다음 티어로 가려면)
### G1. 진짜 병렬성 부재 — **가장 큰 격차**
`run_fanout`이 **순차 실행**이고 `call_worker`가 단계번호·usage 원장을 공유. "멀티에이전트"라면서
동시성이 없음. → `call_workers_parallel()`(단계번호·승인·비용 원자적 선예약) 필요. **ACQUIRE S3에 포함 예정.**
### G2. 워커가 '행동'을 못 함 (텍스트 생산자)
워커는 파일을 못 만짐(안전상 기본 차단). 실제 코딩 에이전트는 편집·실행·테스트를 함. →
**MCP 워커도구**(로드맵) + ACQUIRE read-only 프로필(S2에서 첫 조각 착수). 승인/화이트리스트/감사 전제.
### G3. 앙상블/토론/투표 패턴 없음
현 검수는 2-에이전트(producer-reviewer). SOTA는 N-에이전트 **투표·토론(debate)·best-of-N + 심판**.
→ fanout 병렬화(G1) 위에 "N 후보 생성 → 심판 합성" 패턴을 얹으면 저비용으로 도입 가능.
### G4. 체크포인트/재개 없음
가드 stop·승인 대기·크래시 후 런을 N단계부터 이어갈 수 없음. → **LangGraph 체크포인트 재개**(로드맵).
멀티에이전트 런은 길고 비싸서 재개 가치 큼.
### G5. 관찰가능성(코칭 표면) 미흡 — **코칭 툴이라 특히 중요**
스텝별 **토큰·비용·시간이 이미 기록**되는데(backends `BackendResult`→`step_NN.json`) **채팅에 노출 안 됨**.
코칭 툴이라면 "이 에이전트가 지금 얼마 썼고 왜 느린지"가 보여야 함. → 아래 부속 질문 #4에서 구현 가능.

## 부속 질문 답
### Q1. effort "ultracode" (사용자 지적)
- claude CLI 유효 effort = **low/medium/high/xhigh/max**(CLI가 직접 응답). `--effort ultracode` **없음**.
- "ultracode"는 effort가 아니라 **프롬프트 키워드/클라우드 워크플로 모드**(`ultrareview` 계열). effort
  드롭다운엔 부적합. 원하면 **별도 "ultracode 모드" 토글**(작업 프롬프트에 키워드 주입)로만 가능 —
  단 과금되는 클라우드 멀티에이전트라 우리 자체 오케스트레이터와 역할 중복. **권장: effort와 분리된
  옵션으로, 비용 경고와 함께 opt-in.** (지금 우선순위는 낮음.)
### Q2. temperature / top_p / top_k — **대부분 CLI가 안 받음(우리 누락 아님)**
- **claude CLI**: temperature/top_p/top_k **미노출**(코딩 신뢰성 위해 고정). 
- **gemini CLI**: 해당 플래그 없음(설정파일 thinkingLevel 정도).
- **codex CLI**: 범용 `-c key=value`는 있으나 **추론 모델(gpt-5.x)은 sampling 파라미터를 고정/무시**하는 게 일반적.
- 결론: 이건 **UI 누락이 아니라 백엔드(코딩 CLI)들의 의도적 제약**. 억지로 노출하면 "안 먹는 노브"가 됨.
  **대안(진짜 다양성)**: temperature 대신 **모델·effort·프롬프트 앵글을 다르게** 한 후보 생성(best-of-N).
  이게 코딩 CLI 환경에서 다양성을 얻는 올바른 방법.
### Q3. few-shot / one-shot — **가능하고 유용(우리가 프롬프트를 통제하니까)**
- 우리는 프롬프트를 직접 조립하므로 **task spec/GUI에 예시(few-shot) 필드**를 넣어 워커 프롬프트 앞에
  주입하면 됨. 코칭 툴에 잘 맞음("이렇게 짜줘" 예시로 가르치기). 의존성 0. **도입 권장(경량).**
  주의: knot 자동주입과 달리 사용자가 명시한 예시만(자기오염 방지).
### Q4. 채팅에 에이전트별 진행률·시간·토큰 표시 — **가능(데이터 이미 있음)**
- 스텝별 `total_tokens`·`cost_usd`·`duration_ms`가 **이미 `step_NN.json`에 기록됨**. 채팅 렌더
  (`renderConsoleLog`)에 스텝 카드마다 **토큰/시간/비용 배지**를 추가하면 됨. **구현 쉬움.**
- **완료 %는 근사만 가능**: LLM 스트리밍은 정확한 "% 완료"가 없음. → **스텝 진행률**(예: 3/5=60%)과
  **실행중/완료 상태**로 표시. 진짜 intra-step %는 없다고 명시(허위 진행바 금지).

## 권장 우선순위 (코칭 툴 가치 기준)
1. **Q4 관찰가능성**(스텝별 토큰·시간·비용 채팅 표시) — 데이터 있음, 코칭 핵심, 저비용. **먼저.**
2. **G1 병렬 fanout**(ACQUIRE S3) → 그 위에 **G3 앙상블(best-of-N + 심판)**.
3. **Q3 few-shot 필드**(경량, 코칭 적합).
4. **G4 체크포인트 재개** · **G2 MCP 워커도구**(안전 전제) — 로드맵대로.
5. Q1 ultracode 모드 · Q2 sampling 노브 — **하지 않음/최후순위**(백엔드 제약·역할중복).

## 한 줄 결론
멀티에이전트 **기반기술은 적정**(패턴·교차검수·안전·투명). "코칭 툴"로서의 다음 도약은
**① 관찰가능성 노출 ② 진짜 병렬 + 앙상블 ③ few-shot 코칭 표면**이고, 이 셋이 temperature 같은
"안 먹는 노브"보다 훨씬 높은 가치. 대부분 이미 로드맵 위에 있음.
