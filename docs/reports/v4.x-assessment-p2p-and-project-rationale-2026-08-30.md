# v4.x · 평가 — P2P 네트워크 도입 여부 + "왜 yok3x인가"에 대한 답 · 2026-08-30

## 배경

두 질문에 답한다: (1) 여러 yok3x 설치를 P2P로 연결해 작업을 공유할 수 있는가, (2) "요즘
스킬로 codex·claude 직접 연동하면 되는데 굳이 yok3x를 왜 쓰냐"는 외부 개발자의 비판을
어떻게 볼 것인가. 둘 다 2026-08-30 기준 웹 리서치로 답했다.

---

## 1. P2P 네트워크 — 지금은 권하지 않음

### 조사 결과

2026년 P2P 멀티에이전트 코디네이션은 활발한 연구 영역이다:
- [Matrix](https://arxiv.org/abs/2511.21686): 중앙 오케스트레이터를 없애고 제어·데이터
  흐름을 분산 큐로 직렬화하는 P2P 프레임워크.
- [AgentNet](https://openreview.net/forum?id=tXqLxHlb8Z): DAG 구조 네트워크에서 에이전트가
  자율적으로 능력을 진화·협업하는 RAG 기반 탈중앙 프레임워크.
- [MOD-X](https://arxiv.org/pdf/2507.04376): 이종 AI 에이전트 상호운용을 위한 모듈형
  개방 교환 프레임워크 제안.
- Google의 **A2A(Agent-to-Agent) 프로토콜**: 프레임워크를 넘나드는 에이전트 통신·협업·
  위임을 위한 개방 프로토콜.

### 이 분야 자체가 인정하는 미해결 과제

검색 결과가 공통으로 꼽는 핵심 난제: **"탈중앙화 탐색(discovery)·적대적 견고성
(adversarial robustness)·증거 기반 신뢰(evidence-based trust)"**. 마지막 항목이 정확히
yok3x가 이번 세션 T-1에서 씨름한 문제다 — **단일 로컬 환경, 두 backend(claude/codex)뿐인
상황에서도** "심판(codex-critic)의 SCORE를 신뢰할 수 있는가"를 mutation-testing으로
검증하는 데 세션 전체가 들었다. P2P는 이 신뢰 문제를 **아직 학계도 제대로 못 푼 채** 임의의
낯선 참가자·네트워크 규모로 확장하는 것과 같다.

### 아키텍처적 충돌

P2P는 NAT traversal·피어 탐색·암호화가 필요해 사실상 새 의존성(libp2p·WebRTC·IPFS류)이나
최소한 시그널링/랑데부 서버가 필요하다. yok3x는 이미 같은 이유로 두 번 비슷한 걸 반려·유예한
전례가 있다:
- **V-4(herdr)**: "상시 백그라운드 서버"라는 이유로 코드 통합 비권고, 개인 도구 사용만 권고.
- **V-6(TeamFlow 연동)**: TeamFlow 자체가 "한 팀 전용 설계"이고 멀티테넌시·호스티드 MCP는
  "지금 안 함, 트리거 발생 시 재검토"로 그 프로젝트 스스로 미룬 상태 — V-6도 그 범위를
  그대로 물려받았다("설치자 누구나"가 아니라 "이미 아는 협업자끼리").

### 결론 — 권고

**지금은 P2P를 도입하지 않는다.** 실제 요구("아는 사람들끼리 작업 공유")는 이미 계획서까지
나온 V-6(TeamFlow 경유)로 충분히 맞는다. "낯선 사람들끼리 익명 P2P로 작업을 공유"가 진짜
필요해지는 시점이 오면, 그건 이 문서가 다루는 범위를 넘는 별도의 큰 조사(신뢰 모델·탐색
프로토콜·의존성 수용 여부부터 재검토)가 필요하다.

**재검토 조건**: (a) V-6가 실제로 쓰이기 시작해 "아는 사람 범위"로는 부족하다는 신호가
나오거나, (b) A2A 같은 프로토콜이 성숙해 의존성 추가 없이(또는 아주 가볍게) 쓸 수 있는
수준이 되거나, (c) 사용자가 "낯선 사람과의 공유"를 명시적으로 원할 때.

## 2. "왜 yok3x인가" — skill 기반 직접 연동과의 비교

### 비판의 정확한 형태

"요즘 스킬 써서 그냥 codex랑 claude 연동시키면 되는데 굳이 yok3x를 왜 쓰냐."

### 조사 결과 — 실제로 그런 도구들이 있다

- [**skill-codex**](https://github.com/skills-directory/skill-codex) /
  [**codex-delegator**](https://github.com/eddiearc/codex-delegator): Claude Code
  플러그인/스킬로, Claude가 `codex exec`를 직접 호출해 서브태스크를 위임한다. 모델·추론
  강도·샌드박스 모드를 고르고, 필요 시에만 쓰기/네트워크 권한을 연다.
- **Fusion류 도구**(예: 검색에 나온 "software factory" 포지셔닝의 도구): 칸반 보드,
  태스크당 git worktree, 실시간 대시보드, 워크플로 엔진, 서드파티 CLI 플러그인 — pnpm
  TypeScript 모노레포(패키지 12개·플러그인 18개)로 구현됨.

### 정직한 평가

**"가끔 다른 모델에게 서브태스크를 위임"이 목적이면, skill-codex 쪽이 실제로 더 낫다.**
설치 즉시 쓸 수 있고, 세션 하나 안에서 자연스럽게 위임이 끝난다. 이 좁은 용도에서는 그
개발자의 비판이 맞다 — yok3x는 과하다.

**하지만 yok3x는 그 "한 번 위임"을 훨씬 넘어서는 문제를 푼다.** 검색으로 찾은 어떤 도구도
아래를 하지 않는다:

| yok3x가 하는 것 | skill-codex류 | Fusion류 |
|---|---|---|
| 객관적 게이트(verify_cmd 실제 테스트 통과 확인, 모델 의견이 아님) | ✗ | 불명(워크플로 엔진 수준, 게이트 성격 불명) |
| **심판(리뷰어) 신뢰도를 실측으로 검증**(이번 세션 T-1 mutation-testing — SCORE가 실제 결함을 잡는지 통제실험) | ✗ | ✗ |
| 쿼터/한도 인식 페이싱(5h/7d 한도 앞 자동 속도조절·강등·failover) | ✗ | ✗ |
| 원자적 게시(stage-then-publish, 크래시 시 부분쓰기 방지) | ✗ | 불명 |
| 구조화 리뷰 프로토콜 + 캘리브레이션 데이터 축적(T-6/V-9) | ✗ | ✗ |
| 의존성0(순수 stdlib) | 대체로 가벼움(스킬 하나) | **아님**(모노레포, 패키지 12+플러그인 18) |

**결론**: 두 종류의 도구는 서로 다른 문제를 푼다.
- skill-codex류 = "이번 한 번 다른 모델한테 물어보기"의 마찰을 줄이는 도구.
- yok3x = "반복적으로, 안전장치를 달고, 쿼터를 관리하면서, **심판을 신뢰할 수 있는지
  검증해가며** 자동화"하는 도구.

이 차이를 설명하지 않으면 "왜 굳이"라는 반응은 당연히 나온다 — 겉모습만 보면 둘 다
"클로드가 코덱스를 부른다"이기 때문이다. 실제 차별점은 표면(누가 누굴 부르는가)이 아니라
**그 호출 주변에 쌓은 안전장치·검증·데이터**에 있다.

### 남는 질문(이 문서가 답하지 않음)

이 차별점들이 **실제로 그만큼의 가치**가 있는지(예: 심판 신뢰도 검증에 들인 노력만큼 실사용
가치가 나오는지)는 별도로 계속 지켜봐야 한다 — 이번 T-1/T-6 작업 자체가 "만들어놓고 실사용
검증 안 된 기능"(a1 MCP, sync_layer 등)을 여러 번 발견한 세션이었다는 점도 정직하게
기록해둔다.
