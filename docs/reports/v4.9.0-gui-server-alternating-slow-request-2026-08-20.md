# v4.9.0 GUI 서버 alternating slow request 후속 조사 — 2026-08-20

## 결론

`/api/state`의 6~7초 `200`은 `_gui_state()`, `probe_gui()`, `list_models_gui()`의 동기 대기가 아니었다. `BaseHTTPRequestHandler.handle_one_request()`를 감싼 계측이 요청 라인을 받기 전 소켓 read 대기까지 요청 처리 시간으로 합산하고 있었다. 브라우저/preview 계층이 TCP preconnect를 열고 약 7초 뒤 요청을 보내면, 실제 응답은 수 ms여도 로그에는 6~7초 `200`으로 남는다.

15초 `path=` 타임아웃도 같은 경로다. 요청 라인을 보내지 않은 연결이 `self.connection.settimeout(15.0)`의 read timeout까지 대기한 것이다. py-spy에서 해당 스레드는 `socket.readinto()` → `http.server.handle_one_request()`에 있었고 backend probe 락, snapshot 락, GIL 경합은 관찰되지 않았다.

## 조사 근거

- `Handler`에는 기존에 `protocol_version` 설정이 없었고, 기본값은 HTTP/1.0이었다.
- HTTP/1.1 `http.client` 두 세션을 3.5초 어긋나게 7초 주기로 폴링했을 때 기존 서버의 실제 왕복은 `2.6~451.6ms`였으며, keep-alive 응답은 `HTTP/1.0`과 `will_close=True`로 종료됐다. 단순한 지속 커넥션 재사용만으로는 문제 패턴이 재현되지 않았다.
- TCP 연결 후 8초 뒤 `GET /api/state`를 보내는 preconnect 재현에서 기존 로그는 `duration_ms=8003.8 status=200`이었다. 요청을 보내기 전 py-spy 덤프는 `socket.readinto` → `http.server.handle_one_request` → `yok3x/guiserver.py:823`였다.
- 수정 후 같은 재현의 로그는 `duration_ms=1.6 status=200`이었고, 요청 전송 후 클라이언트 측 응답 측정도 약 `2.0ms`였다.
- 수정 후 두 클라이언트 동시 폴링 결과: A=`11.1, 21.9, 16.2ms`, B=`18.7, 16.2, 6.1ms`; alternating 6~7초 분포는 재현되지 않았다.

## 수정

`yok3x/guiserver.py`만 동작 변경했다. `Handler.protocol_version = "HTTP/1.0"`을 명시하고, 응답에 `Connection: close`를 보내며, `parse_request()` 완료 시점부터 정상 요청 duration을 측정한다. 요청 라인을 받지 못한 timeout은 기존처럼 전체 대기 시간과 빈 path로 남긴다.

백그라운드 snapshot 구조와 `limits.py`, `usage.py`는 변경하지 않았다.
