# GUI 서버 종료 관측성 조사 및 개선 — 2026-08-21

## 결론

기존 23회 재시작 기록에서 GUI 서버 자체가 크래시했다는 증거는 발견되지 않았다. 이번 변경은 추정 원인의 버그 수정이 아니라, 다음 재발 시 정상 종료·외부 종료·메인 루프 예외를 로그만으로 구분하기 위한 관측성 개선이다. 신규 버그는 등록하지 않았다.

## 기존 재시작 기록 조사 결과

- `.yok3x/guiserver.log`의 `Traceback` 3건은 모두 malformed JSON을 받은 `do_POST()`의 `_read_body()` 예외였다. 해당 예외는 요청 처리기가 잡아 400 응답을 반환했으며 서버 종료로 이어지지 않았다.
- 같은 기간 Windows Application Error 이벤트에는 `python.exe` 크래시 기록이 없었다.
- 재시작 전 로그는 정상 요청 또는 BUG-51에서 다룬 15초 idle connection timeout으로 끝났고, 연속 오류·메모리 부족·응답 지연 폭증 없이 다음 `binding GUI server` 기록이 시작됐다.
- 따라서 확인된 자료는 크래시보다 외부 stop/restart 또는 정상 종료 패턴과 부합한다. 다만 기존 구현은 종료 로그가 없었고 `serve_forever()`에서 샌 예외는 파일이 아닌 stderr에만 기록됐으므로, 과거 로그만으로 종료 주체를 확정할 수는 없었다.

## 적용한 관측성 개선

`yok3x/guiserver.py`의 서버 수명 주기에 다음 기록을 추가했다.

- `serve_forever()`의 일반 예외를 `GUI server main loop crashed`와 전체 traceback으로 기록한 뒤 다시 발생시킨다. 기존의 비정상 종료 의미는 바꾸지 않는다.
- `finally`에서 shutdown 전후에 `GUI server stopping/stopped (reason=...)`를 기록한다. reason은 `normal_return`, `keyboard_interrupt`, `main_loop_exception:<예외형>`, `external_signal:<시그널명>`으로 구분된다.
- 지원되는 환경에서는 `SIGTERM` 핸들러를 등록한다. 핸들러는 외부 종료 신호 수신을 기록한 뒤 `SystemExit(128 + signum)`를 발생시켜 종료 의미를 유지하면서 `finally` 로깅을 실행한다. 시그널 미지원 또는 메인 스레드가 아닌 호출 환경에서는 등록을 조용히 생략하며, 종료 시 기존 핸들러를 복원한다.
- Python의 `logging.FileHandler`는 `StreamHandler`를 상속하고 `emit()`마다 `flush()`를 호출하므로 정상적인 로그 레코드는 매번 flush된다. 추가로 shutdown의 마지막 `stopped` 레코드 뒤 모든 GUI 핸들러에 best-effort `flush()`를 수행한다.

## 종료 경로 실측

충돌을 피하려고 18760~18765 포트를 사용했다.

- 메인 루프에 `RuntimeError("injected-main-loop-failure")`를 주입: 파일에 `GUI server main loop crashed` traceback, `reason=main_loop_exception:RuntimeError`의 stopping/stopped가 모두 기록됐고 프로세스는 exit 1로 종료됐다.
- `KeyboardInterrupt` 주입: `reason=keyboard_interrupt`의 stopping/stopped가 기록됐고 exit 0이었다.
- 별도 스레드의 `shutdown()`으로 정상 반환: `reason=normal_return`의 stopping/stopped가 기록됐고 exit 0이었다.
- 프로세스 내부 `signal.raise_signal(SIGTERM)`: `external termination signal received signal=SIGTERM`과 `reason=external_signal:SIGTERM`의 stopping/stopped가 기록됐고 exit 143이었다.
- Windows에서 다른 프로세스가 `os.kill(pid, SIGTERM)` 실행: 대상은 exit 15로 즉시 종료됐고 마지막 파일 기록은 `GUI server listening`이었다. 이 환경의 외부 Windows SIGTERM 경로는 Python 핸들러를 실행하지 않는다.
- `taskkill /F /PID <pid>` 실측 시도는 현재 세션 권한에서 `Access denied`로 거부되어 강제 종료 자체는 실행되지 않았다. 시험 프로세스는 이후 `os.kill(pid, SIGTERM)`으로 정리했다. `/F`가 실제 실행되면 OS가 프로세스를 강제 종료하므로 Python 코드와 `finally`, 로거 flush가 실행될 기회가 없으며 종료 로그를 보장할 수 없다.

즉 POSIX 또는 Python 런타임이 실제로 SIGTERM을 전달하는 환경에서는 신규 핸들러가 유효하지만, Windows 강제 종료를 포착할 수 있다고 간주해서는 안 된다. 그런 경우 `listening` 이후 종료 줄이 없는 것 자체가 비협조적 외부 종료/강제 종료 후보를 가리키는 관측 신호다.
