# v5.x · 결정 — 그래프 저장소: PostgreSQL+AGE 도입 여부 · 2026-07-20

사용자 제안: "그래프DB가 필수인 것 같다. PostgreSQL에 그래프 확장(Apache AGE)을 넣어 쓰면 되지 않나?"
codex 공동검토(read-only 샌드박스) + Claude 독립 재현 검증.

**결론: 그래프 *데이터 모델*이 필요하다는 판단은 옳다. 그러나 PostgreSQL+AGE는 지금 도입하지 않는다.
(d) 파일 정본 + 관계 이벤트 → 필요 시 stdlib `sqlite3` 파생 인덱스.**

## 왜 지금이 아닌가 — 실측

| 항목 | 실측값 |
|---|---|
| `knowledge/` 노트 | 22개 / 72KB |
| **노트 간 관계(간선)** | **0개 / 22** |
| 태그 다양성 | 22/22 전부 `[run, claude-orchestrator]` — 정보량 0 |
| 런 | 17 |
| 검색 | `_load_notes()` 전량 선형 스캔 + 최신성 감쇠 |

**그래프DB의 전제는 "간선이 존재하고 그것을 따라가는 질의가 필요함"이다. 우리 간선은 0이다.**
간선 0인 그래프는 리스트이며, 어떤 엔진을 얹어도 의미가 없다. **순서가 뒤집힌 도입이다.**

## PostgreSQL+AGE의 실제 비용 (codex 조사)
| 항목 | 부담 |
|---|---|
| 설치 | AGE 공식 빌드 안내가 Linux/macOS 중심. **Windows는 사실상 Docker/WSL 또는 자체 DLL 빌드** |
| 실행 | 개인 로컬 CLI에 **서버 프로세스 lifecycle**(기동·포트·인증·비정상종료·로그) 추가 |
| 의존성 | stdlib에 PG 드라이버 없음 → `psycopg` 필수. 공식 AGE Python 드라이버는 **psycopg + ANTLR runtime + NetworkX**까지 요구 |
| CI | upstream 회귀 테스트·Python 드라이버 CI 모두 **Ubuntu 전용** → Windows 품질을 우리가 소유 |
| 호환 | AGE는 **PG 메이저 버전에 결합**. `PG major + AGE version` 고정 필요 |
| 운영 | `pg_dump/restore` 백업·복구 시험, 메이저 업그레이드 시 호환 AGE 바이너리 선설치 |

→ "DB 하나 추가"가 아니라 **새 운영 계층 도입**이다.

## 이미 기각한 Redis/RabbitMQ와의 비교
| | Redis/RabbitMQ | PostgreSQL+AGE |
|---|---|---|
| 같은 점 | 외부 설치·서버 프로세스·포트/인증/버전·비-stdlib 클라이언트 — **정체성을 동일하게 위반** |
| 다른 점 | 메시지 전달·분산 워커 조정 | 영속 관계·트랜잭션·다중 작성자 |
| 대체재 | 로컬 단일 오케스트레이터엔 파일·프로세스 큐로 충분 | 현재 규모엔 sqlite3가 핵심 요구를 훨씬 싸게 충족 |

Postgres가 **다르다는 사실이 지금 예외를 정당화하지는 않는다.** 다만 기본 백엔드가 아니라
**향후 선택형 multi-host 백엔드**라면 정체성과 양립 가능하다.

## sqlite3로 못 하는 것이 로드맵에 있는가 — **현재 없다**
가능: `커밋→버그→테스트→심볼→파일→런` 순회 · `논문→가설→결과→superseded_by` ·
run/agent/artifact 계보 · 도달가능성/조상후손/순환방지.
한계: **동시 writer 1개**(WAL에서도) · 원격 다중 PC 공용 DB·권한·HA · 임의 Cypher 탐색 UI.
→ 전부 현재 로드맵 밖.

### 성능 재현 검증 (Claude 독립 측정) — **codex 수치는 40배 낙관적이었음**
| | codex 주장 | Claude 재현 |
|---|---|---|
| 10만 노드·50만 간선, 5홉 median | 0.72ms | **28.82ms** (p95 59.11ms, DB 15MB) |

codex 측정은 in-memory·warm-cache로 보이며 **디스크 WAL 환경에서 40배 느리다.**
**그러나 결론은 유지된다**: 현재의 **노드 4,500배·간선 ∞배** 규모에서도 p95 59ms로 여유가 크다.
(교훈: 자문 수치는 재현 전까지 근거로 쓰지 않는다.)

## 결정과 정량 트리거
**지금 할 일: 간선을 생산한다.** 엔진 선택이 아니라 데이터 모델 문제다.
1. 안정적 ID — `commit:…` `bug:BUG-21` `symbol:…` `run:…`
2. 타입 간선 — `fixes` `covered_by` `defined_in` `observed_in` `tests` `superseded_by`
3. git·pytest·런 종료 시 **자동 간선 생성**
4. 실제 반복 질의와 latency 계측
※ 현 frontmatter 파서는 완전한 YAML이 아니므로 중첩 YAML 대신
  **한 줄 JSON 관계 필드 또는 `.yok3x/relations.jsonl`**(이벤트 로그)이 stdlib 원칙에 맞다.
  sqlite는 여기서 **재생성 가능한 파생 인덱스**로 만든다(정본은 파일 — 유실 시 재구축 가능).

| 단계 | 트리거 |
|---|---|
| 파일만 유지 (**현재**) | 노트 <1,000 · 간선 <10,000 · 검색 p95 <100ms |
| sqlite3 인덱스 도입 | 간선 ≥100 **또는** 반복 다중홉 질의 ≥3종/월 **또는** 노트 ≥1,000 · p95 ≥100ms |
| sqlite 재벤치 | 노드 ≥100,000 · 간선 ≥1,000,000 · DB ≥1GB · 5홉 p95 ≥200ms 중 하나 |
| PostgreSQL 검토 | **원격 다중 머신 필요** · 독립 writer ≥3 지속 경합 · 간선 ≥10,000,000이며 튜닝 후에도 p95 >500ms |
| AGE까지 검토 | 위 PG 조건 + 유지할 재귀 CTE ≥10종 **또는** 사용자가 임의 가변길이 경로 질의 작성 필요 |

**PostgreSQL이 필요해진다고 해서 AGE까지 자동으로 필요한 것은 아니다**(재귀 CTE는 PG에도 있다).

## 한 줄
**"DB가 없어서 못 하는 게 아니라 간선이 없어서 못 한다."** 간선을 먼저 만들고,
sqlite가 실측에서 실패할 때 PostgreSQL을 검토한다.
